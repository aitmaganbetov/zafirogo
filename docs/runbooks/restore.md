# Runbook: резервные копии и восстановление

Этап 6, блок O2. Код — `deploy/backup/`, задачи — `task backup:*`, учения в CI — `.github/workflows/backup-drill.yml`,
решения и открытые вопросы — [`docs/open-questions/stage6-backup.md`](../open-questions/stage6-backup.md) (BK-N).

## 1. Коротко

| Что | Как защищено | Источник правды после сбоя |
|---|---|---|
| **Postgres** (деньги, ledger, клиенты, настройки) | WAL-G: базовые копии раз в сутки + непрерывный архив WAL в S3 другого региона, сжатие zstd, шифрование OpenPGP | копия + WAL (PITR на любую секунду за ≥ 28 суток) |
| **Valkey** (сессии, лимиты, присутствие ПК, кэш идемпотентности гостя) | AOF (`appendonly yes`) — только для перезапуска; копий нет | ничего не нужно: состояние временное, деньги защищены вторым рубежом в Postgres |
| **NATS JetStream** (поток событий `zafiro-events`) | файловое хранилище; в проде — кластер из 3 узлов, поток R3; копий нет | `outbox_events` в Postgres (публикация повторяется) |

| Сценарий | RPO (потеря данных) | RTO (цель) | Раздел |
|---|---|---|---|
| Потеря инстанса/диска БД | ≤ 1 мин (`archive_timeout = 60 s`) | ≤ 1 ч | [§6](#6-потеря-инстанса-бд) |
| Порча данных (ошибка, баг, ручной SQL) | всё после момента T — переносится вручную (§7.6) | ≤ 2 ч (с поиском T) | [§7](#7-порча-данных--pitr) |
| Потеря региона/площадки | ≤ 1 мин + задержка выгрузки WAL | ≤ 4 ч | [§8](#8-потеря-региона) |
| Потеря Valkey | 0 денег (повторный вход сотрудников) | минуты | [§9](#9-потеря-valkey) |
| Потеря NATS | 0 (outbox) | минуты | [§10](#10-потеря-nats) |

Замеры (локальный стенд, SeaweedFS на том же хосте, 02.11.2026, `deploy/backup/drill-e2e.sh`):

| Операция | Объём | Время |
|---|---|---|
| Базовая копия + хранение + проверка архива (`backup-run.sh`) | демо-база 16 МБ | 2–3 с |
| Полная базовая копия | 570 МБ данных (pgbench) → 27 МБ в S3 | 6 с (≈ 95 МБ/с чтения) |
| Восстановление: загрузка копии + запуск | 570 МБ | 8 с (загрузка 4 с) |
| Проигрывание WAL | 397 МБ WAL (30 с нагрузки, 2 100 tps) | ≈ 13 с (≈ 30 МБ/с) |
| Архивация WAL под нагрузкой 2 100 tps | 25 сегментов за 30 с | без отставания, 0 ошибок |
| Полные учения (латест + PITR, проверки, amcheck) | демо-база | ≈ 1 мин вместе с подъёмом окружения |

Оценка для прода (уточнить на staging и в первых учениях `drill-prod`): база 20 ГБ при 100–200 МБ/с из S3 —
загрузка 2–4 мин; WAL за сутки (1–5 ГБ) — 1–3 мин; с реакцией дежурного и проверками RTO укладывается в 1 ч.
pgbench сжимается нетипично хорошо; реальные данные — в 3–5 раз хуже, время загрузки считать по несжатому объёму.

## 2. Как устроен бэкап

```
Postgres (primary) ──archive_command: walg wal-push──▶ S3 (другой регион) ◀──backup-push── сайдкар backup
       │ PGDATA (том, только чтение для сайдкара)                    ▲            (раз в сутки, BACKUP_AT UTC)
       └── unix-сокет (общий том) ───────────────────────────────────┘
Учения/восстановление: новый Postgres ← walg backup-fetch + restore_command: walg wal-fetch (закрытый ключ)
```

- **Образ** `deploy/backup/Dockerfile` — тот же `postgres:18.6` (digest), что в staging, + WAL-G v3.0.9 (статическая
  сборка из исходников тега, коммит сверяется) + скрипты `deploy/backup/bin`. `task backup:image`.
- **WAL**: `archive_mode=on`, `archive_command='/usr/local/bin/walg wal-push %p'`, `archive_timeout=60s`.
  Postgres не удаляет сегмент, пока он не выгружен: при недоступном S3 растёт `pg_wal` (алерт §4).
- **Базовые копии**: `backup-run.sh` — `backup-push` (каждая 7-я полная, остальные дельты; `WALG_VERIFY_PAGE_CHECKSUMS`
  проверяет контрольные суммы страниц — в PG 18 они включены по умолчанию), пометка месячной копии,
  `delete retain FULL 5`, `wal-verify integrity timeline`, метрики.
- **Шифрование**: OpenPGP, на сервере БД — **только открытый ключ**. Прочитать копии может только тот, у кого
  закрытый ключ и пароль: учения (`drill-prod`), дежурный при восстановлении. Проверено: `wal-fetch` с открытым
  ключом — `openpgp: incorrect key`; без ключа обёртка `walg` отказывается работать.
- **Секреты** — файлы (`/run/secrets/*`), не переменные окружения (`deploy/backup/bin/walg`).

### Политика хранения (BK-3)

- Базовая копия раз в сутки в 02:17 по Астане (`BACKUP_AT=21:17` UTC), полная — раз в неделю (`WALG_DELTA_MAX_STEPS=6`).
- Хранятся 5 последних полных цепочек (`BACKUP_RETAIN_FULL=5`) со всеми дельтами и WAL — **PITR на любую секунду
  за последние ≥ 28 суток** (это покрывает «7 ежедневных + 4 недельных» и даёт PITR не 7, а 28 суток: ошибки в деньгах
  находят при закрытии месяца и сверке Z-отчётов, а не за неделю).
- Первая копия каждого месяца — постоянная (`backup-mark`), хранится 12 месяцев (`BACKUP_KEEP_MONTHLY`), без PITR
  (только состояние на момент копии). Сам ledger в базе не удаляется никогда — копии не заменяют архив операций.
- Прод: бакет с версионированием и Object Lock (compliance, срок ≥ 35 суток) — копию нельзя удалить даже
  украденными ключами; удаление по политике хранения — отдельной учёткой не с сервера БД (BK-5).

## 3. Ключи и секреты

| Секрет | Где лежит | Кто имеет |
|---|---|---|
| Открытый ключ OpenPGP | сервер БД (`walg_pgp_public`) | все узлы БД |
| **Закрытый ключ OpenPGP + пароль** | менеджер секретов/сейф **вне** прод-площадки; окружение GitHub `backup-drill` | дежурные DBA (2 человека), учения |
| Ключи S3 «запись» | сервер БД | сервер БД и сайдкар |
| Ключи S3 «чтение» | окружение `backup-drill`, сейф | учения, восстановление |
| Ключи S3 «удаление» (хранение) | только задача хранения | — |

- Ротация ключа OpenPGP: создать новую пару офлайн (`deploy/backup/gen-secrets.sh` в чистый каталог) → открытый ключ
  на сервер БД → `task backup:now` (новые копии и WAL шифруются новым ключом). Старый закрытый ключ хранить, пока в
  хранилище есть зашифрованные им копии (до 12 месяцев — месячные копии). Учения проверяют оба ключа, пока живы старые копии.
- Потеря закрытого ключа = потеря всех копий. Поэтому ключ в двух независимых местах, проверка — каждые учения.

## 4. Мониторинг (передано O3)

- `zafiro_backup_last_success_timestamp_seconds` (textfile в томе `backup-metrics`, для node_exporter) — алерт,
  если старше 26 ч; `zafiro_backup_last_run_success == 0`; `zafiro_backup_wal_verify_ok == 0` — критично.
- `pg_stat_archiver`: `failed_count` растёт, `now() - last_archived_time > 5 мин` при нагрузке — критично (RPO нарушен).
- Размер `pg_wal` > 50 % тома — критично (S3 недоступен, диск кончится и Postgres остановится).
- Результат `backup-drill` — красный прогон — тикет дежурному.

## 5. Учения восстановления

- **Каждую неделю** — `backup-drill.yml`, job `drill-prod` (self-hosted раннер в сети хранилища, ключи из окружения
  `backup-drill`; включается `vars.BACKUP_DRILL_PROD=true`): latest + PITR на «5 минут назад» на **настоящих** копиях,
  проверки ниже, отчёт со временем — в сводке прогона. До подключения прода — то же на копиях staging:
  `task backup:restore-drill`.
- **На каждом PR**, меняющем `deploy/backup/**` или `db/migrations/**`, и раз в неделю — `drill-e2e` на одноразовом
  окружении: данные → копия → «метка» → T → «порча» (списание всего баланса клиента и удаление кассовых операций) →
  latest и PITR на T. Локально: `task backup:drill-e2e`.
- **Раз в квартал** — ручные учения §6 целиком (новая машина, переключение DSN) с секундомером; итог — в журнал
  учений (дата, объём базы, время каждого шага, кто выполнял, проблемы).

Проверки каждого восстановления (`deploy/backup/restore-drill.sh`, `deploy/backup/verify.sql`):

1. `goose version` = номер последней миграции репозитория, `goose status` без Pending.
2. **Деньги**: для каждого клуба и клиента `member_balances.balance/bonus_balance` = Σ проводок `ledger_entries`
   по счетам `member_main/member_bonus` (запрос `ListMemberBalanceDrift` из `db/queries/balances.sql`, по всем клубам);
   Σ проводок каждой операции = 0; у каждой операции есть проводки.
3. Партиции журналов (`ledger_*`, `audit_log`, `activity_logs`, `api_request_logs`) на текущий и следующий месяц.
4. RLS включена и FORCE на каждой таблице с `club_id` (кроме платформенного `platform_logs`), роли
   `zafiro_app`/`zafiro_platform` и их логины без SUPERUSER/BYPASSRLS.
5. `pg_amcheck` (heap + btree) — без повреждений.
6. PITR: ни одной операции ledger позже T; в `drill-e2e` — отпечаток денег (`fingerprint.sql`: операции, Σ балансов,
   остатки счетов клуба, кассовые операции по клубам) совпадает с исходной базой на T **до тиына**.

Самопроверка `verify.sql` (02.11.2026): на восстановленной копии вручную внесены расхождение баланса на 1 тиын,
несбалансированная проводка, снятый FORCE RLS и неверная ожидаемая версия — все четыре проверки упали.

## 6. Потеря инстанса БД

Признаки: Postgres недоступен, диск/ВМ потеряны, `/readyz` всех инстансов 503. Копии и WAL целы в S3.

| # | Кто | Действие |
|---|---|---|
| 1 | Дежурный | Объявить инцидент, остановить инстансы приложения (`docker compose stop app1 app2` / scale 0) — не копить ошибки агентов. |
| 2 | Дежурный | Если старый диск доступен хотя бы на чтение — **не удалять**: попытаться выгрузить хвост `pg_wal` (`walg wal-push` по оставшимся сегментам) — это сокращает RPO до нуля. |
| 3 | Дежурный | Новая машина/том. Образ `zafiro-postgres-walg` (тот же digest). Секреты: S3 чтение + закрытый ключ (временно, только на время восстановления). |
| 4 | Дежурный | Восстановление: контейнер с пустым томом данных и `restore-into.sh auto` (до конца архива) — как `restore-drill.sh` прогон `latest`, но том постоянный: `docker run -v <том>:/var/lib/postgresql … restore-into.sh auto`. Ждать `SELECT NOT pg_is_in_recovery()` = `t`. |
| 5 | Дежурный | Проверки: `psql -v expected_version=<N> -f deploy/backup/verify.sql` (§5) — все ОК. `pg_amcheck --install-missing`. |
| 6 | Дежурный | Вернуть боевой режим: перезапустить Postgres штатной командой (compose `postgres` из `compose.backup.yml`: `archive_mode=on`), убрать закрытый ключ с машины. Новая линия времени (timeline 2) пишется в тот же префикс — так и должно быть. |
| 7 | Дежурный | **Сразу** `task backup:now` (новая полная копия на новой линии времени) и `walg wal-verify integrity timeline` = OK. |
| 8 | Дежурный | Действия «после восстановления» (§11). Запустить приложение, `/readyz`. |
| 9 | Поддержка | Клубам: короткое уведомление; агенты переподключатся сами (джиттер до 60 с). |

## 7. Порча данных → PITR

Примеры: ошибочная миграция с изменением данных, баг, который массово неверно списал деньги, ручной `UPDATE/DELETE`.
Ledger только дополняется (триггеры + права), поэтому одиночные ошибки в деньгах исправляются **компенсирующими
операциями**, а не PITR. PITR — когда испорчено много и компенсация невозможна или ненадёжна. **Решение о PITR
принимает руководитель инцидента**: всё, что произошло после T, придётся вносить заново (§7.6).

1. **Остановить запись**: инстансы приложения — stop/scale 0 (клубы на старом Laravel не затронуты). Агенты ПК
   продолжают работать офлайн по своим правилам; новые покупки не принимаются.
2. **Сохранить улики, ничего не удалять**: текущий кластер не трогать (он нужен для сверки окна после T).
   Выгрузить события JetStream за окно (до любых действий с NATS):
   `nats stream backup zafiro-events ./events-backup` (консистентный снимок потока) и для чтения людьми
   `nats stream view zafiro-events --since <длительность от T−10 мин до сейчас, например 3h> > events-after-T.txt`.
   Поток хранит 72 ч (`ZAFIRO_EVENTS_STREAM_MAX_AGE`) — это список денежных событий (`balance.changed`,
   `sale.completed`, `shop_order.*`) после T.
3. **Найти T** — последний момент, когда данные были верны: `audit_log`, `activity_logs`, `ledger_transactions.created_at`,
   журнал миграций (`goose_db_version.tstamp`), журналы приложения (O3). T берётся **до** первого ошибочного коммита
   (секундная точность; `recovery_target_inclusive=true` включает коммиты ровно в T).
4. **Восстановить рядом** (не на месте): `task backup:restore-drill -- --pitr-only --target-time "<T>" --keep`
   (на проде — то же с переменными прода) поднимет копию на T и прогонит проверки §5. Контейнер остаётся (`--keep`).
   Сверить с испорченным кластером: что именно откатилось (запросы по `ledger_transactions.created_at > T`).
5. **Переключить**: остановить испорченный Postgres (том сохранить под другим именем на ≥ 30 суток), восстановить
   на штатный том с тем же T (`restore-into.sh auto "<T>"`), шаги 5–7 из §6, затем §11.
6. **Перенести операции окна (T, начало инцидента]** — с владельцем клуба и поддержкой:
   - список — из испорченного кластера (`ledger_transactions` после T, кроме ошибочных) и `events-after-T.txt`;
   - каждую верную операцию — заново через интерфейс/API (новые ключи идемпотентности), касса — по чекам и Z-отчётам;
   - `verify.sql` после переноса; Z-отчёты смен, затронутых окном, сверить с наличностью.
7. **Безопасность**: изменения доступа после T откатились — заново применить отзывы сертификатов ПК, блокировки
   сотрудников, смены паролей и ключей API за окно (из журналов приложения/инцидента). Сертификаты ПК, выданные после T,
   в базе отсутствуют — эти ПК потребуют повторной регистрации.

## 8. Потеря региона

Копии и WAL — в S3 **другого региона/провайдера** (прод-требование, BK-4). Объём WAL, не выгруженный к моменту аварии,
— потерян (≤ 1 мин).

1. Руководитель инцидента объявляет переход в резервный регион.
2. Инфраструктура в резервном регионе (IaC/compose: Postgres-образ бэкапа, Valkey, NATS, 2+ инстанса, балансировщик).
   Секреты приложения (подпись токенов, ключи данных, CA агентов) — из менеджера секретов, **не из бэкапа БД**: без
   `ZAFIRO_SECURITY_DATA_KEYS` секреты вебхуков/Telegram в базе не расшифровать, без CA агентов ПК не подключатся.
3. Восстановление как §6 (шаги 3–7) из S3.
4. DNS панели и `agent.<домен>` на новый балансировщик (TTL записей заранее ≤ 300 с). Агенты переподключаются по имени.
5. Новый S3 для копий — снова в другом регионе (не в том, где теперь работает база).
6. §11, уведомление клубов.

## 9. Потеря Valkey

Что теряется: сессии сотрудников (все выходят, вход заново), refresh-токены, лимиты частоты и неудачных входов
(сбрасываются), присутствие ПК (агенты переподключаются, sweeper сверяет за ≤ 5 мин), токены гостей на ПК (гость
входит заново), кэш идемпотентности денежных RPC агента (24 ч), nonce Z-отчёта, билеты WebSocket, состояние оповещений.

Денег не теряется: второй рубеж идемпотентности — в Postgres (`ledger_idempotency`, `billing_requests`: ключ RPC с
префиксом ПК, `server/internal/agent/guestapi/idempotency.go`). Персистентность: AOF `appendonly yes` (+ `everysec`)
— чтобы плановый перезапуск не разлогинивал всех; копий Valkey **не делаем** (BK-8). Действия: поднять пустой
Valkey с тем же паролем → инстансы переподключаются сами (`/readyz` зелёный) → проверить вход и карту клуба.

## 10. Потеря NATS

Что теряется: поток `zafiro-events` (72 ч событий), durable-потребитель `webhooks`, дедупликация по `Nats-Msg-Id`.
Команды агентам — core NATS (не хранятся; долговременные — в `agent_commands`, досылаются по `seq`), отзыв сертификатов
дублируется перечитыванием кэша из БД (`ZAFIRO_AGENT_CERT_CACHE_FULL_RELOAD`).

Персистентность: JetStream file storage; в проде — кластер из 3 узлов и `ZAFIRO_EVENTS_STREAM_REPLICAS=3`; копий нет
(источник правды — `outbox_events`). Действия:

1. Поднять NATS (пустой) — инстансы создадут поток и потребителя (`outbox.EnsureStream`, `CreateOrUpdateConsumer`).
2. Неопубликованные события (`published_at IS NULL`) публикатор отправит сам. Опубликованные, но не обработанные
   потребителем вебхуков, — переопубликовать (под владельцем схемы):
   ```sql
   UPDATE outbox_events SET published_at = NULL WHERE published_at > now() - interval '15 minutes';
   ```
   Это безопасно: `webhook_deliveries` дедуплицирует по `event_id` (UNIQUE), браузеры получат повтор `computer.state`
   и т. п. (идемпотентно для интерфейса).

## 11. После любого восстановления Postgres из копии

Порядок — до запуска инстансов приложения:

- [ ] `verify.sql` и `pg_amcheck` — зелёные; `goose status` — без Pending (если копия старше последней выкладки —
      job миграций `task staging:migrate` / прод-аналог, затем проверки ещё раз).
- [ ] Архив WAL включён, `task backup:now` выполнен, `wal-verify` OK.
- [ ] Партиции: если копия старше 2 месяцев — воркер партиций создаст их при старте; до старта проверить пункт 3 §5.
- [ ] **Valkey: `FLUSHALL`** (после PITR — обязательно; после §6 — желательно): сессии, токены гостей и кэш
      идемпотентности ссылаются на состояние после T; присутствие ПК пересоберётся.
- [ ] **NATS после PITR: удалить поток** `nats stream rm zafiro-events -f` (после выгрузки §7.2): в нём события

# Этап 2 — итоговый отчёт: транспортный слой

План — [`stage-2-plan.md`](stage-2-plan.md). Вопросы этапа — `docs/open-questions/stage2-*.md`.
Решения владельца по вопросам Этапов 1–2 пока не получены: везде повторяется старое поведение.

## Что сделано

| Блок | Пакеты | Что внутри |
|---|---|---|
| Вход и права | `internal/auth/**` | Argon2id с прозрачным перехешем bcrypt Laravel; access-токен 10 мин (HMAC, ротация ключей по `kid`) + refresh с ротацией и отзывом сессии при повторе; CSRF; права дословно из `ClubPermissions`/`ClubRoles`/`StaffPermissions` (51 право, 93 маршрута); режим просмотра суперадмина; все `throttle:` Laravel в Valkey с точными лимитами |
| Регистрация ПК | `internal/pki`, `internal/agent/enroll`, `internal/grpc` | Свой CA (ECDSA P-256 — совместим с SChannel/.NET), одноразовые коды (в БД — HMAC), CSR → сертификат на 30 дней, продление, отзыв (в т.ч. при удалении ПК), кэш отзывов в памяти + NATS; gRPC с mTLS; клиент .NET 10 проверен на полном цикле |
| Поток агента | `internal/agent/{stream,presence,commands}` | Один поток на ПК; присутствие в памяти + Valkey; команды с `seq`/`command_id`, повторная доставка после реконнекта, маршрутизация между инстансами через NATS |
| События | `internal/{activity,outbox,webhook,realtime,worker/leader}` | Журнал действий (99 событий старого кода) в той же транзакции, `activity_logs` в месячных партициях; outbox → NATS JetStream без потерь и дублей; вебхуки с HMAC, ретраями и защитой от SSRF; WebSocket админки по клубу и правам вместо 5 мест polling |
| REST админки | `api/openapi.yaml`, `internal/http` | 28 операций: касса (смены, X/Z, продажи, пополнения, приход/расход, возвраты), склад, клиенты и история из ledger, тарифы, сессии ПК, карта клуба. Суммы — целые тиыны, ошибки — тексты старого кода, денежные POST идемпотентны |
| gRPC гостя | `internal/agent/guestapi`, `internal/shop` | Вход гостя (пароль, регистрация, QR), токен гостя в Valkey, тарифы и покупки, пакеты, «игра на весь баланс», завершение сессии, магазин (заказ с ПК через ledger и склад), друзья и переводы, чат, переводы интерфейса, PIN выхода |
| Сборка | `internal/app`, `internal/config`, `cmd/zafiro` | Один бинарник: два пула БД (`zafiro_app` без обхода RLS и `zafiro_platform`), Valkey, NATS, gRPC, HTTP, воркеры; секреты не печатаются; корректная остановка с переподключением агентов; dev-окружение создаёт логины БД без паролей в репозитории |

## Проверка

- Интеграционные тесты (реальные Postgres, Valkey, NATS через testcontainers) во всех пакетах, включая сквозные:
  HTTP → сервис → БД по P1-сценариям кассы и балансов; gRPC с mTLS: регистрация ПК → поток → вход гостя → покупка
  (идемпотентный повтор) → `BalanceChanged` в потоке → завершение сессии с возвратом; полный запуск приложения
  с регистрацией ПК, отзывом сертификата и остановкой без утечек горутин.
- Права — вся матрица ролей; режим просмотра; изоляция клубов (RLS); лимиты.
- **Нагрузка:** 10 000 потоков агентов со статусом раз в 30 с — **0 записей в Postgres** при неизменном состоянии,
  ~20 % одного ядра, ~61 КБ памяти на ПК (без TLS; с mTLS нужно замерить на стенде). Старый код при 50 000 ПК
  давал ~1 700 UPDATE/с.
- `go vet`, golangci-lint, gosec, `sqlc vet` — чисто.

## Исправлено при сборке

- Пересадка всегда отклонялась на давно подключённые ПК: проверка «в сети» по `last_seen_at` (90 с) не работает,
  когда поток пишет в БД только изменения. Теперь используется `club_computers.status`, который ведёт присутствие (AS-2).
- Роль клиента во фронте называлась `customer` вместо `client`; формат CN сертификата в proto и документации приведён к коду.

## Не сделано

- Экраны React (Этап 3); эндпоинты панели для кодов регистрации ПК и списка ПК.
- Telegram (восстановление пароля, коды перевода) — `UNIMPLEMENTED`; бронирования в gRPC гостя; карта мест для пересадки гостем.
- Партиции остальных журналов (`api_request_logs`, `webhook_deliveries`, `platform_logs`); интеграционный API v1; инструмент переноса данных.

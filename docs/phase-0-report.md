## Главные риски

1. **Деньги в старой БД хранятся в тенге (`decimal(12,2)`), а не в тиынах**: 12 полей. В 0001 они стали `bigint` в тиынах
   под прежними именами, при переносе значение умножается на 100. Суммы внутри JSON (чеки, заказы, уровни в настройках)
   пока в тенге — нужно решение (Q-001, Q-003).
2. **Округление PHP.** `round()` в PHP 8.3 сначала округляет десятичную запись; наивный Go даст расхождение на тиын
   (бонус за пополнение, пороги уровней). Касса считает во `float`.
3. **Ошибки знака** в `amountToCents`/`formatCents` для отрицательных сумм (Q-004).
4. **Журнал действий участвует в расчётах** (лимит продаж тарифа, зоны пересадки, вид прихода в X/Z) — переносить
   как есть или выделить данные (Q-007).
5. **Heartbeat пишет в MySQL почти на каждый пинг** (три источника heartbeat в агенте). При 50 000 ПК это главный
   риск производительности; в новом протоколе состояние в памяти/Valkey.
6. **Бездисковые ПК** сейчас регистрируются после каждой перезагрузки по многоразовому ключу клуба —
   несовместимо с одноразовым кодом из ТЗ (Q-037).
7. **Секреты, зашифрованные `APP_KEY` Laravel** (секреты вебхуков, ключ установки, Telegram), при переносе нужно
   расшифровать старым ключом (Q-050).
8. **Мобильные приложения** работают на старом REST и сломаются при поклубном переходе, если в Go не будет
   совместимого API.
9. **Карта клуба** (~56 КБ JS, drag-and-drop) — самый трудоёмкий экран для переноса.
10. Обновления агента сейчас проверяются только по SHA-256; ключ Ed25519 для подписи ещё не заведён.

## Предлагаемый план Этапа 1 — ядро денег на Go

Условие старта: ответы на топ-10 вопросов из `OPEN_QUESTIONS.md` (в первую очередь Q-001…Q-004, Q-007).

1. **Пакет `money`**: тип тиынов `int64`, разбор/форматирование сумм, эквивалент PHP `round()`,
   `intdiv`, проценты; тесты на граничных значениях (BR §2).
2. **Миграции 0002+**: ledger (двойная запись, ключ идемпотентности), аудит (только добавление), RLS по `app.club_id`,
   партиции журналов по месяцам — по `schema-changes.md`.
3. **sqlc-запросы и сервисы** в порядке зависимостей, каждый — сначала тесты по эталонным сценариям (P1):
   - балансы и ledger (пополнение, списание, возврат, перевод);
   - бонус за пополнение (`TopUpBonus`, `PercentLevels`) и лояльность (`LoyaltyProgram`);
   - правила оплаты (`PaymentRules`): область скидки, лимит бонусов, смешанная оплата, цены по `WeeklyPeriods`;
   - покупка тарифа/пакета (`AgentTariffPurchaseService`) и расчёт сессии (`SessionSettlement`): возврат по секундам,
     пакеты минутами;
   - касса: смены, продажи, возвраты, X/Z-отчёты (`CashRegisterService`, `ShiftReport`).
4. **Тесты**: табличные Go-тесты с ID сценариев `GS-xxx`/`GAP-xxx`, реальный Postgres через testcontainers;
   GAP-сценарии предварительно подтвердить прогоном на копии старого Zafiro (Q-006).
5. **Инструмент сверки**: прогон одних и тех же входных данных через старый PHP-код и новый Go
   (дифференциальные тесты денежных функций).
6. Без UI и без агента: Этап 1 заканчивается, когда все P1-сценарии зелёные.

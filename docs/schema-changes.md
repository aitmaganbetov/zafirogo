# Изменения схемы БД: MySQL (Laravel) → PostgreSQL (zafirogo)

Документ описывает:
1. как старая схема MySQL переложена в `db/migrations/0001_init.sql` (зеркало, без новой логики);
2. что добавляем **отдельными миграциями Этапа 1** и почему: журнал операций (ledger), аудит-журнал,
   RLS, партиционирование, вынос heartbeat из Postgres.

Инвентаризация старой схемы — `docs/parts/30-database.md`. Вопросы владельцу — `docs/open-questions/database.md`.
Проверено на образе **`postgres:18.6`** (последний стабильный major 18; 19 пока RC) — goose up/down/up проходит.

---

## 1. Принцип 0001

- [ ] `0001_init.sql` = зеркало итоговой схемы после 86 миграций Laravel: те же 42 таблицы, те же имена полей,
  индексов и ограничений (имена Laravel — для сверки и переноса данных).
- [ ] В 0001 **нет** ledger, аудита, RLS, партиций, новых таблиц токенов — только отдельные миграции `0002+`.
- [ ] Таблицы Laravel-инфраструктуры не переносятся (`sessions`, `password_reset_tokens`, `cache`, `cache_locks`,
  `jobs`, `job_batches`, `failed_jobs`, `personal_access_tokens`, `migrations`) — замены см. `30-database.md`.

## 2. Маппинг типов MySQL → Postgres

| Laravel / MySQL | Postgres в 0001 | Комментарий |
|---|---|---|
| `id()` bigint unsigned auto_increment | `bigint GENERATED BY DEFAULT AS IDENTITY` | BY DEFAULT — чтобы вставлять старые id; после переноса `setval` (см. п. 3.9) |
| `foreignId` / `unsignedBigInteger` | `bigint` (+ `CHECK >= 0`, где это не FK) | |
| `unsignedInteger` (0…4 294 967 295) | `bigint CHECK (col >= 0)` | `integer` в PG только до 2^31−1 — берём шире, без потерь |
| `unsignedSmallInteger` (0…65 535) | `integer CHECK (col >= 0)` | |
| `unsignedTinyInteger` (0…255) | `smallint CHECK (col >= 0)` | |
| `integer` | `integer` | |
| `decimal(12,2)` / `decimal(14,2)` — **деньги в тенге** | `bigint` — **тиыны** | **смена единицы**, значение × 100 (см. п. 3.1) |
| `decimal(5,2)` (скидка %), `decimal(6,2)` (load avg) | `numeric(5,2)` / `numeric(6,2)` | не деньги |
| `string(n)` | `varchar(n)` | длины сохранены (по умолчанию 255) |
| `char(n)` (хэши) | `varchar(n)` | `char` в PG дополняет пробелами; значения хэшей фиксированной длины, смысл не меняется |
| `text`, `longText`, `mediumText` | `text` | |
| `boolean` (tinyint(1)) | `boolean` | |
| `timestamp`, `dateTime` | `timestamptz` | в MySQL хранится UTC (`config/app.php` timezone = UTC) |
| `date` | `date` | `todo_tasks.due_on` — календарный день клуба |
| `json` | `jsonb` | порядок ключей и дубли ключей не сохраняются (для нас не важно) |
| `uuid` (char(36)) | `uuid` | `agent_qr_logins.id`, `webhook_deliveries.event_id` |
| enum-строки (`varchar` + константы PHP) | `varchar(n)` + `CHECK (col IN (…))` | списки — `30-database.md` |
| `useCurrent()` | `DEFAULT CURRENT_TIMESTAMP` | `api_request_logs`, `api_idempotency_keys` |
| `softDeletes()` | `deleted_at timestamptz NULL` | `products`, `tariffs` |
| неявный индекс MySQL под FK | явный `CREATE INDEX <table>_<col>_foreign` / `<имя составного FK>` | PG не создаёт индексы под FK сам |

## 3. Отличия 0001 от старой схемы (полный список)

- [ ] **3.1 Деньги в тиынах.** 12 полей `decimal` (тенге) стали `bigint` (тиыны), имена не менялись, у каждого есть
  `COMMENT ON COLUMN … 'Тиыны …'`: `products.price`, `tariffs.price`, `club_zones.price_per_hour`, `club_services.price`,
  `shop_orders.amount`, `member_balances.balance`, `member_balances.bonus_balance`, `club_memberships.total_spent`,
  `saas_plans.price_monthly`, `cash_shifts.opening_balance`, `cash_shifts.closing_balance`, `cash_transactions.amount`.
  Перенос: `tiyn = decimal × 100` — точно (2 знака после запятой), считать в SQL MySQL как
  `CAST(ROUND(col * 100) AS SIGNED)` или строкой, как `AgentTariffPurchaseService::amountToCents()` (~стр. 385).
  Уже в тиынах и не меняются: `session_purchases.main_cents`, `session_purchases.bonus_cents`, `transfer_codes.amount_cents`.
  Суммы **внутри JSON** (`receipt_data`, `shop_orders.items`, `activity_logs.details`, `webhook_deliveries.payload`,
  уровни в `clubs.settings`) в 0001 остаются в тенге — решение в open-questions В-2.
  ⚙️ Решение Q-003 (DECISIONS.md): новые записи `receipt_data`, `shop_orders.items` и уровней в `clubs.settings` — формат v2
  (тиыны и базисные пункты, `"v": 2`, §10.11); читатели понимают оба формата; перенос данных переводит всё в v2.
  Требует подтверждения владельца (open-questions В-1).
- [ ] **3.2 unsigned → CHECK (>= 0)** и тип на ступень шире (таблица выше). Поведение «уход склада в минус — ошибка БД»
  (`products.quantity` unsigned в strict-режиме MySQL) сохраняется.
- [ ] **3.3 enum-строки → CHECK.** Добавлены CHECK там, где набор значений закрыт и найден в коде:
  `club_subscriptions.status`, `club_invitations.role`, `stock_movements.type`, `cash_shifts.status`, `cash_transactions.type`,
  `club_zones.icon/theme/status`, `club_computers.status/power_command/agent_state/staff_kind`, `tariffs.payment_method`,
  `session_purchases.kind`, `shop_orders.status`, `webhook_deliveries.status`, `request_metrics.channel`.
  **Без CHECK**: `club_memberships.role` (есть старые роли вроде `'Пользователь'`), `activity_logs.event`, `platform_logs.event`
  (открытые списки). Перед переносом — проверочный `SELECT DISTINCT` (open-questions В-8).
- [ ] **3.4 Явные индексы под FK**, которые MySQL создавал неявно (имена `<table>_<col>_foreign` или имя составного FK).
- [ ] **3.5 `char(n)` → `varchar(n)`** для хэшей и префиксов (`installation_key_hash`, `agent_token_hash`, `key_hash`, …).
- [ ] **3.6 Регистр.** В MySQL `utf8mb4_unicode_ci` — UNIQUE и сравнения регистронезависимы; в 0001 сравнения
  **регистрозависимы** (поведение отличается!). Решение — open-questions В-7 (варианты: unique-индексы по `lower()`,
  недетерминированная ICU-collation, `citext`). До решения ETL должен проверять дубли без учёта регистра.
- [ ] **3.7 Зарезервированное слово:** `translations.group` в SQL пишется как `"group"`.
- [ ] **3.8 Миграции данных Laravel не повторяются в 0001** (бэкфиллы, сид языков). Для чистой установки нужен сид
  `languages` (`ru`, `kk`, `en`, `is_system = true`) — отдельной миграцией/командой Этапа 1.
- [ ] **3.9 Identity после переноса:** для каждой таблицы
  `SELECT setval(pg_get_serial_sequence('<t>', 'id'), COALESCE(max(id), 1)) FROM <t>;` — иначе первая вставка упадёт на дубле.
- [ ] **3.10 Поклубный перенос и глобальные id.** id общие для всех клубов (одна последовательность на таблицу). При переносе
  клуба за клубом в одну Postgres-базу старые id не пересекутся, пока источник один (одна MySQL). Если появятся новые клубы
  в Go-стеке до окончания переноса — нужен сдвиг последовательностей (open-questions В-11).
- [ ] **3.11 Зашифрованные поля** (`clubs.installation_key`, `webhook_endpoints.secret`, `platform_settings.value.token`)
  зашифрованы Laravel `Crypt` (AES-256-CBC + HMAC, APP_KEY) — переносить с перешифровкой (open-questions В-5).
- [ ] **3.12 Модели sqlc содержат все колонки** (включая `password`, `installation_key`, `agent_token_hash`) с JSON-тегами —
  наружу (HTTP/WS) отдавать только DTO, не структуры `store.*` (аналог `$hidden` в Eloquent).

## 4. Журнал операций (ledger) — миграция `0002_ledger.sql` (Этап 1)

**Зачем.** Сейчас баланс меняется обновлением поля: `MemberBalance::update(['balance' => …])` (`app/Services/AgentShop.php`
~стр. 70), `decrement('balance', …)` (`app/Services/CashRegisterService.php` ~стр. 181–184), а история денег разбросана по
`cash_transactions`, `session_purchases`, `shop_orders`, `activity_logs.details`. Правило нового проекта: **все движения денег —
через журнал с ключом идемпотентности, баланс не меняется «просто обновлением поля»**.

**Модель — двойная запись по счетам:**

- `ledger_accounts` — счета: `member_main` / `member_bonus` (на пару `club_id, user_id`), `cash_drawer` (касса клуба, смена),
  `revenue_time`, `revenue_shop`, `revenue_services`, `bonus_issued` (эмиссия бонусов), `external` (деньги снаружи: наличные/карта/QR).
- `ledger_transactions` — одна бизнес-операция: `club_id`, `kind` (`top_up`, `top_up_bonus`, `refund`, `tariff_purchase`,
  `minutes_purchase`, `session_settlement_refund`, `shop_order`, `shop_order_cancel`, `pos_sale`, `service_sale`, `friend_transfer`,
  `write_off`, `cash_income`, `cash_expense`, `migration_opening_balance`), **`idempotency_key`** (`UNIQUE (club_id, idempotency_key)`),
  `actor_user_id`, ссылки на источник (`cash_transaction_id`, `session_id`, `shop_order_id`, `transfer_code_id` …), `created_at`.
- `ledger_entries` — проводки: `transaction_id`, `account_id`, `amount bigint` (тиыны, знак: + приход на счёт / − расход),
  `created_at`. Инвариант: `SUM(amount) = 0` по каждой транзакции (проверка — deferred constraint trigger).

**Связь с текущими таблицами:**

- [ ] `member_balances.balance/bonus_balance` остаются как **проекция** (быстрое чтение и `SELECT … FOR UPDATE` для очереди
  списаний); меняются только в той же транзакции, что и вставка в ledger, функцией/сервисом `billing`. Сверка:
  `balance = SUM(entries по member_main)` — ночная проверка воркером. Прямой `UPDATE` баланса запрещён правами роли
  (UPDATE разрешён только функции `SECURITY DEFINER` или проверяется триггером, что в транзакции есть проводка).
- [ ] `cash_transactions` остаётся документом кассы (чек, смена, возврат `refund_of_id`), каждая строка ссылается на свою
  `ledger_transaction` (новая колонка `ledger_transaction_id`).
- [ ] `session_purchases.main_cents/bonus_cents` — состав сессии для возврата (`SessionSettlement`); покупка и возврат — ledger-операции
  с ключом `session:<session_id>:<purchase_id>`.
  Учесть: старый код удаляет `session_purchases` старше 8 дней (`routes/console.php`, `session-purchases:prune`) — источником
  истории станет ledger, а `session_purchases` может и дальше чиститься.
- [ ] `shop_orders`, `transfer_codes` — документы; деньги — через ledger (ключ `shop_order:<id>`, `transfer:<code_id>`).
- [ ] `club_memberships.total_spent` (лояльность) — проекция по операциям трат (`LoyaltyProgram`), пересчитываемая из ledger.
- [ ] Перенос: на дату переключения клуба создаются операции `migration_opening_balance` на ненулевые балансы (основной и
  бонусный; реализовано пачками по 500 клиентов — §10.3) — история до переноса остаётся в старых таблицах/`activity_logs`.

Набросок DDL:

```sql
CREATE TABLE ledger_transactions (
    id              bigint GENERATED ALWAYS AS IDENTITY,
    club_id         bigint NOT NULL REFERENCES clubs (id),
    kind            text   NOT NULL CHECK (kind IN ('top_up', 'refund', 'tariff_purchase', /* … */ 'migration_opening_balance')),
    idempotency_key text   NOT NULL,
    actor_user_id   bigint REFERENCES users (id),
    meta            jsonb,
    created_at      timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (id, created_at),
    UNIQUE (club_id, idempotency_key, created_at)      -- см. п. 7: в партиционированной таблице ключ включает created_at
) PARTITION BY RANGE (created_at);
-- Глобальная идемпотентность без created_at — отдельная непартиционированная таблица:
CREATE TABLE ledger_idempotency (
    club_id         bigint NOT NULL,
    idempotency_key text   NOT NULL,
    transaction_id  bigint NOT NULL,
    created_at      timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (club_id, idempotency_key)
);
CREATE TABLE ledger_entries (
    id             bigint GENERATED ALWAYS AS IDENTITY,
    club_id        bigint NOT NULL,
    transaction_id bigint NOT NULL,
    account_id     bigint NOT NULL REFERENCES ledger_accounts (id),
    amount         bigint NOT NULL CHECK (amount <> 0),   -- тиыны
    created_at     timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);
CREATE INDEX ON ledger_entries (club_id, account_id, created_at);
```

Вставка: `INSERT INTO ledger_idempotency … ON CONFLICT DO NOTHING RETURNING …` — если строка не вставилась,
операция уже была, возвращаем прежний результат (повтор запроса агента/кассы безопасен).

## 5. Аудит-журнал (только добавление) — миграция `0003_audit.sql`

**Зачем.** ТЗ: аудит всех действий с деньгами, тарифами и правами, только добавление. `activity_logs` для этого не годится:
это журнал для интерфейса (его можно удалить вместе с клубом каскадом, строку можно изменить).

- [ ] Таблица `audit_log`: `id`, `club_id` (NULL для платформы), `actor_user_id`, `actor_kind` (`staff`, `guest`, `agent`, `api_key`,
  `system`), `action` (`money.*`, `tariff.*`, `permission.*`, `role.*`, `api_key.*`, `settings.finances.*`), `subject_type`,
  `subject_id`, `before jsonb`, `after jsonb`, `ip inet`, `request_id`, `created_at`. Без секретов и персональных данных сверх нужного.
- [ ] Защита: `REVOKE UPDATE, DELETE, TRUNCATE ON audit_log FROM zafiro_app;` + триггер `BEFORE UPDATE OR DELETE` → `RAISE EXCEPTION`.
  Без FK `ON DELETE CASCADE` к `clubs` (удаление клуба не стирает аудит).
- [ ] Опционально — хэш-цепочка `prev_hash`/`hash` (sha256 предыдущей записи клуба) для обнаружения подмены (open-questions В-15).
- [ ] Партиционирование по месяцам; удаление старых партиций — только ролью владельца схемы по регламенту хранения.

```sql
CREATE FUNCTION audit_log_forbid_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'audit_log is append-only';
END $$;
CREATE TRIGGER audit_log_append_only BEFORE UPDATE OR DELETE ON audit_log
    FOR EACH ROW EXECUTE FUNCTION audit_log_forbid_change();
REVOKE UPDATE, DELETE, TRUNCATE ON audit_log FROM zafiro_app;
```

## 6. Row-Level Security — миграция `0004_rls.sql`

**Зачем.** Второй рубеж тенантности после фильтра `club_id` в каждом sqlc-запросе (правило `sqlc vet` `tenant-filter`
в `sqlc.yaml`). Аналог global scope `BelongsToClub` (`app/Models/Concerns/BelongsToClub.php`): без клуба — пусто (`1 = 0`).

- [ ] Роли: `zafiro_owner` (владелец схемы, миграции), `zafiro_app` (сервер, **без** `BYPASSRLS`, не владелец таблиц),
  `zafiro_platform` (суперадминка и фоновые задачи по всем клубам, `BYPASSRLS` или отдельная политика).
- [ ] Для каждой тенантной таблицы (24 модели с `BelongsToClub` + `club_zone_tariff`, `club_subscriptions`, `club_request_metrics`,
  `club_load_snapshots`, `news` с особой политикой, новые ledger/audit):

```sql
ALTER TABLE club_computers ENABLE ROW LEVEL SECURITY;
ALTER TABLE club_computers FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON club_computers
    USING      (club_id = current_setting('app.club_id', true)::bigint)
    WITH CHECK (club_id = current_setting('app.club_id', true)::bigint);
```

  `current_setting(…, true)` без значения даёт NULL → условие ложно → строк нет (как `1 = 0` в Laravel).
- [ ] `news`: `USING (club_id IS NULL OR club_id = current_setting('app.club_id', true)::bigint)` для чтения, запись — только своего клуба.
- [x] Таблицы без `club_id` (`transfer_codes`, `api_idempotency_keys`): добавить `club_id` (рекомендуется, open-questions В-10)
  или политика через `EXISTS` по родителю. Сделано миграцией `0012` (решение Q-028, L-1): `club_id NOT NULL` с бэкфиллом
  из родителя, составной FK `(club_id, родитель) → родитель (club_id, id)`, обычная политика `club_id = app.club_id`.
- [x] `0012` (решение Q-031): `tariffs_club_id_name_unique` — частичный уникальный индекс `(club_id, lower(name)) WHERE deleted_at IS NULL`
  (имя удалённого тарифа снова свободно; регистр не важен, как в MySQL, Q-025); `time_packages (expires_at)` — суточное
  сгорание пакетов (Q-011).
- [ ] **Как ставить через pgx** — только внутри транзакции и только `is_local = true` (значение живёт до конца транзакции,
  соединение возвращается в пул чистым):

```go
// internal/store/tx.go (Этап 1)
func (s *Store) InClub(ctx context.Context, clubID int64, fn func(q *Queries) error) error {
    return pgx.BeginFunc(ctx, s.pool, func(tx pgx.Tx) error {
        // set_config(..., true) == SET LOCAL; параметр, а не конкатенация строки.
        if _, err := tx.Exec(ctx, "SELECT set_config('app.club_id', $1, true)", strconv.FormatInt(clubID, 10)); err != nil {
            return err
        }
        return fn(New(tx))
    })
}
```

  `SET` без `LOCAL` / `set_config(…, false)` **запрещены** (значение «утечёт» в следующее использование соединения из пула).
- [ ] Тест (testcontainers): под ролью `zafiro_app` запрос без `app.club_id` возвращает 0 строк; с чужим `club_id` — 0 строк;
  `INSERT` с чужим `club_id` падает на `WITH CHECK`.
- [ ] Составные FK проверяются движком в обход RLS — целостность между клубами по-прежнему держат FK `(club_id, id)`.

## 7. Партиционирование журналов и истории по месяцам — миграция `0005_partitions.sql`

**Зачем.** ТЗ: таблицы журналов и истории — по месяцам; при 50 000 ПК журналы растут быстро, удаление старого = `DROP`/`DETACH`
партиции вместо `DELETE` (сейчас очистка — команда планировщика `routes/console.php`).

| Таблица | Ключ | Почему |
|---|---|---|
| `activity_logs` | `created_at` | самый большой журнал клуба; FK на неё никто не ссылается |
| `platform_logs` | `created_at` | журнал суперадмина |
| `api_request_logs` | `created_at` | лог каждого запроса API v1 |
| `webhook_deliveries` | `created_at` | outbox доставок; `UNIQUE(event_id)` → `UNIQUE(event_id, created_at)` |
| `club_request_metrics`, `request_metrics`, `server_metrics` | по `minute` (range) | поминутные метрики |
| `club_load_snapshots` | `captured_at` | снимок раз в 5 минут на клуб |
| `chat_messages` | `created_at` | растёт; при необходимости |
| `ledger_entries`, `ledger_transactions`, `audit_log` (новые) | `created_at` | история денег и аудит |

- [ ] Ограничение Postgres: PK/UNIQUE партиционированной таблицы должны включать ключ партиционирования → PK `(id, created_at)`.
  Поэтому таблицы, на которые ссылаются FK (`cash_transactions.refund_of_id`), **не** партиционируем; `session_purchases`,
  `cash_transactions` — пока нет.
- [ ] Перевод существующей таблицы: создать новую `… PARTITION BY RANGE`, перелить данные при переносе (ETL пишет сразу в
  партиционированную), переименовать. В 0001 таблицы обычные.
- [ ] Создание партиций заранее (текущий + 2 месяца) и удаление по сроку хранения — Go-воркер (или `pg_partman`, open-questions В-16).

## 8. Статус ПК / heartbeat — вне Postgres

Сейчас каждый heartbeat пишет `club_computers.last_seen_at`, `status = 'online'`, `remote_ip` (+ `agent_state`)
(`app/Services/ClubComputerSessions.php` ~стр. 95), а онлайн вычисляется как `last_seen_at > now() − 90 с`
(`ClubComputer::HEARTBEAT_TIMEOUT_SECONDS`, `currentStatus()`). При 50 000 ПК и пинге раз в N секунд это тысячи UPDATE/с
по одной горячей таблице.

- [ ] Онлайн-статус и «последний пинг» — в памяти инстанса, держащего gRPC-стрим агента, + Valkey
  (`HSET pc:<club_id>:<id> last_seen … agent_state … remote_ip …`, TTL 90 с; присутствие = наличие ключа/стрима).
- [ ] В Postgres — только **изменения состояния**: online ↔ offline (с дебаунсом), смена `agent_state`, начало/конец сессии,
  смена версии агента/железа. `last_seen_at` пишется при переходе в offline (и периодически, например раз в 5 мин, для отчётов).
- [ ] Админка получает статусы push'ем (WebSocket) из NATS, а не опросом таблицы.
- [ ] `club_load_snapshots` строится воркером из Valkey/памяти.
- [ ] Команды питания (`power_command`, `wake_requested_at`) и сообщения (`staff_message`) — команды в стрим агента;
  поля в БД остаются как журнал «последняя команда» на переходный период (open-questions В-14).

## 10. Как реализовано (Этап 1): ledger, аудит, RLS, партиции

`server/internal/billing/balance*.go` (операции верхнего уровня). Запросы: `db/queries/ledger.sql`, `balances.sql`,

Отличия от плана выше (§4–§7): партиционирование существующих журналов (`activity_logs`, `api_request_logs` и др., §7) **не**
сделано — только новые таблицы ledger и аудита; номер `0005` занят способом оплаты (Q-013), партиции старых журналов — отдельной
миграцией. Таблицы `ledger_transactions.cash_transaction_id`/`session_id`/… — ссылки без FK (документы чистятся).

### 10.1. Счета и знак суммы

`ledger_entries.amount` — тиыны со знаком: **> 0 кредит, < 0 дебет**; сумма проводок операции = 0. Для счетов клиента, выручки и
фондов остаток = `SUM(amount)`; для кассы (актив) остаток = `−SUM(amount)`.

| Счёт (`ledger_accounts.kind`) | Владелец | Смысл | Проекция |
|---|---|---|---|
| `member_main` | клиент (`user_id`) | основной баланс | `member_balances.balance` |
| `member_bonus` | клиент | бонусный баланс | `member_balances.bonus_balance` |
| `cash_drawer` | клуб | касса (наличные/карта/QR — один остаток, BR-051) | — |
| `revenue_time` / `revenue_shop` / `revenue_pos` | клуб | выручка: время / магазин агента / POS | — |
| `bonus_fund` | клуб | бонусный фонд: выпуск бонусов (дебет), их расход и возврат (кредит) | — |
| `cash_other` | клуб | прочие приходы/расходы кассы (BR-054) | — |
| `owner_adjustment` | клуб | корректировки владельцем (BR-058), начальный баланс (BR-059) | — |
| `opening_balance` | клуб | входящие остатки переноса из MySQL | — |

Счета создаются лениво (`UpsertLedgerAccounts`), уникальность — `UNIQUE NULLS NOT DISTINCT (club_id, kind, user_id)`.

Поиск счетов операции (`UpsertLedgerAccounts`, S5-M3-О3) — по индексу этой уникальности двумя ветками: счета клиента
`user_id = …`, счета клуба `user_id IS NULL`. Прежнее одно условие `a.user_id IS NOT DISTINCT FROM wanted.user_id` индекс не
использует: Hash Join с Seq Scan по всем счетам клуба на каждой денежной операции. EXPLAIN (ANALYZE) на синтетике
(postgres:18.6, клуб с 50 000 клиентов = 100 006 счетов, операция пополнения: `member_main`, `member_bonus`, `cash_drawer`,
`bonus_fund`, все счета уже есть):

| | План | Buffers | Execution Time (5 прогонов) |
|---|---|---|---|
| до | Hash Join ← Seq Scan `ledger_accounts` (100 006 строк, Rows Removed by Join Filter: 99 998) | 972 | 18,9–21,7 мс (первый — 34 мс) |
| после | 2 × Nested Loop ← Index Scan `ledger_accounts_club_kind_user_unique` (`user_id = …` / `user_id IS NULL`) | 36 | 0,15–0,20 мс |

Время больше не растёт с числом счетов клуба. Новых индексов не нужно (миграции нет): `UNIQUE NULLS NOT DISTINCT` — обычный
btree, `IS NULL` в нём ищется как условие индекса.

Типовые проводки (реализованы в `billing/balance*.go`; остальные — по тому же образцу у владельцев пакетов):

| Операция (`kind`) | Проводки |
|---|---|
| `top_up` (BR-053) | счёт клиента +X, `cash_drawer` −X; бонус (BR-041, хук `TopUpBonusFunc`): `member_bonus` +B, `bonus_fund` −B |
| `top_up_refund` (BR-055) | счёт клиента −X, `cash_drawer` +X; бонус назад `min(B, бонусы)`: `member_bonus` −b, `bonus_fund` +b |
| `owner_top_up` / `owner_write_off` (BR-058) | счёт клиента ±X, `owner_adjustment` ∓X |
| `initial_balance` (BR-059) | `member_main` +M, `member_bonus` +B, `owner_adjustment` −(M+B) |
| `friend_transfer` (BR-091/092) | `member_main` отправителя −X, `member_main` друга +X |
| покупки `tariff_purchase`, `minutes_purchase`, `shop_order` (`billing.Charge`) | `member_main` −m → выручка +m; `member_bonus` −b → `bonus_fund` +b |
| возвраты `session_refund`, `shop_order_cancel` (`billing.Credit`) | обратные проводки покупки |
| `migration_opening_balance` | `member_main`/`member_bonus` ±, `opening_balance` ∓ (может быть < 0, Q-004) |
| `pos_sale`, `cash_income`, `cash_expense`, `guest_session` (пакет cash) | `cash_drawer` −/+, `revenue_pos` / `cash_other` / `revenue_time` +/− |
| `pos_refund` | обратные `pos_sale`; `reverses_transaction_id` — исходная `pos_sale` (CSQ-6, 0014) |
| `cash_shift_opening` (CSQ-1, 0014) | выравнивание при открытии смены: `cash_drawer` ∓d, `opening_balance` ±d (d — начальный остаток смены минус остаток кассы по журналу) |

### 10.2. Ledger минут — отдельная таблица в той же операции

`ledger_minute_entries` (`user_id`, `time_package_id`, `tariff_id`, `minutes` со знаком) пишется в рамках той же
`ledger_transactions` (тот же ключ идемпотентности и та же транзакция, что и деньги — например, `session_refund` с возвратом денег и
сохранённым пакетом). Почему не вид счёта: минуты — другая единица (сумма по клубу смешала бы тиыны и минуты), у них нет второй
стороны, и инвариант «сумма = 0» к ним неприменим. Проекция — `time_packages.minutes_left` (меняет пакет сессий).

### 10.3. Идемпотентность

- `ledger_idempotency (club_id, idempotency_key)` — PK, **не** партиционирована (глобальная уникальность ключа в клубе невозможна в
  партиционированной таблице без `created_at`). Хранит `fingerprint` = sha256 канонического JSON `{kind, request}`.
- `ledger.Begin` захватывает ключ **до** блокировок и проверок (`INSERT … ON CONFLICT DO NOTHING`; параллельный запрос с тем же ключом
  ждёт COMMIT первого): повтор с тем же телом → прежний результат (`Replayed`), с другим → `ErrIdempotencyConflict`. Поэтому повтор
  перевода «на весь баланс» получает прежний ответ, а не «Недостаточно средств».
- id операции выдаётся из `ledger_transaction_id_seq` при захвате ключа — без UPDATE (таблицы только дополняются).
- Естественные ключи: `top_up_refund:<id прихода>`, `transfer_code:<id кода>`, `initial_balance:<user_id>`,
  при переносе клуба — `opening_balances:<первый user_id>-<последний>` (пачка до 500 клиентов, `migrate.postOpeningBalances`)
  и `opening_cash_drawer` (остаток кассы); для запросов кассы/агента — ключ запроса клиента.

### 10.4. Проекция `member_balances` и запрет «просто обновить поле»

- Баланс меняет **только** BEFORE INSERT-триггер `ledger_apply_member_entry()` на `ledger_entries` (SECURITY DEFINER): сдвигает
  `balance`/`bonus_balance` и пишет `balance_after` в проводку.
- Дебет, после которого баланс < 0, — ошибка (`ledger_member_balance_non_negative`), кроме `migration_opening_balance`
  (старые данные могут быть < 0, Q-004). Старый код всегда проверял достаточность перед списанием, поэтому поведение то же; в Go та
  же проверка под `FOR UPDATE` возвращает `*ledger.InsufficientFundsError`, а операции верхнего уровня — тексты старого кода.
- Предел `999 999 999 999` тиынов (`decimal(12,2)` старой схемы, BR-001/053) — `ErrBalanceOverflow`.
- Защита: роль `zafiro_app`/`zafiro_platform` имеет `INSERT (club_id, user_id, created_at, updated_at)` и
  `UPDATE (created_at, updated_at)` на `member_balances` — колонки баланса недоступны; триггер-сторож `member_balances_guard`
  (`pg_trigger_depth() = 1` → исключение) останавливает и владельца схемы; новая строка — только с нулями.
- Сверка: `ListMemberBalanceDrift` (агрегат в SQL) — для ночной фоновой задачи.
- **Перенос данных (ETL):** строки `member_balances` вставляются с нулями, остатки — операциями `migration_opening_balance` по 500 клиентов
  (`migrate.postOpeningBalances`, ключ `opening_balances:<первый>-<последний>`).

### 10.5. Только добавление

`ledger_*` и `audit_log`: триггеры `BEFORE UPDATE OR DELETE` (строка) и `BEFORE TRUNCATE` (оператор) →
`zafiro_forbid_change()`; плюс `REVOKE UPDATE, DELETE, TRUNCATE` у ролей приложения. Нет FK с `ON DELETE CASCADE` к клубам/пользователям
(клубы и членства в старом коде не удаляются; у `audit_log` FK нет вовсе).

### 10.6. Партиции

`ledger_transactions`, `ledger_entries`, `ledger_minute_entries`, `audit_log` — `PARTITION BY RANGE (created_at)`, месяцы по **UTC**,
имена `<таблица>_YYYY_MM`. PK включает `created_at`: `(club_id, id, created_at)` у ledger, `(id, created_at)` у аудита; проводки
ссылаются на операцию составным FK `(club_id, transaction_id, created_at)`. Функция `zafiro_create_monthly_partitions(parent, from,
months)` (SECURITY DEFINER, белый список таблиц, EXECUTE — только `zafiro_platform`) создаёт недостающие партиции и отзывает права на
них (читать можно только через родителя, где действуют политики). Миграция создаёт текущий месяц + 3; дальше —
`db.EnsurePartitions` из фоновой задачи раз в сутки (Q-081). DEFAULT-партиции нет: если задача стоит больше 3 месяцев, запись денег
упадёт явно, а не уйдёт молча в «свалку».

Индексы с `club_id` первым: `ledger_transactions (club_id, created_at)`, `(club_id, kind, created_at)`, частичные по
`cash_shift_id`/`session_id`; `ledger_entries (club_id, account_id, created_at, id)` (история счёта, keyset), `(club_id, transaction_id,
created_at)`; `audit_log (club_id, created_at)`, `(club_id, category, created_at)`, `(club_id, subject_type, subject_id, created_at)`.

### 10.7. Аудит (`audit_log`)

Категории: `money` (пишут операции `billing`: `money.top_up`, `money.owner_write_off`, `money.friend_transfer`, …, со ссылкой на
`ledger_transaction_id`), `tariff`, `permission`, `settings`, `security`. `actor_kind`: staff, guest, agent, api_key, superadmin,
system. `club_id NULL` — событие платформы (пишет только `zafiro_platform`). Колонка `hash` заложена под хэш-цепочку (Q-053).
`activity_logs` остаётся журналом интерфейса.

### 10.8. RLS и роли

- `zafiro_app` (сервер, без BYPASSRLS, не владелец) и `zafiro_platform` (суперадминка и фоновые задачи; политика
  `platform_access USING (true)` — BYPASSRLS не нужен, работает на управляемом Postgres). Роли — NOLOGIN; логины создаются при
  развёртывании (`CREATE ROLE … LOGIN IN ROLE zafiro_app`). Миграции запускает владелец схемы (нужен CREATEROLE для первой установки).
- Политика `tenant_isolation` (для всех, включая владельца — FORCE): `club_id = zafiro_current_club_id()`, где функция =
  `NULLIF(current_setting('app.club_id', true), '')::bigint` (пустая строка остаётся в соединении после транзакции с `SET LOCAL` —
  без `NULLIF` запрос упал бы на приведении типа). Без клуба — NULL → строк нет.
- Охват: все 28 таблиц 0001 с `club_id NOT NULL` + 6 новых; особые политики: `news` (читаются и платформенные `club_id IS NULL`),
  `api_request_logs` (запись без клуба допускается), `transfer_codes` и `api_idempotency_keys` (до `0012` — через родителя;
  с `0012` — свой `club_id` и обычная политика, Q-028), `club_memberships` + `member_self_read` (свои членства во
  всех клубах при `app.user_id` — выбор клуба при входе).
- Без RLS (не данные клуба): `users`, `clubs`, `saas_plans`, `password_recovery_codes`, `platform_settings`, `languages`,
  `translations`, `server_metrics`, `request_metrics`, `platform_logs`.
- С `0028_least_privilege` (Этап 6, `docs/security-review.md` SEC-005, `open-questions/stage6-security.md` SQ-4) права
  `zafiro_app` на них урезаны: `users` — `INSERT`/`UPDATE` только профиля и пароля (`is_superadmin`, `blocked_at` — только
  `zafiro_platform`), без `DELETE`; `clubs` — RLS без FORCE: читают все, `UPDATE` пулом клуба — только `id = app.club_id`,
  `INSERT`/`DELETE` — платформа; `platform_settings`, `saas_plans` — только чтение; `platform_logs` — без `UPDATE`/`DELETE`;
  `goose_db_version` — без прав.
- `zafiro_tables_without_rls()` — проверка в тестах: таблицы с `club_id` без включённого и принудительного RLS (новые миграции
  обязаны включать RLS сами; права на новые таблицы роли получают через `ALTER DEFAULT PRIVILEGES`).
- Go: `db.InTenantTx(ctx, pool, clubID, fn)` — `BEGIN; SELECT set_config('app.club_id', $1, true), set_config('app.user_id', …),
  set_config('lock_timeout', '5000ms', true)`; повтор всей транзакции при `40001`/`40P01` (до 3 раз). `db.InPlatformTx` — для пула
  логина `zafiro_platform`. Конкурентные списания сериализуются `SELECT … FOR UPDATE` по `member_balances` в порядке `user_id`
  (`ledger.LockBalances`, как `lockForUpdate()` в `Friends::transfer()` и др., BR-005).
- Аутентификация до выбора клуба (вход по телефону, API-ключ, сертификат ПК) не видит тенантных строк под `zafiro_app` — нужны
  `app.user_id` (членства) или узкие запросы через `zafiro_platform` (см. `open-questions/stage1-ledger.md`).

### 10.11. Решения Этапа 1 в схеме (0014) и форматы JSON v2

Миграция `0014_stage1_decisions.sql` (решения из `docs/DECISIONS.md` и `docs/open-questions/stage1-*.md`):

- **CSQ-1** — вид `cash_shift_opening` в `ledger_transactions_kind_check` (раньше выравнивание кассы при открытии смены шло
  видами `cash_income`/`cash_expense` с `meta.reason = "shift_opening"`). Откат миграции невозможен, пока есть такие операции.
- **CSQ-6** — индекс `ledger_transactions (club_id, cash_transaction_id) WHERE cash_transaction_id IS NOT NULL`; `pos_refund`
  и `top_up_refund` заполняют `reverses_transaction_id` id исходной `pos_sale` / `top_up`.
- **CSQ-7** — `cash_shifts.drawer_snapshot_entry_id/balance/at`: при закрытии смены — последняя учтённая проводка `cash_drawer`,
  остаток после неё и `now()` транзакции. Остаток кассы при открытии = снимок последней закрытой смены + проводки с id больше
  снимка (`created_at` не раньше снимка минус сутки — только для отсечения партиций). Нет снимка (перенесённые смены) —
  полная сумма. Корректно, потому что все проводки `cash_drawer` пишутся под блокировкой открытой смены.
- **CSQ-9, PD-6** — `cash_transactions.description` → `text` (описание гостевой сессии со всеми ПК); форма прихода/расхода — по-прежнему ≤ 255.
- **PQ-4** — `CHECK (price BETWEEN 0 AND 999999999999)` у `tariffs.price` и `club_zones.price_per_hour` (`pricing.MaxPrice`).

Форматы JSON v2 (решение Q-003; поля сумм названы иначе, чем в v1, чтобы старый читатель не принял тиыны за тенге):

| Где | v2 (пишет новый код) | v1 (старый код, читается) |
|---|---|---|
| `cash_transactions.receipt_data` продажа | `{"v":2,"items":[{"product_id"\|"service_id","name","quantity","price_tiyn","total_tiyn"}]}` | `{"items":[{…,"price","total"}]}` — тенге (PHP float) |
| `cash_transactions.receipt_data` пополнение | `{"v":2,"top_up":{"user_id","balance_type","bonus_tiyn"}}` | `{"top_up":{…,"bonus"}}` — тенге |
| `shop_orders.items` | `{"v":2,"items":[{"product_id","name","quantity","price_tiyn","total_tiyn"}]}` | `[{…,"price","total"}]` — тенге строкой `formatCents` |
| `clubs.settings.finances.topup_bonus_levels`, `loyalty_levels` | `{"v":2,"levels":[{"threshold_tiyn","percent_bp"}]}` | `[{"amount"\|"spent","percent"}]` — тенге и проценты |

Код: `cash/service/receipt.go` (`encodeReceipt`/`decodeReceipt`), `shop.EncodeItems`/`shop.DecodeItems`,
`bonus.EncodeLevels`/`bonus.ParseSettings`. Запись уровней v2 подключится к экрану настроек (Этап 3).

## 11. Шифрование секретов в базе (0025, Этап 4)

Решение Q-050. В Laravel `webhook_endpoints.secret` — каст `'encrypted'` (`app/Models/WebhookEndpoint.php`), токены
Telegram в `platform_settings` — `Crypt::encryptString` (`app/Services/TelegramGateway.php`,
`Monitoring/TelegramAlerts.php`), ключ — `APP_KEY`. Здесь шифрует сервер, ключа в SQL нет.

- **Шифр** — `server/internal/secretbox`: AES-256-GCM, ключ AES — HKDF-SHA256 от секрета конфигурации. Формат
  `v2:<kid>:base64(nonce ‖ шифротекст)`. Связка ключей — `security.data_keys` (`ZAFIRO_SECURITY_DATA_KEYS=kid:секрет,…`,
  секрет ≥ 32 байт, в prod обязательна): первый шифрует, остальные только расшифровывают.
- **Контекст (associated data)**: секрет вебхука шифруется с `webhook_endpoints.secret:club=<club_id>`
  (`webhook.SecretContext`) — шифротекст, скопированный в endpoint другого клуба, не расшифруется. Токены Telegram —
  без контекста.
- **Формат `v1:`** (Этап 3, кабинет суперадмина: ключ SHA-256 от `superadmin.secret_key`) только расшифровывается,
  если `superadmin.secret_key` задан; воркер перешифровывает такие значения в `v2`, после чего ключ можно убрать.
- **Где шифруется / расшифровывается**: выдача и ротация секрета вебхука (`sections/integrations`, секрет
  показывается один раз в ответе, в базе — только шифротекст), отправка вебхука (`webhook.Deliverer` расшифровывает
  перед подписью HMAC; не расшифровался — попытка «secret unavailable», запрос не уходит), токены Telegram
  (`sections/superadmin`, `internal/telegram`).
- **Миграция 0025**: `CHECK (secret ~ '^v[0-9]+:') NOT VALID` на `webhook_endpoints` — новые и изменённые строки
  только шифротекстом; если открытых секретов нет (новая база), ограничение сразу проверяется целиком (`VALIDATE`).
  Иначе `VALIDATE CONSTRAINT webhook_endpoints_secret_sealed` — отдельной миграцией после того, как воркер отработает
  на всех окружениях.
- **Воркер `reencrypt-secrets`** (`server/internal/worker/reencrypt_secrets.go`, один исполнитель — advisory lock,
  при старте и раз в час): открытые секреты вебхуков (строки до 0025), `v1` и `v2` со старым `kid` → текущий ключ;
  токены `platform_settings.value.token` в `v1`/`v2` со старым `kid` → текущий ключ. Запись условная (значение не
  изменилось), поэтому повтор и параллельная ротация секрета пользователем безопасны. Нерасшифровываемое значение
  остаётся как есть (ошибка в журнале, без значения).
- **Ротация ключа**: 1) добавить новый ключ **первым** в `security.data_keys` (старый — следом) и перезапустить
  инстансы; 2) воркер перешифрует строки (журнал `secrets re-encrypted`, проверка — нет строк с префиксом старого
  `kid`: `SELECT count(*) FROM webhook_endpoints WHERE secret LIKE 'v2:<старый kid>:%'`); 3) убрать старый ключ.
- **Перенос из MySQL** (Q-050): инструмент расшифровывает значения Laravel старым `APP_KEY` (передаётся ему как
  секрет) и записывает зашифрованными `secretbox` (тот же `security.data_keys`, контекст клуба): открытый текст в
  `webhook_endpoints.secret` CHECK не пропустит.

## 12. Срок хранения журналов — удаление месячных партиций (0026, Этап 4)

Решения Q-081 («отсоединение по сроку»), H1-Q1 (`docs/open-questions/stage4-h1.md`).

- **Функция** `zafiro_drop_monthly_partitions(parent, before timestamptz)` (`SECURITY DEFINER`, EXECUTE — только
  `zafiro_platform`): `DETACH PARTITION` + `DROP TABLE` для партиций `<parent>_YYYY_MM`, весь месяц которых
  (UTC) раньше `before`; возвращает число удалённых. Белый список — только журналы, которые старый код чистил по
  сроку: `api_request_logs` (90 дней, `PruneIntegrationData`). `ledger_*` и `audit_log` не удаляются никогда,
  `activity_logs` старый код хранил вечно — для них функция бросает исключение.
- **Задача** `logs:retention` (`server/internal/worker/log_retention.go`, `db.DropPartitionsBefore`): раз в
  `workers.log_retention.interval` (1h, как `integrations:prune`) под `leader.RunOnce`; срок —
  `integrations.request_log_retention` (`2160h`). `lock_timeout` 5 с: DETACH блокирует родителя, вставки журнала не
  должны ждать в очереди.
- **Отличие от старого**: удаление целыми месяцами — строка живёт не меньше срока, до месяца дольше.
- **Тестовые базы** (`dbtest`) создают партиции и на 24 месяца назад (тесты с замороженными датами); в проде
  партиции под старые даты создаёт только инструмент переноса (`tools/migrate-from-mysql/README.md`).

## 13. Второй фактор суперадмина (0029, Этап 7)

Новая функция по поручению владельца (SEC-010; решения — `docs/open-questions/stage7-totp.md`). В старом Laravel
таблиц нет — при переносе из MySQL они пустые: каждый суперадмин настраивает TOTP при первом входе.

- **`superadmin_totp`** (`user_id` PK → `users` ON DELETE CASCADE): `secret` — только шифротекст `secretbox`
  (CHECK `^v[0-9]+:`, контекст `superadmin_totp.secret:user=<id>`, связка `security.data_keys`, перешифровка —
  воркер `reencrypt-secrets`, §11); `confirmed_at` — NULL, пока не введён первый код; `last_step` — последний
  принятый шаг TOTP (повтор кода отклоняется, `UPDATE … WHERE last_step < шаг`).
- **`superadmin_recovery_codes`**: `code_hash` — sha256 кода (80 бит случайности) с привязкой к пользователю,
  `used_at` — когда использован (одноразово, `UPDATE … WHERE used_at IS NULL`); UNIQUE (`user_id`, `code_hash`).
- **Права**: только `zafiro_platform` (`SELECT, INSERT, UPDATE, DELETE`); у `zafiro_app` — ничего (как SEC-005:
  ошибка в запросе пула клуба не выдаёт и не сбрасывает второй фактор суперадмина). Проверка —
  `TestAppRoleLeastPrivilege`.
- **Сессии** (Valkey, не Postgres): поле `mfa` в `auth:s:{sid}`; сессия суперадмина без него не действует.

## 14. История проблем здоровья ПК (0030, Этап 7)

Новая функция по поручению владельца (решения — `docs/open-questions/stage7-health.md`). В старом Laravel таблицы нет —
при переносе из MySQL она пустая. Измерения агента живут только в снимке присутствия (Valkey); здесь — **переходы**.

- **`computer_health_events`**: `club_id` → `clubs`, `computer_id` → `club_computers` (ON DELETE CASCADE), `kind`
  (CHECK: `cpu_hot`, `gpu_hot`, `disk_low`, `disk_smart`, `mouse`, `keyboard`, `monitor`, `network_slow`, `unstable`),
  `raised_at`, `cleared_at` (NULL — проблема есть; CHECK ≥ `raised_at`), `details` jsonb (температура и порог, диски,
  скорость сети, счётчики сбоев — без персональных данных). PK (`id`, `raised_at`).
- **Партиции** по месяцам `raised_at` (UTC), как `api_request_logs` (§10.6, §12): белые списки
  `zafiro_create_monthly_partitions` и `zafiro_drop_monthly_partitions` расширены, таблица в `db.PartitionedTables` и
  `db.RetentionTables`; срок — `agent.health.event_retention` (90 дней), задача `logs:retention`.
- **Индексы**: (`club_id`, `computer_id`, `raised_at` DESC, `id` DESC) — история ПК с keyset; частичный
  (`club_id`, `computer_id`, `kind`) WHERE `cleared_at IS NULL` — открытые проблемы.
- **Одна открытая проблема вида у ПК** — `INSERT … SELECT … FROM club_computers WHERE club_id AND id AND NOT EXISTS
  (открытая)` (уникальный индекс партиционированной таблицы должен включать `raised_at`); ПК чужого клуба не вставить.
- **RLS** `tenant_isolation` + `platform_access` (FORCE). **Права**: `zafiro_app` — SELECT, INSERT, UPDATE
  только `cleared_at` (ни подменить, ни удалить историю), `zafiro_platform` — SELECT. Проверки —
  `TestAppRoleLeastPrivilege`, `TestHealthStatusToSnapshotAndHistory` (RLS чужого клуба).
- **Запись**: только при подтверждённом переходе (дребезг `raise_after`/`clear_after`, `server/internal/agent/health`),
  не на каждый Status: на 5 000 ПК в установившемся режиме — 0 строк в минуту (`docs/load-test.md` §6.3).

## 15. Почасовая история здоровья ПК (0031, Этап 7)

Новая функция (решения — `docs/open-questions/stage7-health.md` S7-H-13, S7-H-14). В старом Laravel таблицы нет — при
переносе из MySQL она пустая. Агрегат часа копится в Valkey (`docs/agent-protocol.md` §16.6); здесь — **одна строка на ПК
и час** после конца часа.

- **`computer_health_hourly`**: `club_id` → `clubs`, `computer_id` → `club_computers` (ON DELETE CASCADE), `hour` (начало
  часа UTC, CHECK `date_trunc('hour', hour) = hour`), `online_minutes`, `session_minutes` (0..60), среднее и максимум
  загрузки CPU, ОЗУ, GPU (сотые доли %) и температур CPU, GPU (десятые доли °C; NULL — не измерено; минимумов нет —
  S7-H-26: для решения о ремонте нужны максимумы и средние), `system_disk_free_mb` (минимум за час) и
  `system_disk_total_mb`, `smart_worst` (CHECK `ok`/`warning`/`failing`, NULL — не измерено), `peripheral_disconnects`,
  `unexpected_shutdowns`, `bugchecks` (прирост за час по счётчикам агента «перед загрузкой», ≥ 0; не измерено — 0,
  S7-H-27). Без float.
- **PK** (`club_id`, `computer_id`, `hour`) — он же составной индекс выборок «ПК за период» и ключ UPSERT сброса.
- **Партиции** по месяцам `hour` (UTC): белые списки `zafiro_create_monthly_partitions` и
  `zafiro_drop_monthly_partitions` расширены, таблица в `db.PartitionedTables` и `db.RetentionTables`; срок —
  `agent.health.hourly_retention` (180 дней), задача `logs:retention`.
- **RLS** `tenant_isolation` + `platform_access` (FORCE). **Права**: `zafiro_app` — SELECT, INSERT, UPDATE только
  измерений (повтор UPSERT); ключ строки (клуб, ПК, час) не изменить, строки не удалить; `zafiro_platform` — SELECT.
  Проверки — `TestAppRoleLeastPrivilege`, `TestClubMapComputerHealthWeekly` (строка чужого клуба с id нашего ПК не видна).
- **Запись**: задача `agent:health-hourly` (один исполнитель, Q-086) — `INSERT … SELECT FROM jsonb_to_recordset(…) JOIN
  club_computers (ПК этого клуба) ON CONFLICT DO UPDATE`, одна транзакция на клуб за час; объём и время —
  `docs/load-test.md` §6.4.
- **`zafiro_computer_diskless(club_id, computer_id)`** — признак «бездисковый ПК» (S7-H-18, S7-H-22) одним правилом для
  стрима и панели: действующий неотозванный сертификат ПК, иначе последний выпущенный, иначе false. `LANGUAGE sql STABLE`,
  SECURITY INVOKER — `agent_certificates` читается с RLS вызывающего; права — как у `zafiro_current_club_id` (0004).

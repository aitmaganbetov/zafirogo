## Настройки

### Q-S1. Фолбэк `storage/app/settings.json` для клуба `legacy`
- Контекст: `app/Services/CurrentClub.php` (`settings()`, ~строки 71–83): если у клуба со `slug='legacy'` `settings = null`, настройки читаются из файла.
- Варианты: (а) при переносе данных записать содержимое файла в `clubs.settings` этого клуба; (б) игнорировать (клуб получит дефолты).
- Рекомендация: (а), если файл существует на проде; иначе (б). Нужна проверка прод-сервера (`/home/admzafiro/Zafiro/storage/app/settings.json`).
- Решение (30.10.2026): см. [Q-022](../OPEN_QUESTIONS.md#q-022) — по DECISIONS «Данные и перенос» — проверяет инструмент переноса: файл есть — записать в `clubs.settings`, нет — дефолты; Go файл не читает.

### Q-S2. Нормализация старых значений настроек при переносе
- Контекст: минутные поля секции `club` могут быть строками вида `"30 сек"` (`SettingsController::minutes()`, ~416–426); черновые ключи `loyalty_rules`, `loyalty_type`, `tax_rate` должны были убраться миграцией `2026_10_18_100000_backfill_loyalty_spending.php`.
- Варианты: (а) `tools/migrate-from-mysql` приводит все значения к типам схемы и сообщает о неизвестных ключах; (б) хранить как есть и нормализовать при чтении в Go.
- Рекомендация: (а) — в Go строгая схема без «магического» парсинга строк, отчёт по клубам с неожиданными значениями.
- Решение (30.10.2026): см. [Q-023](../OPEN_QUESTIONS.md#q-023) — по DECISIONS «Данные и перенос» — нормализует инструмент переноса с отчётом о неизвестных ключах; в Go — строгая схема.

### Q-S3. Эндпоинт `GET /api/settings/{section}/{key}` и экран `/settings/api`
- Контекст: `routes/api.php` ~164–170, `SettingsController::showSetting()`, `api()`. Доступен любой роли клуба по Sanctum-токену (замечание в `docs/integration-api.md`, раздел 1). Используется (судя по экрану) мобильными приложениями, которые отложены.
- Варианты: (а) не переносить, настройки агенту — в составе gRPC-конфигурации, админке — через REST `/settings`; (б) перенести для будущих мобилок.
- Рекомендация: (а); вернуть при переносе мобилок в новом API.
- Решение (30.10.2026): см. [Q-059](../OPEN_QUESTIONS.md#q-059) — по DECISIONS Q-059 — `GET /api/settings/{section}/{key}` и экран `/settings/api` не переносим.

### Q-S4. Неиспользуемые настройки `session_idle_timeout` и `session_auto_terminate_when_pc_unavailable`
- Контекст: ключи сохраняются и показываются (`resources/views/settings/club.blade.php` ~31–32), но ни сервер, ни агент их не читают (grep по `app/` и `WindowsAgent/`). Сессии офлайн-ПК заканчиваются только по `session_ends_at` (`club-computers:expire-sessions`).
- Варианты: (а) перенести как «мёртвые» поля 1:1 (экран тот же); (б) убрать из UI; (в) реализовать смысл (авто-завершение при бездействии / недоступности ПК) — это изменение бизнес-логики и денег.
- Рекомендация: (а) на этапе переноса (дизайн сохраняется), пометить в коде `// не используется в Laravel`; реализацию (в) — отдельной задачей после запуска.
- Решение (30.10.2026): см. [Q-024](../OPEN_QUESTIONS.md#q-024) — по DECISIONS «Данные и перенос» — переносятся как есть (хранение и показ); реализация смысла — не в рамках переноса.

### Q-S5. Лимит сотрудников «на смене» без таблицы `sessions`
- Контекст: `app/Services/StaffShifts.php::onShift()` считает «на смене» по живым web-сессиям в БД за `SESSION_LIFETIME` (работает только при `SESSION_DRIVER=database`).
- Варианты: (а) аналог по активным refresh-токенам/сессиям в Valkey с последней активностью ≤ 120 мин; (б) явные смены сотрудника (вход/выход).
- Рекомендация: (а) — поведение то же; ввод явных смен — изменение логики.
- Решение (30.10.2026): см. [Q-035](../OPEN_QUESTIONS.md#q-035) — принята рекомендация: по активным сессиям панели в Valkey (≤ 120 мин активности); приложение сотрудника не ограничивать (как сейчас).

### Q-S6. Хэши PIN выхода агента и паролей (bcrypt → Argon2id)
- Контекст: `clubs.agent_exit_pin_hash` — `Hash::make` (bcrypt), `SettingsController::agentPin()`; то же для паролей и кодов.
- Варианты: (а) переносить bcrypt-хэши и перехэшировать Argon2id при успешной проверке; (б) сбросить PIN всем клубам.
- Рекомендация: (а) (поддержка проверки bcrypt только для старых хэшей).
- Решение (30.10.2026): см. [Q-051](../OPEN_QUESTIONS.md#q-051) — по DECISIONS Q-051 — bcrypt переносится как есть, перехеш при успешном входе (сделано); короткоживущие коды не переносятся.

### Q-S7. Пороги уровней скидки/бонуса в тенге с копейками (float) в JSON
- Контекст: `loyalty_levels[].spent`, `topup_bonus_levels[].amount` хранятся в тенге с 2 знаками (int|float) — `app/Support/PercentLevels.php`; сравнение в центах `round(x*100)`.
- Варианты: (а) хранить в jsonb тиынами (int64) + версия схемы, конвертировать при переносе и в API; (б) оставить формат как есть.
- Рекомендация: (а) — соответствует правилу «деньги только int64 в тиынах»; процент хранить в базисных пунктах (int) — так он и используется (`round(percent*100)`).
- Решение (30.10.2026): см. [Q-003](../OPEN_QUESTIONS.md#q-003) — по DECISIONS Q-003 — новые записи JSON в тиынах и базисных пунктах с `"v": 2`; чтение понимает старый формат; перенос данных переводит всё в v2.

### Q-S8. Значения, зашифрованные `APP_KEY` Laravel
- Контекст: `clubs.installation_key` (cast `encrypted`), `webhook_endpoints.secret` (cast `encrypted`), токены `platform_settings.telegram_gateway|telegram_alerts` (`Crypt::encryptString`). Формат Laravel: base64 JSON `{iv, value, mac, tag}`, AES-256-CBC + HMAC-SHA256.
- Варианты: (а) `tools/migrate-from-mysql` расшифровывает старым ключом (env только на время переноса) и шифрует новым AES-GCM; (б) секреты вебхуков перевыпустить (сломает интеграторов), Telegram-токены ввести заново.
- Рекомендация: (а) для `installation_key` и секретов вебхуков (иначе переустановка агентов/перенастройка интеграций); Telegram-токены — ввести заново вручную (2 значения).
- Решение (30.10.2026): см. [Q-050](../OPEN_QUESTIONS.md#q-050) — по DECISIONS Q-050 — секреты `APP_KEY` переносятся с расшифровкой старым ключом и перешифровкой новым; ключ установки клуба выпускается заново.

- Рекомендация: (б) только как событие (без движения денег), чтобы сверка «покупки ↔ сессии» была полной; денежная логика не меняется.
- Решение (30.10.2026): см. [Q-010](../OPEN_QUESTIONS.md#q-010) — по DECISIONS Q-010 — как в старом (части сессии при естественном окончании не удаляются) плюс событие `computer.session_expired` в журнал.

### Q-J3. Метрики сервера: таблица `server_metrics` или Prometheus
- Контекст: `CollectServerMetrics`/`ServerProbe` читают `/proc` одного хоста; при нескольких инстансах Go это теряет смысл.
- Варианты: (а) сохранить страницу «Сервер» суперадминки с метриками по каждому инстансу (`server_metrics` + `instance_id`); (б) экспорт `/metrics` в Prometheus/VictoriaMetrics, страница — ссылки/встроенные графики.
- Рекомендация: на этапе переноса (а) с `instance_id` (экран сохраняется), параллельно отдать `/metrics`.
- Решение (30.10.2026): см. [Q-083](../OPEN_QUESTIONS.md#q-083) — принята рекомендация: страница «Сервер» — `server_metrics` + `instance_id` и параллельно `/metrics`; старые `server_metrics`, `request_metrics` не переносить.

### Q-J4. Алерт по сроку TLS-сертификата

### Q-J5. Статус истёкших триалов

# Этап 1 — сервисный слой покупок и сессий (`server/internal/billing/service`): вопросы

Пакет связывает чистые расчёты (`billing/pricing`, `billing/session`, `billing/bonus`) с БД: покупка тарифа/минут,
запуск пакета, досрочное завершение с расчётом, пересадка, гостевая продажа, истечение сессий
(`server/internal/worker/expire_sessions.go`). Миграция — `db/migrations/0006_session_purchases_zone.sql`,
запросы — `db/queries/purchases.sql`, `db/queries/sessions.sql`.

- [ ] **SV-1. Идемпотентность покупок — своя таблица `billing_requests`, а не только `ledger_idempotency`.**
  - Контекст: покупка за 0 тиынов (скидка 100 %, GAP-011) и запуск пакета без минут не создают проводок, а повтор
    запроса должен вернуть прежний ответ (session_id, new_balance) даже после завершения сессии. Поэтому ключ клиента
    захватывается в `billing_requests (club_id, idempotency_key)` до блокировок, ответ первого выполнения хранится в
    `response`; ledger-операция использует тот же ключ. Отказ (валидация) ключ не занимает — транзакция откатывается.
  - Вопрос: срок хранения ключей (как L-6 для `ledger_idempotency`). Рекомендация: 13 месяцев, чистка фоновой задачей
    по индексу `(club_id, created_at)`.

- [ ] **SV-2. Лимит количества тарифа — счётчик `tariff_sales` (Q-007).**
  - Контекст: `purchaseCount()` (`AgentTariffPurchaseService.php` стр. 331–338) считал записи журнала `tariff.purchased`.
    Счётчик увеличивается под блокировкой тарифа (`FOR UPDATE`, как в `purchase()`); гостевые продажи его не трогают.
  - Перенос данных: `tools/migrate-from-mysql` должен заполнить `tariff_sales.sold = COUNT(activity_logs WHERE
    event='tariff.purchased' AND subject = тариф)`.
  - Попутно: `purchase()` не проверяет `is_active` — неактивный тариф покупается по id, если он в продаже
    (список агента его не показывает). Перенесено буквально; исправлять ли?

- [ ] **SV-3. `session_purchases.zone_id` / `source` для старых строк.**
  - Сделано по S1-SES-02 (вариант а): новые части пишут зону ПК и источник (`tariff` | `minutes` | `package`).
    Старые строки — `NULL`. В Go: `source NULL` → по `kind` (tariff — как покупка тарифа, minutes — поминутка);
    поминутка без `zone_id` для зон пересадки пропускается (ограничение снимается).
  - Перенос данных: заполнить из `activity_logs` (`time.purchased` → subject = зона, `tariff.purchased` → tariff,
    `time.package_started` → package) по `details.session_id`. Части живут ≤ 8 дней, поэтому достаточно перенести
    только части текущих сессий.

- [ ] **SV-4. Порядок блокировок: баланс блокируется раньше проверок.**
  - Контекст: в `sell()` баланс `lockForUpdate()` после всех проверок; `pricing.Quote*` считает всё сразу, поэтому
    сервис блокирует `member_balances` перед расчётом (после тарифа/членства/ПК — порядок блокировок тот же).
    Отличие только в том, что при отказе строка баланса тоже была заблокирована до конца транзакции.
  - Нет строки баланса: в Laravel `firstOrFail()` — 404 после проверок; здесь сначала проверки с нулевыми балансами
    (их ошибка важнее), затем `ErrNotFound`.
  - Взаимоблокировка: покупка тарифа блокирует членство → баланс, завершение сессии — баланс → членство
    (`subtractSpending`). В Laravel то же (UPDATE членства берёт блокировку строки); `db.InTenantTx` повторяет
    транзакцию при `40P01`. Подтвердить, что так оставляем.

- [ ] **SV-5. Ledger минут при запуске и сохранении пакета (Q-011).**
  - Запуск пакета: операция `package_start`, одна строка «минус весь остаток пакета» (пакет удаляется целиком, даже если
    срок урезал минуты — GAP-014); в `meta` — `started_minutes` и `lost_minutes`.
  - Сохранение при завершении: `+minutes` по созданному `time_packages.id` в той же операции, что возврат денег
    (`session_refund`), или отдельной `package_kept`, если денег нет. Ключ — `session_end:<session_id>`.
  - Потерянные секунды (тариф без лимита, неполная минута) — только в `meta` (`seconds_left`), как предлагал S1-SES-05.

- [ ] **SV-6. Нет строки баланса при возврате — деньги не начисляются, траты всё равно уменьшаются.**
  - Контекст: `SessionSettlement::settle()` стр. 329–337: `$balance === null` → баланс не меняется, но
    `subtractSpending()` вызывается. Повторено буквально (OQ-BR-12). Рекомендация: писать предупреждение в журнал
    сервера — в новой схеме строки баланса создаются вместе с членством, ситуация означает порчу данных.

- [ ] **SV-7. Предел `total_spent`.**
  - В MySQL `club_memberships.total_spent` — `decimal(12,2)`: больше 9 999 999 999.99 — ошибка и откат. Сервис
    проверяет этот предел (`MaxTotalSpent`). В `billing/bonus.AddSpending` предел — `money.MaxAmount` (1e15 тиынов),
    а в комментарии написано про decimal(12,2) — расхождение в чистом пакете (не мой файл; сервис его не использует
    для увеличения, увеличение — атомарным `UPDATE … total_spent + cents`, как `increment()`).

- [ ] **SV-8. Журнал действий (`activity_logs`) не пишется.**
  - Старый код писал `tariff.purchased`, `time.purchased`, `time.package_started`, `time.refunded`, `time.package_kept`,
    `computer.session_ended`, `session.transferred`, `cash.income`, `computer.guest_session`. Источником данных они больше
    не служат (лимит — `tariff_sales`, зоны — `session_purchases`), но экраны истории (GS-110, «Журнал») и GS-088/GS-103
    ожидают события. Денежные операции пишутся в `audit_log` (категория `money`, ссылка на ledger).
  - Вопрос: кто пишет журнал интерфейса — сервис (нужен общий пакет `activity`) или подписчик событий NATS?
    Рекомендация: общий пакет `activity` с вызовом из сервиса в той же транзакции (как старый код).

- [ ] **SV-9. Время брони в ошибке покупки — UTC.**
  - `sell()` форматирует `$booking->starts_at->format('H:i')`; модель брони отдаёт время в поясе
    `CurrentClub::timezone()`, а для `api/*` он UTC (`SetCurrentClub::handle()` стр. 89–91). Клиент в агенте видит
    «ПК забронирован с 02:30» при брони на 07:30 по Алматы. Перенесено буквально (UTC); гостевая продажа (веб) —
    в поясе клуба. Рекомендация: исправить на пояс клуба (баг старого кода).

- [ ] **SV-10. Контракт `CashRecorder` (гостевая продажа) — согласовать с агентом кассы.**
  - Сервис: захват ключа → `LockOpenShift` (нет смены → «Сначала откройте смену в кассе.») → тариф → ПК → цена →
    сессии ПК → `RecordGuestSessionIncome`. Реализация пишет `cash_transactions` (income, `income_kind = guest_session`,
    `payment_method`, `idempotency_key`), ledger `guest_session` (`cash_drawer` −сумма, `revenue_time` +сумма, ссылки на
    смену и операцию) и аудит. Сумма 0 (тариф за 0): приход 0.00 создаётся, проводок нет.
  - Описание операции собирается по-русски при записи (`Гостевая сессия: тариф «Час», ПК PC-01 (наличные)`) — как
    `__()` в старом коде, который писал текст на языке запроса. По правилам локализации тексты в БД не переводятся —
    при переносе экрана кассы решить, хранить ли описание ключом с параметрами.

- [ ] **SV-11. Истечение сессий: тикер раз в минуту + advisory lock на тик.**
  - Как `everyMinute()` Laravel; `docs/parts/50-jobs.md` предлагает 5–10 с и событие NATS (`OnExpired` — точка
    подключения). Лок берётся на тик (`pg_try_advisory_lock` на соединении пула `zafiro_platform`), не на всё время
    жизни процесса: два инстанса не выполняют тик одновременно, но могут выполнить его подряд (UPDATE идемпотентен).
  - `expireIfDue()` в heartbeat — не перенесён (слой агента).
  - Запрос `ExpireDueSessions` — платформенный (без `club_id` в WHERE; правило `sqlc vet` пропускает его из-за
    `RETURNING club_id`). Рекомендация: явно внести его в список исключений `sqlc.yaml`.

# Вопросы Этапа 6 — O4 «нагрузка»

Код и файлы: `server/cmd/loadgen/**` (тег `loadgen`, не в CI), `tools/loadgen/**` (дополнение compose, адреса клубов,
README), `docs/load-test.md` (отчёт), `docs/deploy.md` §12 «Ресурсы». Исправления сервера (с тестами):
`server/internal/app/run.go` (listener gRPC закрывается до Drain), `server/internal/db/pool.go` +
`server/internal/app/observability.go` (размер пулов по умолчанию), `server/internal/monitoring/workers.go`
(порядок UPSERT счётчиков).

Решения приняты по принципам `docs/DECISIONS.md` (владелец поручил); отменить может только владелец.

## Открытые (нужна работа до прода)

Нет (S6-O4-1…3 сделаны — ниже).

## Принятые решения (подтвердить)

- [x] **S6-O4-1. Лимит дескрипторов балансировщика — в `deploy/staging/compose.yaml`.** `lb.ulimits.nofile` =
  `${STG_LB_NOFILE:-20000}` (без него nginx получал мягкий лимит 1024 на воркер — ≈ 2 000 агентов); дополнение
  `tools/loadgen/compose.load.yaml` для этого больше не нужно. Прод — ≥ 131 072 (`docs/deploy.md` «Ресурсы»),
  проверка: в журнале nginx при старте нет `setrlimit … failed`.
- [x] **S6-O4-2. `proxy_connect_timeout` HTTP-upstream — 1 с** (`deploy/staging/nginx/snippets/proxy.conf`, было 3 с;
  умолчание nginx 60 с там не действовало — сниппет подключён во всех `location`). Пока адрес остановленного инстанса
  в кэше DNS (≤ 10 с), запрос ждёт не больше секунды и уходит на другой инстанс (`proxy_next_upstream error timeout`;
  POST nginx не повторяет). Соединение внутри сети — доли миллисекунды, запас достаточный. Поток агентов (stream) —
  без изменений (3 с; переподключение агента и так с повтором).
- [x] **S6-O4-3. Перевод сообщений API больше не открывает транзакцию на каждый вызов.** `i18n.Catalog.Lookup`
  берёт строки из памяти, пока версия переводов сверена не раньше чем 5 с назад (`lookupVersionTTL`); язык клуба
  (`ClubLocale`) уже кэшировался на 30 с. Транзакция платформенного пула изнутри тенантной открывается теперь не чаще
  раза в 5 с на инстанс (было — на каждое переводимое сообщение, под общим мьютексом каталога). Цена: правка перевода
  в суперадминке видна в сообщениях API сервера через ≤ 5 с (пакеты i18next интерфейса — сразу, как раньше). Тест
  `TestLookupUsesMemoryWithinTTL`.
- [x] **S6-O4-4. Плановая остановка: listener gRPC закрывается до Drain** (`app/run.go`, тест
  `TestAppDrainOnShutdown`). Было: во время окна Drain инстанс принимал новые соединения, и балансировщик (`least_conn`:
  на уходящем инстансе меньше всего соединений) возвращал переподключающиеся ПК обратно — они рвались при выходе:
  2 500 потоков → 7 300 обрывов, 78 с до восстановления. Стало: 0 обрывов, ПК ушли на второй инстанс в окне 10 с.
- [x] **S6-O4-5. Размер пулов Postgres по умолчанию — `max(16, 4 × CPU)`** (`db.ParsePoolConfig`, тест
  `TestParsePoolConfigMaxConns`); явный `pool_max_conns` в DSN имеет приоритет. Было (умолчание pgx `max(4, CPU)`):
  4 соединения на пул; при 5 000 ПК на одном инстансе (после потери второго) — пул занят целиком, 160+ ожидающих,
  ответы 10–30 с, тысячи таймаутов (денег не потеряно). Стало: 0 ошибок, занято в пике 5 из 16.
- [x] **S6-O4-6. Сброс счётчиков мониторинга — в одном порядке** (`monitoring.Workers.Flush`, `sortedKeys`, тест
  `TestSortedKeysStableOrder`). Было: два инстанса в одну секунду UPSERT'или строки `request_metrics` в порядке обхода
  map — 14 deadlock за час (повторялись, данные не терялись). На staging после исправления не перемерено (модульный тест).
- [x] **S6-O4-7. Сертификаты ПК для теста — прямой выпуск от staging-CA.** `loadgen prepare` выпускает сертификаты
  `pki.CA.Issue` и пишет строки `agent_certificates` (как `Enroll`); лимиты регистрации в коде не отключались. Настоящий
  путь (код через REST → `Enroll` через nginx) — выборка 50 ПК (p95 код 6 мс, `Enroll` 11 мс).
- [x] **S6-O4-8. Адрес источника на клуб** (`tools/loadgen/net.sh`): лимиты по IP действуют на клуб, как в жизни.
- [x] **S6-O4-9. Пароли набора — Argon2id** (иначе первый вход каждого гостя — bcrypt cost 12 + перехеширование).

## Наблюдения (не блокируют, на 50 000 ПК)

- [ ] **S6-O4-10. Автобиллинг: 200 ПК за тик (1 с) на кластер.** `guestapi.AutoBillingBatch = 200`, пересмотр гостя
  без сессии — раз в 30 с: потолок ≈ 6 000 одновременно вошедших гостей без сессии. На 5 000 ПК тик занимает 1–2 %
  времени. На 50 000 — следить за `zafiro_worker_run_duration_seconds{job="agent:auto-billing"}` и размером zset
  `<agent.stream.key_prefix>ab:due`; при росте — пакет больше или повтор тика, пока есть просроченные.
- [ ] **S6-O4-11. `BalanceChanged` читает присутствие всего клуба.** `guestapi.abNotifier.BalanceChanged` на каждое
  изменение баланса вызывает `Presence.List(club)` (HGETALL + разбор JSON всех ПК клуба). 100 ПК — незаметно; клуб на
  500 ПК в пиковую минуту — тысячи разборов в секунду. На потом: индекс «гость → ПК» в Valkey.
- [ ] **S6-O4-12. После перезапуска потоки остаются на одном инстансе** (`least_conn` выравнивает только новые
  соединения). Рекомендация в runbook: после возврата инстанса — плановый перезапуск перегруженного (Drain) или
  команда «перебалансировать» в будущем.

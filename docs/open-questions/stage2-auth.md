# Этап 2, A1 — авторизация и права: вопросы и допущения

Код: `server/internal/auth/**`, `server/internal/http/auth.go`, `api/openapi.yaml` (`/api/auth/*`, `/api/superadmin/*`),
`db/queries/auth.sql`. Везде, где решения нет, повторено старое поведение; отступления перечислены ниже.

## Нужно сделать оркестратору

- [ ] **sqlc.yaml — исключения tenant-filter.** Запросы к `users` (платформенная таблица без `club_id` и без RLS) не могут
  фильтровать по клубу: `GetUserByPhone`, `GetUserAuth`, `UpdateUserPasswordHash` (`db/queries/auth.sql`). Добавить их в список
  `query.name in [...]` правила `tenant-filter`, иначе `sqlc vet` падает (генерация работает).
- [ ] **Фронт:** `npm run gen:api` в `web/` (типы `/api/auth/*`) — в `web/` A1 не пишет.

## Вопросы владельцу

### 1. Лимит на веб-вход и регистрацию
- Контекст: в старом `POST /login`, `POST /register` без `throttle:` (`routes/web.php:158, 165`; `docs/open-questions/screens.md` §1).
- Сделано: именованные правила `web-login` и `web-register` (5/мин на IP+телефон и 300/мин на IP — как `customer-login`),
  **выключены по умолчанию**; `web-login` уже подключён к `POST /api/auth/login`, включается `Options.Enable` лимитера.
- Рекомендация: включить `web-login` (подбор пароля сотрудника без лимита — главный риск панели).

### 2. Режим просмотра клуба суперадмином (Q-054)
- Сделано: не отдельный токен, а поле `view` в той же сессии (как ключ `superadmin_viewing_club_id` в web-сессии Laravel).
  Principal = владелец (все права) + `ReadOnly`; `permissions.RequireClub` отклоняет всё, кроме GET/HEAD/OPTIONS/TRACE,
  текстом «Режим просмотра: суперадмин не может ничего менять в клубе.». Смена клуба в этом режиме тоже запрещена
  (в старом `clubs.switch` не входит в исключения `superadmin.*`, `auth.logout`). Выход из режима — `POST /api/superadmin/leave-club`.
- Допущение: транзакция `auth.TenantTx` в режиме просмотра не помечается `READ ONLY` (у `db.InTenantTxWith` нет такого
  параметра). Рекомендация: добавить в `db` опцию `ReadOnly` и включать её из `TenantTx` — второй рубеж.

### 3. «На смене» (BR-060, Q-035, Q-S5)
- Сделано как в старом: на смене — члены клуба с ролью (кроме входящего), у которых есть сессия панели с активностью за
  `IdleTTL` = 120 мин (SESSION_LIFETIME). Активность — в Valkey (`auth:u:{uid}`), обновляется при входе, refresh и запросах
  (не чаще раза в минуту). Как и в старом, учитывается сессия пользователя в любом клубе. Выход — сразу освобождает место.
- Приложение сотрудника (мобилки отложены) лимит не проверяет — как сейчас.

### 4. «Запомнить меня»
- Старый: cookie remember Laravel (по умолчанию ~5 лет). Новый: сессия с `remember` живёт без активности до 30 дней,
  абсолютный срок любой сессии — 30 дней (`MaxLifetime`). Без `remember` — 120 мин без активности.
- Вопрос: устраивает ли 30 дней? Рекомендация: да.

### 5. Текст и формат 429
- Ответ: 429 `{"error":"too_many_requests","message":"Too Many Attempts."}` + `Retry-After`, `X-RateLimit-Limit`,
  `X-RateLimit-Remaining`, `X-RateLimit-Reset` (как `ThrottleRequests` для JSON). Текст английский — в старом он не шёл через `__()`.
  Веб-маршруты старого показывали HTML-страницу 429. Вопрос: переводить ли («Слишком много попыток»)? Рекомендация: добавить ключ перевода на Этапе 3.

### 6. Алгоритм лимитов
- Скользящее окно (журнал меток в sorted set, Lua), а не фиксированное окно Laravel: «не больше N за любые M минут».
  Строже Laravel на стыке окон (Laravel пропускает до 2N). Порядок лимитов правила — как `ThrottleRequests`: каждый
  засчитывается по очереди, первый превышенный даёт 429. Отклонённые запросы не считаются.
- При недоступном Valkey лимитер отклоняет запрос (503), как старый при упавшем кэше; есть `FailOpen`.

### 7. Членство в выбранном клубе удалено во время сессии
- Старый: `SetCurrentClub` → 403 «Нет доступа к выбранному клубу.» на всех маршрутах (включая выход) до конца web-сессии.
- Новый: Principal без клуба (`ClubID = 0`), клубные эндпоинты — 403 «У аккаунта нет доступа ни к одному клубу.»,
  `/api/auth/me` и выбор другого клуба работают. Рекомендация: оставить (старое поведение — тупик).

### 8. Домен кабинета суперадмина (Q-069)
- Проверка «Здесь входят только суперадмины Zafiro.» на `SUPERADMIN_DOMAIN` не перенесена — зависит от решения Q-069.

### 9. Блокировка
- Как в старом: проверяется после пароля (статус «заблокирован» виден только с верным паролем); при запросе с живой
  сессией — 403 «Аккаунт заблокирован.» и отзыв всех сессий пользователя. Блокировка суперадмином (волна B) должна
  вызывать `session.Manager.RevokeUser` — тогда отказ мгновенный и без обращения к БД.

## Технические решения (для сведения)

- Access-токен — HMAC-SHA256 (свой компактный формат, kid для ротации ключей), 10 мин; на каждом запросе проверяется
  сессия в Valkey и пользователь/членство в Postgres (права и блокировка — сразу, как в старом). Ed25519 не нужен:
  выпускает и проверяет один сервис.
- Refresh — `<sid>.<32 байта>`, в Valkey только sha256; ротация на каждом обновлении; повтор использованного — отзыв семейства;
  повтор предыдущего в течение 10 с — 409 (гонка вкладок), без отзыва; угаданный sid сессию не отзывает.
- Cookie: `__Secure-zafiro_rt` (HttpOnly, Secure, SameSite=Strict, Path=/api/auth), `__Host-zafiro_csrf` (не HttpOnly) —
  `X-CSRF-Token` = HMAC(ключ, sid), проверяется пересчётом; плюс отказ при `Sec-Fetch-Site: cross-site/same-site`
  (и на входе — защита от login CSRF). Отсутствующий `X-CSRF-Token` на `/refresh` — 400 от сгенерированного биндинга.
- Пароли: Argon2id m=19 MiB, t=2, p=1 (OWASP); bcrypt `$2y$` проверяется по первым 72 байтам (как PHP `password_verify`),
  при успешном входе — перехеш (как `rehash_on_login` Laravel 11). Неизвестный телефон — та же работа (dummy-хэш).
  Одновременных вычислений Argon2id — не больше 2×GOMAXPROCS. PIN выхода агента (`clubs.agent_exit_pin_hash`, Q-S6) может
  использовать тот же `password.Hasher`.

## Сверка с `web/src/layouts/permissions.ts`

- Матрица `SECTIONS` и `allows()` совпадают с `ClubPermissions.php` (проверено построчно).
- Расхождения: `MembershipRole` содержит `'customer'`, в старом и новом — `'client'` (и старые не-сотруднические роли вроде
  «Пользователь»); `permissions` в TS не допускает `null` (в БД `club_memberships.permissions` — NULL у большинства);
  меню не учитывает режим просмотра (кнопки изменений видны, сервер их отклонит).
- Рекомендация: в SPA брать готовый список `me.permissions` из `/api/auth/me` (сервер уже применил роль и выбор владельца)
  вместо повторного расчёта — одна точка правды.

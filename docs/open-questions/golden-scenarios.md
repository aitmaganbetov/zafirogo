# Открытые вопросы: эталонные сценарии

Документ: [`docs/golden-scenarios.md`](../golden-scenarios.md). Вопросы, которые требуют решения владельца или проверки на работающем старом коде.

## ОВ-1. Подтвердить числа сценариев GAP-001…GAP-036 на старом коде

- **Контекст.** Сценарии раздела «Пробелы покрытия» посчитаны вручную по формулам старого кода (`app/Services/SessionSettlement.php` `settle()`, `AgentTariffPurchaseService.php` `sell()/discounted()/minutesPriceInCents()`, `TopUpBonus.php` `for()`, `CashRegisterService.php` `refund()/close()`, `ShiftReport.php` `for()`, `Friends.php` `transfer()`, `FriendTransferCodes.php`). Старый репозиторий по правилам Этапа 0 только для чтения — тесты в нём не запускались.
- **Варианты.** (а) Принять числа как есть; (б) на Этапе 1 прогнать эти сценарии как Pest-тесты в одноразовой копии Zafiro (Docker, не трогая оригинал) и только потом сделать эталоном Go; (в) проверить вручную на стенде старого Laravel.
- **Рекомендация:** (б) — это дёшево (36 коротких тестов) и снимает риск ошибки ручного расчёта.
- Решение (30.10.2026): см. [Q-006](../OPEN_QUESTIONS.md#q-006) — по DECISIONS Q-006 — сделано: GAP-сценарии подтверждены оракулом.

## ОВ-2. Суммы с тремя и более знаками после запятой

- **Контекст.** Касса и пополнение без кассы принимают `numeric` и считают во `float`: `CashRegisterService::topUpBalance()` (`$balance->increment($balanceType, $amount)`, ~строка 112), `sale()` (`$total += (float) $product->price * $quantity`, ~строка 49), `UserController::update()` (`round((float) $data['top_up_amount'], 2)`, ~строка 111). Колонки `decimal(12,2)` / `decimal(14,2)` округляют при записи (поведение зависит от СУБД). Переводы друзьям, наоборот, отвергают больше двух знаков (`Friends::amountToCents()`, ~строка 176 → 0 → ошибка `amount`). Тесты используют максимум два знака (`10000.55`, `40.5`).
- **Варианты.** (а) В Go везде отвергать суммы с >2 знаками (422); (б) округлять half-up до тиына, как MySQL `decimal(…,2)`; (в) повторить поведение каждого места отдельно.
- **Рекомендация:** (а) — единое правило проще и безопаснее; пользователям интерфейса это не мешает (поля ввода и так с двумя знаками). Нужно согласие владельца, т. к. это формально изменение поведения.
- Решение (30.10.2026): см. [Q-002](../OPEN_QUESTIONS.md#q-002) — по DECISIONS Q-002/CQ-3 — ввод с > 2 знаками после точки отклоняется (422) во всех формах и RPC; остаток кассы и лимиты сравниваются точно в тиынах.

## ОВ-3. Бонус за пополнение и начальный баланс вне кассы

- **Контекст.** Бонус за пополнение начисляется только при пополнении через кассу (`CashRegisterService::topUpBalance()`). Пополнение владельцем «без кассы» (`UserController::update()`, ~строки 140–152) и начальный баланс при создании клиента (`users.store`, тест `UsersTest.php` «the user list creates customers only»: 2500 / 150) бонус не дают и записи в кассе не создают (GAP-020).
- **Вопрос.** Это намеренно (владелец сам решает, сколько бонусов дать) или недосмотр?
- **Рекомендация:** перенести буквально (без бонуса), как требует принцип «бизнес-логика сохраняется»; при желании изменить — отдельной задачей после переноса.
- Решение (30.10.2026): см. [Q-009](../OPEN_QUESTIONS.md#q-009) — по DECISIONS Q-009 — как в старом: бонус только при пополнении основного баланса через кассу; при возврате бонус забирается в пределах остатка.

## ОВ-4. Лимит количества тарифа считается по журналу действий

- **Контекст.** `AgentTariffPurchaseService::purchaseCount()` (~строка 331) и `availableFor()` считают покупки тарифа по числу записей `activity_logs` с `event = tariff.purchased` и `subject = тариф`, за всё время и по всем пользователям. Тест `TariffEditTest.php` «the tariff list says why a tariff is not offered now…» создаёт такие записи напрямую через `ActivityLogger`. Гостевые сессии с тарифом на кассе (`GuestSessions::sell()`) эту запись не создают и в лимит не входят.
- **Варианты.** (а) В Go хранить счётчик/таблицу покупок тарифа, при переносе данных посчитать его из `activity_logs`; (б) оставить подсчёт по журналу.
- **Рекомендация:** (а) — журнал не должен влиять на деньги; но правило «гостевые продажи в лимит не входят» сохранить и записать в `business-rules.md`. Уточнить у владельца, правильно ли, что кассовые продажи тарифа не уменьшают лимит.
- Решение (30.10.2026): см. [Q-007](../OPEN_QUESTIONS.md#q-007) — по DECISIONS Q-007 — сделано: своя таблица `tariff_sales`, кассовые продажи лимит не расходуют; счётчики заполняет инструмент переноса.

## ОВ-5. Истечение сессии не вызывает расчёт (`settle()`)

- **Контекст.** `ClubComputerSessions::expireIfDue()` (~строка 177) и `expireAll()` (~строка 189) только очищают поля сессии ПК; строки `session_purchases` удаляет лишь `SessionSettlement::settle()` при досрочном завершении. После естественного окончания строки остаются навсегда (GAP-005). На деньги это не влияет (время использовано полностью).
- **Варианты.** (а) В Go удалять части сессии и при истечении (без возврата); (б) повторить как есть.
- **Рекомендация:** (а) — наблюдаемое поведение (балансы, ответы) не меняется, база не растёт. Если владелец против — (б).
- Решение (30.10.2026): см. [Q-010](../OPEN_QUESTIONS.md#q-010) — по DECISIONS Q-010 — как в старом (части сессии при естественном окончании не удаляются) плюс событие `computer.session_expired` в журнал.

## ОВ-6. Поле `discount_amount` в отчёте смены

- **Контекст.** `ShiftReport::for()` (~строка 63) суммирует `receipt_data.discount_amount`, но ни один код его не пишет (`grep discount_amount` находит только чтение). Отчёт всегда показывает скидку 0.
- **Рекомендация:** не переносить поле (или переносить как постоянный 0) — уточнить, планировалась ли скидка на чек POS.
- Решение (30.10.2026): см. [Q-017](../OPEN_QUESTIONS.md#q-017) — по DECISIONS Q-017 — `discount_amount` в отчёте смены оставляем (всегда 0, как в старом).

## ОВ-7. Коды ответов для нового API агента и гостя

- **Контекст.** Сценарии агента проверяют HTTP-коды старого API: 401 (`invalid_agent_token`, `device_mismatch`), 402 (подписка), 403 (`wrong_computer`, `use_device_token`, `shop_disabled`, `qr_disabled`), 409 (`signed_in_elsewhere`, `pin_not_configured`), 410 (`qr_expired`), 422 (валидация), 429 (лимиты). По решению №3 API агента проектируется заново (gRPC).
- **Рекомендация:** зафиксировать таблицу соответствия в контракте `proto/agent/v1`: 401 → `UNAUTHENTICATED`, 402 → `FAILED_PRECONDITION` + reason `subscription_inactive`, 403 → `PERMISSION_DENIED`, 409/410 → `FAILED_PRECONDITION`/`ABORTED` с машинным `code`, 422 → `INVALID_ARGUMENT` + `BadRequest.field_violations`, 429 → `RESOURCE_EXHAUSTED`; машинные коды (`wrong_computer`, `qr_expired`, …) сохранить строками в `ErrorInfo.reason`, чтобы сценарии переносились один в один.
- Решение (30.10.2026): см. [Q-043](../OPEN_QUESTIONS.md#q-043) — принята рекомендация: в `ErrorInfo.reason` — имена `ERROR_CODE_*` proto; в `agent-protocol.md` — таблица «старый код → `ERROR_CODE_*` + gRPC-статус».

## ОВ-8. Наследие `settings.json` для клуба `legacy`

- **Контекст.** `CurrentClub::settings()` (~строка 72) для клуба `legacy` при `clubs.settings = NULL` читает настройки из файла `storage/app/settings.json`. Тесты `TariffTest.php`, `DashboardTest.php`, `SettingsTest.php` на это опираются (валюта RUB из файла).
- **Вопрос.** Остался ли на проде клуб `legacy` с `settings = NULL` и файлом настроек?
- **Рекомендация:** в Go не переносить чтение файла; при переносе данных записать содержимое файла в `clubs.settings` клуба `legacy`. Соответствующие сценарии в Go дают настройки сразу в БД.
- Решение (30.10.2026): см. [Q-022](../OPEN_QUESTIONS.md#q-022) — по DECISIONS «Данные и перенос» — проверяет инструмент переноса: файл есть — записать в `clubs.settings`, нет — дефолты; Go файл не читает.

## ОВ-9. «Клиент» с ролью кассира в тестах агента

- **Контекст.** В `AgentSecurityTest.php` и `ComputerSessionTest.php` («staff get a device token…») пользователь, названный в тесте «customer», на самом деле имеет роль `cashier`, потому что «клиентское» поведение там означает «не из `ClubComputerSessions::STAFF_ROLES` = owner, admin, manager, operator» (`app/Services/ClubComputerSessions.php`, ~строка 28). То есть кассир на ПК считается клиентом.
- **Вопрос.** Это намеренно (кассир не должен получать токен ПК и права техрежима)?
- **Рекомендация:** перенести буквально; в Go-тестах прогонять эти сценарии для ролей `cashier` и `client` (оба должны вести себя как клиент).
- Решение (30.10.2026): см. [Q-044](../OPEN_QUESTIONS.md#q-044) — принята рекомендация: перенести буквально (кассир на ПК — как клиент), тесты для `cashier` и `client`.

## ОВ-10. Отрицательные суммы в `amountToCents()/formatCents()`

- **Контекст.** `AgentTariffPurchaseService::amountToCents("-1.50")` даёт −50 вместо −150, `formatCents(-150)` даёт `"-1.-50"` (~строки 385–395). Сейчас отрицательные балансы не возникают (проверки «не ниже нуля» в `sell()`, списании и возвратах), поэтому ошибка не проявляется. В `Friends::formatCents()` отрицательные числа обрабатываются верно.
- **Рекомендация:** в Go использовать одну корректную функцию форматирования `int64` тиынов (с правильным знаком) и тест на отрицательные значения; поведение для неотрицательных сумм совпадает со старым.
- Решение (30.10.2026): см. [Q-004](../OPEN_QUESTIONS.md#q-004) — по DECISIONS Q-004 — ошибку знака не переносим; ledger не даёт уйти в минус; `CHECK (balance >= 0)` — после проверки данных при переносе, отрицательные остатки — входящим остатком с пометкой в отчёте.

## ОВ-11. Учёт трат лояльности опирается на глобальный скоуп клуба

- **Контекст.** `LoyaltyProgram::addSpending()/subtractSpending()` (~строки 127–145) обновляют `ClubMembership::where('user_id', …)` без явного `club_id` — правильный клуб выбирает глобальный скоуп `BelongsToClub`. Аналогично `MemberBalance::where('user_id', …)` во всех денежных сервисах.
- **Рекомендация:** не вопрос к владельцу, а требование к Go: каждый денежный запрос sqlc обязан содержать `club_id` явно; добавить сценарий «клиент в двух клубах — покупка в одном не меняет баланс и `total_spent` в другом» (частично есть: `AgentRegisterTest.php` «a customer of another club joins…», `ApiAuthTest.php` «api me returns only…»).
- Решение (30.10.2026): см. [Q-020](../OPEN_QUESTIONS.md#q-020) — по принципам (PD-1) — правило подтверждено: каждый денежный sqlc-запрос к тенантной таблице явно фильтрует по `club_id`, второй рубеж — RLS; сценарий «клиент в двух клубах» обязателен в тестах денежных операций.

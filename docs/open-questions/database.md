## Деньги

- [x] **В-1. Единица хранения денег: в MySQL — тенге `decimal`, в 0001 — тиыны `bigint` при тех же именах полей. Подтверждаете?**
  - Контекст: 12 полей `decimal(12,2)`/`decimal(14,2)` хранят тенге (cast `decimal:2`, например `app/Models/MemberBalance.php`,
    `CashTransaction.php`); при этом `session_purchases.main_cents/bonus_cents` и `transfer_codes.amount_cents` уже в тиынах,
    а код переводит туда-обратно через `AgentTariffPurchaseService::amountToCents()/formatCents()` (~стр. 385–395).
    ТЗ требует `int64` в тиынах.
  - Варианты: (а) `bigint`-тиыны с теми же именами (`price`, `amount`, `balance`) + `COMMENT` — сделано в 0001;
    (б) переименовать в `*_tiyn` (`price_tiyn`) — сразу видно единицу, но ломает «те же имена»;
    (в) оставить `numeric(14,2)` в тенге и переводить в Go — противоречит правилу «int64 в тиынах».
  - Рекомендация: (а). Перенос `× 100` точный; в Go — тип `money.Tiyn int64`, чтобы не спутать единицы.
  - Решение (30.10.2026): см. [Q-001](../OPEN_QUESTIONS.md#q-001) — по DECISIONS Q-001 — `bigint`-тиыны под прежними именами колонок, перенос `× 100` (сделано в 0001).

- [x] **В-2. Суммы внутри JSON — переводить в тиыны при переносе?**
  - Контекст: `cash_transactions.receipt_data` (`{top_up: {bonus: <float тенге>}}`, `{items: [...]}` —
    `app/Services/CashRegisterService.php` ~стр. 69, 126) участвует в расчёте возврата (~стр. 175–184);
    `shop_orders.items[].price/total` — строки `"0.00"` (`AgentShop.php` ~стр. 60–61); `clubs.settings.finances.loyalty_levels[].spent`,
    `topup_bonus_levels[].amount` — тенге (`SaveSettingsRequest.php` стр. 35, 46); `activity_logs.details.amount` — тенге (история);
    `webhook_deliveries.payload.amount` — строка `"123.45"` (внешний контракт API v1, `CashRegisterService.php` ~стр. 81).
  - Варианты: (а) переводить всё в тиыны; (б) переводить только то, что участвует в расчётах (`receipt_data`, `items`, уровни в
    `settings`), историю (`activity_logs.details`) и внешний payload оставить; (в) не трогать, переводить при чтении в Go.
  - Рекомендация: (б) + поле версии формата (`"v": 2`) в переведённых JSON; payload вебхуков — формат API v1 решается отдельно.
  - Решение (30.10.2026): см. [Q-003](../OPEN_QUESTIONS.md#q-003) — по DECISIONS Q-003 — новые записи JSON в тиынах и базисных пунктах с `"v": 2`; чтение понимает старый формат; перенос данных переводит всё в v2.

- [x] **В-3. Можно ли балансу быть отрицательным? Добавить `CHECK (balance >= 0)` в Этапе 1?**
  - Контекст: `member_balances.balance` — signed `decimal`, CHECK нет; код проверяет достаточность перед списанием
    (`AgentShop.php` ~стр. 66–68, `CashRegisterService.php` ~стр. 178), но гарантии БД нет.
  - Рекомендация: после переноса проверить `SELECT … WHERE balance < 0 OR bonus_balance < 0`; если пусто — добавить CHECK вместе с ledger.
  - Решение (30.10.2026): см. [Q-004](../OPEN_QUESTIONS.md#q-004) — по DECISIONS Q-004 — ошибку знака не переносим; ledger не даёт уйти в минус; `CHECK (balance >= 0)` — после проверки данных при переносе, отрицательные остатки — входящим остатком с пометкой в отчёте.

- [x] **В-4. Float в денежном коде кассы.** `CashRegisterService` сравнивает и вычитает `(float)` (`~стр. 169–187`), бонус
  хранит `bonus['cents'] / 100` (~стр. 126). В Go всё станет целыми тиынами — возможны расхождения в 1 тиын с

  - Решение (30.10.2026): см. [Q-005](../OPEN_QUESTIONS.md#q-005) — по DECISIONS Q-005 — для корректного ввода расхождения в 1 тиын недопустимы; при переносе — пересчёт балансов из истории старой БД в отчёте переноса.

## Схема и данные

- [x] **В-7. Регистронезависимость MySQL (`utf8mb4_unicode_ci`) — сохранять?**
  - Контекст: `config/database.php` ~стр. 57. UNIQUE `users.phone`, `clubs.slug`, `products(club_id, sku)`, `tariffs(club_id, name)`,
    `product_categories(club_id, name)`, `languages.code` и все `WHERE name LIKE …` сейчас без учёта регистра (и без учёта
    конечных пробелов — PAD SPACE). В 0001 — регистрозависимо.
  - Варианты: (а) unique-индексы по `lower(col)` + поиск через `lower()`/`ILIKE` (+ `pg_trgm` для поиска);
    (б) недетерминированная ICU-collation `und-u-ks-level2` на этих колонках (нет `LIKE` по ним в PG < 18 — в 18 частично);
    (в) `citext`.
  - Рекомендация: (а) миграцией Этапа 1 для перечисленных UNIQUE; перед переносом — запрос на дубли без учёта регистра.
  - Решение (30.10.2026): см. [Q-025](../OPEN_QUESTIONS.md#q-025) — по DECISIONS Q-025 — `citext`/уникальные индексы по `lower()` там, где в MySQL была уникальность строки; перед переносом — поиск дублей без учёта регистра.

- [x] **В-8. CHECK на enum-полях могут не пустить старые данные.** Наборы взяты из текущего кода (`docs/parts/30-database.md`),
  но ранние версии могли писать другие значения (например `club_computers.status` — сейчас пишутся только
  `available/online/offline/restarting`; вычисляемый `reserved` в БД не пишется). Рекомендация: перед переносом выполнить на MySQL
  `SELECT col, COUNT(*) … GROUP BY col` по всем полям с CHECK; неизвестные значения — решить по одному.
  - Решение (30.10.2026): см. [Q-026](../OPEN_QUESTIONS.md#q-026) — по DECISIONS «Данные и перенос» — инструмент переноса проверяет распределение значений всех полей с CHECK, неизвестные — в отчёт.

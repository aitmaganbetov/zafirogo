# Открытые вопросы: ledger, аудит, RLS (Этап 1, субагент «ledger»)

Формат: вопрос → контекст → варианты → что сделано сейчас. Реализация — `docs/schema-changes.md` §10.

- [ ] **L-1. Удаление кодов перевода после подтверждения — во всех клубах или только в текущем?**
  - Контекст: `FriendTransferCodes::confirm()` (`app/Services/FriendTransferCodes.php` ~стр. 94) удаляет **все** коды пользователя
    (`TransferCode::where('user_id', …)->delete()`), а последний код ищет тоже без клуба (~стр. 79). У `transfer_codes` нет `club_id`
    (Q-028), правило `sqlc vet tenant-filter` требует `club_id` в каждом запросе.
  - Сделано: запросы `LockLatestTransferCode`/`DeleteUserTransferCodesInClub` ограничены дружбами текущего клуба (`JOIN friendships`).
    Отличие: коды того же пользователя в других клубах остаются до суточной очистки (часовой лимит отправки — строже, не слабее);
    если у пользователя есть более новый код в другом клубе, старый код его «перекрыл» бы, новый — нет.
  - Варианты: (а) оставить; (б) добавить `club_id` в `transfer_codes` (Q-028) и считать лимиты по аккаунту отдельным
    платформенным запросом (исключение в `sqlc.yaml`). Рекомендация: (б) вместе с Q-028.

- [ ] **L-2. Отправка кода перевода (`FriendTransferCodes::send()`): лимиты 60 с / 5 в час — кто переносит?**
  - Контекст: `send()` (~стр. 32–62) считает коды пользователя во всех клубах; это запрос без `club_id` (нужно исключение в
    `sqlc.yaml` или `app.user_id` + RLS-политика `transfer_codes`, она уже пускает свои коды при `app.user_id`).
  - Сделано: только подтверждение (`billing.ConfirmFriendTransferCode`) и константы `TransferCode*`. Отправка (Telegram) — не перенесена.

- [ ] **L-3. Вход и аутентификация до выбора клуба под RLS.**
  - Контекст: вход клиента/сотрудника ищет членства пользователя во всех клубах; API-ключ и сертификат ПК — по хэшу, клуб ещё не известен.
    Под `zafiro_app` без `app.club_id` таблицы клуба пусты.
  - Сделано: политика `member_self_read` (свои членства при `app.user_id`, `db.Options{UserID}`).
  - Варианты для ключей/сертификатов: узкие запросы через пул `zafiro_platform`; или `SECURITY DEFINER`-функции поиска по хэшу.
    Рекомендация: SECURITY DEFINER-функции (минимальная поверхность, не нужен второй пул в обработчике запроса).

- [ ] **L-4. Бонусы в покупках: выручка или бонусный фонд?**
  - Контекст: бонусы не считаются тратами лояльности (BR-042) и не деньги клуба.
  - Сделано: `billing.Charge` — основной баланс → счёт выручки, бонусы → `bonus_fund` (выручка за время в отчётах = только «живые» деньги).
    Если отчётам нужна «выручка с учётом бонусов», её можно получить суммой обоих счетов.

- [ ] **L-5. Касса: один счёт `cash_drawer` или по способам оплаты?**
  - Контекст: Q-013 (допущение: способ хранится, остаток не разделяется), BR-051.
  - Сделано: один `cash_drawer` на клуб, смена — ссылкой `ledger_transactions.cash_shift_id`, способ — в `meta` и
    `cash_transactions.payment_method`. Разделение на `cash_drawer_cash/card/qr` — после решения Q-013.

- [ ] **L-6. Хранение ключей идемпотентности.**
  - Контекст: `ledger_idempotency` не партиционирована (нужна глобальная уникальность ключа в клубе) и растёт на строку за операцию.
  - Варианты: хранить вечно (≈ 40 байт + индекс на операцию); чистить ключи старше N месяцев (повтор через N месяцев
    станет новой операцией). Рекомендация: хранить 13 месяцев, чистить фоновой задачей ролью владельца (сейчас удаление запрещено триггером).

- [ ] **L-7. Партиции старых журналов (`activity_logs`, `api_request_logs`, `webhook_deliveries`, метрики) — §7 плана.**
  - Сделано: партиционированы только новые таблицы (ledger, аудит). Перевод существующих таблиц — отдельная миграция вместе с ETL
    (`tools/migrate-from-mysql` пишет сразу в партиционированные таблицы). Нужна ли она до первого перевода клуба?

- [ ] **L-8. Роли БД при развёртывании.**
  - Контекст: `0004_rls.sql` создаёт `zafiro_app`/`zafiro_platform` (NOLOGIN), для этого владельцу миграций нужен CREATEROLE.
    Логины (`… LOGIN IN ROLE zafiro_app`) и пароли — секреты окружения, не миграция.
  - Вопрос: в проде миграции запускает отдельная роль-владелец (не суперпользователь)? Тогда при FORCE RLS её data-миграции должны
    выполняться с `SET ROLE zafiro_platform` (владельцу выдать членство). Нужна строка в `docs/dev-setup.md` / Taskfile (не мои файлы).

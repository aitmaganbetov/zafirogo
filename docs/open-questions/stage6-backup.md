# Этап 6, O2 «Резервные копии»: решения и открытые вопросы

Автор: субагент O2. Решения приняты по принципам `docs/DECISIONS.md` (владелец поручил решать самостоятельно);
отменить или изменить может только владелец. Код — `deploy/backup/`, runbook — `docs/runbooks/restore.md`.

## BK-1. pgBackRest или WAL-G

- [x] **Решение: WAL-G v3.0.9** (тег 20.08.2026, коммит `3e493188…`; PostgreSQL 18 в матрице тестов WAL-G).
- **Почему.** Оба умеют базовые копии + архив WAL, дельты, S3, PITR, проверку архива. Решили:
  - WAL-G — один статический Go-бинарник, собирается из исходников закреплённого тега тем же инструментарием, что и
    проект (`CGO_ENABLED=0`, `deploy/backup/Dockerfile`, тег сверяется с коммитом). pgBackRest (C) ставится только
    пакетами ОС (PGDG/Debian), и его версия привязана к репозиторию дистрибутива;
  - шифрование OpenPGP с **асимметричным** ключом (BK-6): на сервере БД только открытый ключ — копии с него не прочитать.
    У pgBackRest шифрование симметричное (`repo-cipher-pass`): без отдельного repo-хоста пароль лежит на сервере БД;
  - проверка целостности: `WALG_VERIFY_PAGE_CHECKSUMS` при копии, `wal-verify integrity timeline` после каждой копии;
    главная проверка — еженедельное восстановление с `pg_amcheck` и денежными инвариантами (BK-9).
- **Чем платим.** У pgBackRest богаче `verify` (проверка всех файлов репозитория без восстановления) и встроенная
  политика full/diff. Компенсируем учениями восстановления.
- **Проверено на практике**: сборка образа по Dockerfile целиком (клонирование тега, проверка коммита, `go build`)
  в отдельном builder'е; копия, дельты, хранение, PITR, восстановление цепочки дельт, отказ `wal-fetch` с открытым ключом.

## BK-2. MinIO для staging недоступен — SeaweedFS

- [x] **Решение: S3 staging — SeaweedFS 4.48** (`chrislusf/seaweedfs:4.48@sha256:4e61d15f…`, релиз 28.09.2026).
- **Контекст.** Задача называла MinIO. MinIO с октября 2025 не публикует community-образы и бинарники (только исходники),
  последний образ — `RELEASE.2025-09-07T16-13-09Z` без последующих исправлений безопасности; в этой среде ни
  `minio/minio`, ни `quay.io/minio/minio`, ни зеркала недоступны (Docker Hub закрыт прокси, в `mirror.gcr.io` образа нет).
  Ставить в staging хранилище без обновлений — против принципа 4.
- **Варианты.** (а) MinIO последнего образа — без исправлений; (б) собирать MinIO из исходников — тяжёлая сборка ради
  staging; (в) SeaweedFS — Apache-2.0, активно выпускается, S3 API с учётками в конфиге, образ доступен.
- **Рекомендация владельцу** — оставить (в). В проде хранилище — внешнее S3 провайдера (BK-4), staging-хранилище
  туда не попадает. Если нужен именно MinIO — заменить сервис `s3` в `compose.backup.yml` (WAL-G не меняется).
- Порог свободного места SeaweedFS — `S3_MIN_FREE_SPACE` (по умолчанию 1 %; на стендах с малым диском — `200MiB`).

## BK-3. Политика хранения

- [x] **Решение**: базовая копия ежедневно (02:17 Астаны), полная раз в 7 дней, остальные — дельты; хранятся 5 полных
  цепочек → **PITR на любую секунду за ≥ 28 суток**; первая копия месяца — постоянная, 12 месяцев; RPO ≤ 1 мин
  (`archive_timeout=60s`).
- **Почему не «7 ежедневных + 4 недельных + PITR 7 дней».** Ошибки в деньгах всплывают при закрытии месяца и сверке
  Z-отчётов, а не за неделю; PITR на 28 суток стоит только места под WAL (зашифрованный zstd). Ledger в базе вечный —
  копии нужны для катастроф, а не как архив операций, поэтому 12 месячных копий достаточно.
- Параметры: `BACKUP_RETAIN_FULL`, `BACKUP_KEEP_MONTHLY`, `WALG_DELTA_MAX_STEPS`, `BACKUP_AT`.
- Наблюдение: WAL-G не берёт дельту от постоянной копии — после пометки месячной копии следующая копия полная.
  Проверено: дальше идут дельты, восстановление цепочки дельт — успешно.

## BK-4. Прод: хранилище, RPO/RTO, горячая реплика

- [ ] **Открыто (инфраструктура владельца).** Где прод-S3: другой регион/провайдер, чем база (обязательно);
  версионирование + Object Lock compliance ≥ 35 суток. Цели: RPO ≤ 1 мин, RTO ≤ 1 ч (инстанс), ≤ 4 ч (регион).
- **Рекомендация**: для RTO в минуты добавить потоковую реплику (hot standby) и переключение — это не бэкап и вне O2,
  но без неё RTO = время восстановления из S3. При управляемом Postgres провайдера — его PITR вместо WAL-G;
  `verify.sql` и `restore-drill.sh` (через DSN) остаются для учений.

## BK-5. Учётки S3

- [x] **Решение**: в проде три учётки — «запись» (сервер БД: `wal-push`, `backup-push`), «чтение» (учения,
  восстановление), «удаление» (только задача хранения, не на сервере БД; при Object Lock удаляет лишь истёкшее).
  В staging — одна учётка SeaweedFS (упрощение стенда).
- [ ] **Открыто (прод-выкладка)**: в staging хранение выполняет сайдкар. В проде сайдкару — `BACKUP_RETENTION=0`, а
  `walg delete retain FULL 5 --confirm` — отдельной задачей с учёткой «удаление» вне сервера БД.

## BK-6. Шифрование

- [x] **Решение**: OpenPGP (RSA 4096, подключ шифрования), на сервере БД — открытый ключ, закрытый — вне площадки
  (runbook §3). libsodium (симметричный) требует cgo и держит ключ на сервере БД — не выбран.
  Обёртка `deploy/backup/bin/walg` не запускает WAL-G без ключа (копии без шифрования невозможны).

## BK-7. Подключение к compose O1

- [x] `deploy/backup/compose.backup.yml` подключается `-f` поверх `deploy/staging/compose.yaml` (и поверх
  `docker-compose.dev.yml` в учениях): меняет образ и команду `postgres`, добавляет сеть `default`, тома
  `postgres-run`/`backup-metrics`/`s3-data`, сервисы `backup`, `s3`, `s3-init`. Проверено на раскладке staging
  (`postgres` + `backup`: архив WAL, первая копия, учения восстановления — зелёные).
- [ ] **Связка, о которой надо помнить (O1)**: `command` переопределяет команду базового файла — параметры staging
  (`max_connections=300`, `shared_buffers=256MB`) повторены в `compose.backup.yml` (`BACKUP_PG_*`). Меняя их в
  `deploy/staging/compose.yaml`, менять и здесь. Рекомендация: в будущем вынести параметры Postgres в общий
  `postgresql.conf`-фрагмент. Имена `postgres` (сервис) и `postgres-data` (том, `/var/lib/postgresql`) — договорённость.
- `task staging:up` без файла бэкапа вернёт обычный образ без архива WAL — на staging с копиями запускать `task backup:up`.

## BK-8. Valkey и NATS

- [x] **Valkey**: AOF (как в staging O1), копий нет; после PITR — `FLUSHALL` (runbook §9, §11). Денег не теряется:
  второй рубеж идемпотентности — в Postgres.
- [x] **NATS**: JetStream file storage; прод — 3 узла, `ZAFIRO_EVENTS_STREAM_REPLICAS=3`; копий нет — источник правды
  `outbox_events`. После PITR поток удаляется и outbox около T переопубликуется; после потери NATS — переопубликация
  последних 15 минут (дедупликация вебхуков по `event_id`).
- [ ] **Открыто (O1/O3)**: прод-значение `ZAFIRO_EVENTS_STREAM_REPLICAS=3` и кластер NATS — в описании прод-выкладки.

## BK-9. Расписание — цикл в сайдкаре, а не Go-воркер

- [x] CLAUDE.md требует фоновые задачи приложения делать воркерами в Go. Бэкап — задача инфраструктуры кластера БД
  (нужен доступ к PGDATA на хосте БД), не приложения: сайдкар `backup` с `backup-scheduler.sh` в compose;
  в Kubernetes — `CronJob` (`concurrencyPolicy: Forbid`) рядом с primary. Один экземпляр на кластер.

## BK-10. Права файлов секретов в compose

- [x] Compose без swarm монтирует секреты файлами хоста без смены владельца; контейнер читает их от uid 999
  (postgres) — файлы 0644 в каталоге 0700 (`gen-secrets.sh`). В проде — менеджер секретов / Kubernetes Secret с
  `defaultMode` и `fsGroup`.

## BK-11. Частичное восстановление одного клуба

- [ ] **Открыто (владелец).** PITR откатывает все клубы. Если испорчены данные одного клуба, точечный перенос из
  PITR-копии рядом (`--keep`) в боевую базу — ручная процедура с риском для ledger (только добавление: исправления —
  компенсирующими операциями). **Рекомендация**: не автоматизировать; при порче одного клуба — компенсирующие
  операции по данным PITR-копии, поднятой рядом, а глобальный PITR — только при массовой порче.

## BK-12. Найдено на практике

- Восстановление падало (`recovery aborted because of insufficient parameter settings`), когда у исходного сервера
  `max_connections=300` (staging), а у восстанавливаемого — 100 по умолчанию. `restore-into.sh` берёт
  `max_connections`, `max_worker_processes`, `max_wal_senders`, `max_prepared_transactions`,
  `max_locks_per_transaction` из `pg_controldata` копии.
- Пароль в выводе `goose` (DSN аргументом) — учения передают DSN через `GOOSE_DBSTRING`.
- Восстановленный кластер запускается с `archive_mode=off`: копия-двойник не должна писать WAL в боевое хранилище.
- Тег `postgres:18.6` пересобран выше по течению: Docker Hub сейчас отдаёт digest `3a426452…`, а staging/dev закреплены
  на `979bccfd…` (локальный, тот же 18.6). Образ бэкапа закреплён на `979bccfd…` — одинаковые glibc/коллации с
  staging. Обновление digest — через Dependabot синхронно в `deploy/staging/compose.yaml` и `deploy/backup/Dockerfile`.
- Один прогон учений из шести упал из-за переполнения диска стенда (`no space left on device` в журнале dockerd в ту же
  секунду) — не дефект скриптов; повторы зелёные.

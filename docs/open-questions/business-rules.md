# Открытые вопросы: бизнес-правила (Этап 0, г1)

К документу [`docs/business-rules.md`](../business-rules.md). Код старого проекта — `/home/user/Zafiro`.
Пока решения нет, при переносе **повторяем старое поведение** (принцип «перенос, а не редизайн»).

- [ ] **OQ-BR-01. Суммы с >2 знаками после точки.**
  Контекст: пополнение (`StoreBalanceTopUpRequest`: `numeric`, `gt:0`), приход/расход (`StoreCashTransactionRequest`: `numeric`, без max),
  открытие смены — принимают любое число знаков; `CashRegisterService` пишет float, MySQL `decimal(…,2)` округляет; бонус считает
  `TopUpBonus::for()` через PHP `round($amount*100)` (с «предокруглением»: 100.005 → 10001).
  Варианты: (а) повторить: принимать и округлять «половина от нуля» по десятичной записи; (б) отклонять >2 знаков валидацией.
  Рекомендация: (б) — проще и безопаснее; совпадение сумм для корректного ввода сохраняется.

- [ ] **OQ-BR-02. Отрицательные балансы и `amountToCents`/`formatCents`.**
  Контекст: `AgentTariffPurchaseService::amountToCents("-1.50") = -50`, `formatCents(-50) = "0.-50"` (BR-001). Может ли в проде быть
  отрицательный `member_balances.balance`? (`Friends::storedCents` прямо говорит «possibly negative».)
  Варианты: повторить ошибку; исправить (корректный знак). Рекомендация: исправить и перед миграцией данных проверить SQL-ом,
  есть ли отрицательные балансы/траты.

- [ ] **OQ-BR-03. Клуб `slug = legacy` с настройками в `storage/app/settings.json`** (`CurrentClub::settings()` стр. 77–79).
  Есть ли такой клуб в проде? Рекомендация: при переносе данных записать содержимое файла в `clubs.settings` и убрать особый случай.

- [ ] **OQ-BR-04. Журнал действий как источник данных.**
  Сейчас журнал определяет лимит продаж тарифа (BR-016), зоны пересадки (BR-035), вид прихода в X/Z-отчёте (BR-057).
  Рекомендация: в Go хранить эти факты в своих таблицах (покупки/ledger, `cash_transactions.kind`), журнал — только аудит;
  при миграции посчитать счётчики/виды из старого журнала. Подтвердите, что лимит продаж — глобальный (не на клиента)
  и что гостевые продажи с кассы его не расходуют.

- [ ] **OQ-BR-05. Где считать «игру на весь баланс» и автобиллинг** (BR-022, BR-023).
  Сейчас — в JS агента (`WindowsAgent/Frontend/main.js`), сервер лишь продаёт N минут. При новом API агента: оставить расчёт в агенте
  или сервер сам покупает минуты по событию «вход/конец тарифа»? Рекомендация: перенести на сервер (меньше доверия клиенту, одна формула),
  формулу `affordableMinutes` сохранить.

- [ ] **OQ-BR-06. Просроченный пакет при попытке запуска** не удаляется (откат транзакции), его чистит суточная задача (BR-024, §15 п. 21).
  Повторять или удалять сразу? Рекомендация: удалять сразу (на деньги не влияет).

- [ ] **OQ-BR-07. Завершение сессий на нескольких ПК с карты** — по транзакции на ПК (не атомарно). Оставить? Рекомендация: оставить
  (ошибка на одном ПК не должна откатывать возвраты на других), но вернуть в ответе список неуспешных.

- [ ] **OQ-BR-08. Печать Z-отчёта перед закрытием смены.**
  Веб требует печать (флаг в сессии), приложение сотрудника — нет (BR-056). Как должно быть в новом UI? Рекомендация: хранить факт печати
  в БД (`cash_shifts.z_printed_at`) и требовать его в вебе, как сейчас; для приложения — как сейчас (без печати).

- [ ] **OQ-BR-09. Лимит сотрудников на смене и «один ПК за раз»** опираются на таблицу web-сессий Laravel и `last_used_at` токенов Sanctum.
  В Go — по активным refresh-сессиям? Должен ли лимит смены распространяться на приложение сотрудника? Рекомендация: по активным
  сессиям панели, приложение — не ограничивать (как сейчас).

- [ ] **OQ-BR-10. Нормализация телефона в панели** не отрезает ведущую `8` (`AuthController::normalizePhone`), в агенте — отрезает.
  Унифицировать (`PhoneNumber::normalize`)? Рекомендация: унифицировать — безопасно.

- [ ] **OQ-BR-11. `saas_plans.features` и лимит `max_computers`.** Лимит читается из `features.max_computers`, но UI сохраняет
  `features` списком строк — лимит не задать. Нужен ли лимит ПК по тарифу платформы? Рекомендация: отдельное поле `max_computers`.

- [ ] **OQ-BR-12. Возврат за время клиенту без строки `member_balances`** теряется, но траты уменьшаются (§15 п. 2).
  Рекомендация: создавать баланс при отсутствии (в Go баланс — производная ledger, проблема исчезает) — подтвердите.

- [ ] **OQ-BR-13. Способ оплаты в кассе.** Наличные/карта/QR не разделяются в остатке смены, POS-продажа без способа оплаты.
  Нужен ли раздельный учёт (и X/Z-отчёт по способам) в Этапе 1, или строго повторить? Рекомендация: хранить способ оплаты в новой
  колонке (для будущих отчётов), остаток и отчёты считать как сейчас.

- [ ] **OQ-BR-14. Удаление зоны** каскадом удаляет ПК с идущими сессиями, а тарифы «только этой зоны» становятся доступны везде (§15 п. 7).
  Рекомендация: запретить удаление зоны с идущими сессиями; тарифы, оставшиеся без зон, выключать (`is_active = false`) — нужно решение владельца.

- [ ] **OQ-BR-15. Пополнения без бонуса и возврат бонуса.** Подтвердите: (а) бонус за пополнение только при пополнении основного
  баланса через кассу; не при пополнении владельцем без кассы; (б) при возврате пополнения бонус забирается в пределах остатка
  бонусного баланса (потраченное не возвращается).

- [ ] **OQ-BR-16. Пересадка и флаг `session_guest`** (§15 п. 16). Рекомендация: при пересадке явно ставить `session_guest = false`
  на целевом ПК и сбрасывать на исходном — это исправление бага, поведение для нормального случая не меняется.

- [ ] **OQ-BR-17. Неиспользуемые настройки** `club.session_idle_timeout`, `club.session_auto_terminate_when_pc_unavailable` — переносить
  (показывать в UI как сейчас) или реализовать/удалить? Рекомендация: перенести как есть (хранение и показ), отметить «не действует».

- [ ] **OQ-BR-18. Вход клиента без указания клуба** выбирает «первое» членство без сортировки (§15 п. 25). Рекомендация: в новом API агента
  клуб всегда известен из сертификата ПК — вопрос закрывается; для моб. приложения — сортировать по `id`.

- [ ] **OQ-BR-19. ПК без токена устройства** позволяет купить время/заказать/пересадить удалённо (§15 п. 10). В новой схеме (mTLS) у каждого
  ПК есть сертификат — проверку «запрос с этого ПК» делать всегда? Рекомендация: всегда.

# Уровни зон (Zafiro 79d014f, 55e3878): решения исполнителя

Решено по принципам `docs/DECISIONS.md` (поручение владельца). Правило — BR-196, сценарии — GS-574, GS-575.

| ID | Вопрос | Решение |
|---|---|---|
| ZL-1 | Тип и ограничения `club_zones.level`: в MySQL `tinyint unsigned` (0…255), форма — 1…99. | `smallint` + `CHECK (level BETWEEN 1 AND 99)` (принцип 4: база держит правило формы). Значение вне диапазона при переносе — ошибка вставки с id строки; старая форма его записать не могла. |
| ZL-2 | Чей уровень сравнивается — зоны покупки или зоны ПК, где сидит клиент? | Как в старом: зоны **исходного ПК** на момент запроса (`$computer->club_zone_id`). Уже пересевший в зону ниже дальше идёт по её уровню. |
| ZL-3 | Карта свободных мест и пересадка могут разойтись. | Одна функция для обоих путей: `billing/service.allowedZones()` → `session.AllowedZones(покупки, ListLevelZoneIDs)`; интеграционный тест проверяет, что на недоступный по карте ПК пересадка отклоняется. |
| ZL-4 | В Blade уровень передаётся в форму через `data-level` кнопки «Редактировать». | В React форма заполняется из данных зоны (`Zone.level` в `GET /api/club-map`), как и остальные поля; атрибута `data-level` нет — проверка Pest `data-level="3"` перенесена как «значение подставляется в поле `#zone-level`». Разметка и классы поля — из Blade без изменений. |
| ZL-5 | `dump-schema.sh` пересобирает и `testdata/demo-data.sql`: фикстура `tools/visual/fixtures/demo.json` изменилась после прошлого дампа (реселлеры и др.), и новые строки ломают `TestMigrateUpstream2026_11`. | В этом блоке закоммичен только пересобранный `schema.sql` (+ колонка `level`); `demo-data.sql` оставлен прежним (вставки перечисляют колонки, `level` — `NULL`). Пересборку демо-данных с правкой ожиданий теста — отдельной задачей. |

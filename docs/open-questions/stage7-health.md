# Вопросы Этапа 7 — загрузка и здоровье ПК на сервере и карте клуба

Новая функция по поручению владельца (в старом Laravel её не было): администратор клуба видит загрузку и здоровье
своих ПК. Агентная часть (сбор измерений) — [`stage7-health-agent.md`](stage7-health-agent.md), протокол —
`proto/agent/v1/agent.proto` (`Status.health`, `ComputerHealth`, не менялся). Здесь — сервер, история, realtime, API и
карта. Описание: `docs/agent-protocol.md` §16, `docs/realtime.md` §4, `docs/schema-changes.md` §14–15, `docs/load-test.md` §6.3–6.4.

Код: `server/internal/agent/health` (пороги, дребезг, журнал), `server/internal/agent/presence/health.go` (снимок),
`server/internal/agent/stream/health.go` и `validate.go` (проверка, живые обновления, пинг),
`server/internal/clubmap/events.go` (`LiveEvents`, `computer.load`), `server/internal/realtime` (`live.club.>`),
`server/internal/http/sections/clubmap/health.go`, `db/migrations/0030_computer_health_events.sql`,
`db/queries/computer_health.sql`, `web/src/features/clubmap/ComputerHealth.tsx`, `healthText.ts`; история по часам и
неделям — `agent/health/hourly.go`, `hourly_flush.go`, `verdict.go`, `http/sections/clubmap/health_history.go`,
`db/migrations/0031_computer_health_hourly.sql`, `db/queries/computer_health_hourly.sql`, `web/src/features/clubmap/HealthChart.tsx`,
`liveSeries.ts`.

Решения приняты по принципам `docs/DECISIONS.md` (владелец поручил решать самому); отменить может только владелец.

## Принятые решения (подтвердить)

- [x] **S7-H-1. Проблемы считает сервер.** Агент шлёт только измерения; пороги — `agent.health.*` (одинаковы для всех ПК,
  меняются без выпуска агента). Значения по умолчанию — как поручено: CPU ≥ 90 °C, GPU ≥ 85 °C; системный диск —
  свободно < 10 % или < 10 ГБ; другой диск — < 5 %; SMART warning/failing; мышь/клавиатура/монитор не подключены
  (гарнитура — нет: её часто снимают и уносят, это не неисправность); скорость сети < 1000 Мбит/с, если на этом
  подключении была ≥ 1000, или < 100 всегда; нестабилен — ≥ 3 внезапных выключений или ≥ 1 «синего экрана» за 7 суток.
  Сравнения дисков — целыми (free·100 < total·percent), без float. Уточнение: вид периферии, которого нет в списке агента,
  — «не измерено», а не «не подключено» (S7-HA-9 агента: сбой источника не даёт ложной тревоги); несколько устройств
  одного вида — проблема, только если не подключено ни одно.
- [x] **S7-H-2. Дребезг: время + гистерезис температуры.** Проблема попадает в историю, продержавшись
  `agent.health.raise_after` (2 мин), и снимается, отсутствуя `clear_after` (5 мин); мигание сбрасывает отсчёт.
  Перегрев снимается, только когда температура ниже порога на `temp_hysteresis_c` (5 °C). Переход фиксируется только
  после записи в журнал — сбой Postgres не теряет его (повтор на следующем измерении). Отсчёт идёт по измерениям
  (Status с health раз в `status_interval`), поэтому фактическая задержка — `raise_after` + до одного интервала.
- [x] **S7-H-3. Открытые проблемы переживают переподключение и офлайн.** При первом health нового подключения открытые
  проблемы читаются из журнала (одна выборка по частичному индексу на подключение; ПК со старым агентом в журнал не
  ходят) — повторной строки нет. Офлайн проблему не закрывает: иначе каждая перезагрузка ПК (дольше
  `offline_grace`) давала бы пару «ушла/появилась». Для упавшей скорости сети прежняя «полная» скорость
  восстанавливается из `details.previous_mbps`. Наибольшая скорость сети в остальном — память подключения (после
  перезагрузки ПК, поднявшегося сразу на 100 Мбит/с, сработает только правило «< 100»).
- [x] **S7-H-4. История — только переходы, помесячные партиции, срок 90 дней.** `computer_health_events` (0030): строка
  на появление, `cleared_at` — на уход; партиции по `raised_at`, удаление по сроку `agent.health.event_retention`
  (90 дней — как `api_request_logs`) той же задачей `logs:retention`. Проблема, открытая дольше срока, уходит с
  партицией; у ПК в сети она будет записана снова. Права: пул клуба — SELECT, INSERT и UPDATE только `cleared_at`
  (подменить или удалить историю нельзя), платформа — SELECT. Уникальность «одна открытая проблема вида у ПК» —
  `INSERT … WHERE NOT EXISTS` (уникальный индекс партиционированной таблицы обязан включать `raised_at`).
- [x] **S7-H-5. Неверное health отбрасывается целиком, Status принимается.** Температуры −50..150 °C (0 — не измерено),
  доли ≤ 10000, ≤ 26 дисков (точка монтирования 1–16 символов), ≤ 16 устройств, название ≤ 128 символов; запрещены
  управляющие символы и переключатели направления письма (U+202A–202E, U+2066–2069, U+200E/F — подмена отображаемого
  имени); free ≤ total ≤ 1 ПиБ (защита от переполнения целочисленных сравнений). Неизвестный вид периферии или
  состояние SMART (агент новее сервера) — пропускается / «не измерено», а не ошибка. Счётчик —
  `Service.HealthDropped()`.
- [x] **S7-H-6. Срочный health не режется ограничением частоты Status (S7-HA-2).** Status, где сменились подключение
  периферии, её набор или SMART диска (`presence.HealthChanged`), принимается даже внутри `MinStatusGap` (2 с) и сразу
  уходит в снимок и живым обновлением. Только температура, загрузка или место на диске внутри окна — отбрасываются, как
  прежде. `presence.State.Significant` не расширен: он запускает событие `computer.state` через outbox (запись в
  Postgres), а изменения здоровья идут без Postgres (S7-H-7).
- [x] **S7-H-7. Живые обновления — core NATS, без outbox.** Событие `computer.load` (`docs/realtime.md`) публикуется в
  `live.club.<club>.computer.load` (не пересекается с потоком JetStream `club.>` — не сохраняется), хаб каждого
  инстанса раздаёт его сотрудникам с правом `club_map.view`. Частота: не чаще `live_min_gap` (15 с) на ПК и только при
  заметном изменении (±5 п.п. CPU/ОЗУ, ±2 °C CPU/GPU, появление/пропажа данных); смена набора проблем, периферии или
  SMART — сразу. Доставка «не более одного раза», как у остальных событий: после переподключения экран перечитывается.
  Служебное `staff.access_changed` по живому каналу не принимается.
- [x] **S7-H-8. Пинг — мгновенная команда Ping раз в минуту.** Время от постановки Ping в очередь стрима до
  `CommandResult` (включает обработку агентом — это «отклик агента», а не чистый RTT сети). Первый Ping — через
  `ping_interval` после подключения (не добавлять сообщений в шторм переподключений); значение попадает в снимок с
  ближайшим Status. 5 000 ПК — 83 сообщения/с в обе стороны. `ping_interval: 0` — выключено. Заодно агент сверяет часы
  (Ping.server_time), как было задумано протоколом.
- [x] **S7-H-9. API и права.** `GET /api/club-computers/{id}/health` и `…/health/events` (keyset, `cursor`/`limit`) — право
  `club_map.view` (маршрут `club-map.state`, как у состояния карты); клуб — из аутентификации, чужой ПК — 404. Карта
  (`/api/club-map`, `/api/club-map/state`) получила необязательные поля `load`, `problems`, `rtt_ms` — только у ПК в сети
  с новым агентом; у остальных полей нет (ответ для старых ПК не изменился). Маршрут `…/health` использует сквозной тест
  агента .NET (`Здоровье_ПК_доходит_до_сервера`).

- [x] **S7-H-13. История по часам: агрегат в Valkey, одна строка на ПК и час.** Поручение владельца: в панели ПК —
  состояние в реальном времени и по неделям, чтобы решать о ремонте, замене или наблюдении. Каждый Status в Postgres не
  пишется (CLAUDE.md «Производительность»): агрегат часа (min/avg/max загрузки и температур, минимум свободного места
  системного диска, худший SMART, минуты онлайн и в сессии, отключения периферии, прирост внезапных выключений и «синих
  экранов») — в Valkey по ключу «ПК + час», одним Lua-скриптом на Status. Valkey, а не память инстанса: ПК переезжает между
  инстансами посреди часа (перебалансировка) — агрегат не теряется и не дублируется. Сброс — задача `agent:health-hourly`
  раз в минуту под advisory lock (один исполнитель, Q-086), через 5 мин после конца часа (Status последних секунд часа
  успевает дописаться с любого инстанса); UPSERT по (`club_id`, `computer_id`, `hour`) — повтор идемпотентен; ключи Valkey
  удаляются только после записи (TTL 26 ч на случай аварии). Средние — целым делением, без float. Почему не «сырые»
  Status в Postgres: 5 000 ПК — 7,2 млн строк в сутки против 120 тыс.; почему не память инстанса с записью при переезде —
  переезд при падении инстанса терял бы час. Час — UTC (пояса Казахстана — целые часы; для поясов с получасом недели
  считаются по часам UTC — расхождение на полчаса на границе недели).
- [x] **S7-H-14. Срок хранения почасовой истории — 180 дней** (`agent.health.hourly_retention`, ≥ 14 суток): полгода
  достаточно, чтобы видеть деградацию (рост температуры, учащение сбоев) и сравнивать сезоны; дольше истории проблем
  (90 дней), потому что строки компактны (≈ 226 байт; 5 000 ПК ≈ 2,4 ГБ за 180 дней при 12 ч в сети в сутки,
  `docs/load-test.md` §6.4). Удаление — DROP месячных партиций той же задачей `logs:retention`.
- [x] **S7-H-15. Вердикт за неделю считает сервер по прозрачным правилам** (`health.Judge`, `docs/agent-protocol.md`
  §16.7, пороги `agent.health.verdict_*` и пороги проблем): «Требует ремонта» — SMART `failing` или ≥ 1 «синего экрана»
  за неделю, или перегрев больше 24 ч в неделю (хронический — нужна чистка/термопаста); «Наблюдать» — перегрев больше 2 ч,
  SMART `warning`, ≥ 3 внезапных выключений, системный диск < 10 %, рост средней температуры к прошлой неделе на ≥ 5 °C;
  иначе «Исправен». Уровень — наихудший из причин, каждая причина — код и числа (значение, порог) для текста-перевода.
  Внезапные выключения — «наблюдать», а не «ремонт»: их частая причина — отключение питания в клубе, а не ПК. Диск —
  «наблюдать»: место освобождается уборкой, не ремонтом. Порог часов перегрева — по часам с максимумом ≥ порога проблемы
  (`cpu_temp_c` 90 / `gpu_temp_c` 85), чтобы вердикт и колокольчик говорили об одном.
- [x] **S7-H-16. Недели в поясе клуба, только с данными; живой график — в браузере.** Неделя — с понедельника 00:00 по
  поясу клуба (`clubs.timezone`, как остальные отчёты); границы считает сервер, выборка — диапазоном по `hour`. Недели без
  данных (ПК не включали) не показываются; по умолчанию 8 недель, не больше 12; график недели — точки по часам (≤ 8 суток
  за запрос). Живой график 15 минут копится в браузере из событий `computer.load` (в событие добавлены `cpu_temp_deci`,
  `gpu_temp_deci`) — без нового серверного хранения.

- [x] **S7-H-18. Бездисковые ПК: без дисков, сеть строже** (замечание владельца «Диски зачем, если бездисковая
  система?»; описание — `docs/agent-protocol.md` §16.9).
  - *Признак — сертификат, а не самоотчёт агента.* `agent_certificates.diskless` (выпущен по ключу образа, Q-037) уже
    есть: стрим берёт сертификат своего подключения (подзапрос по первичному ключу в `GetAgentComputer` — тот же запрос
    Hello, без лишнего обращения к БД при шторме переподключений), API — последний выпущенный сертификат ПК (по
    `issued_at`, а не по `not_after`: прежний сертификат по коду живёт год и отозван при переводе на образ). Новой
    колонки и миграции не нужно; признак есть и у ПК не в сети. `DeviceInfo.diskless` (настройка агента) решает только,
    что собирает агент: ПК с `Diskless` в настройке, но сертификатом по коду, — просто без дисков в данных.
  - *Диски у бездискового не оцениваются нигде:* сервер отбрасывает присланные диски (старый агент, тома образа iSCSI /
    RAM-диск кэша), проблем `disk_low`/`disk_smart`, системного диска и SMART в почасовой истории и причин вердикта по
    дискам нет; часы с проблемами дисков (из истории до перевода) в «часы с проблемами» не входят. Открытые проблемы
    дисков снимутся обычным `clear_after` после переподключения.
  - *Сеть — строже, отклик — нет.* У бездискового ПК система и игры грузятся по сети: 100 Мбит/с — это минуты загрузки
    игры, поэтому `network_slow` — при скорости ниже `link_full_mbps` (1000) всегда (у обычного — только после падения
    с ≥ 1000 или ниже 100). В вердикт недели (только у бездискового) — причина `network_slow`, «наблюдать», если часов с
    открытой `network_slow` больше `verdict_network_slow_hours` (2, как часы перегрева): чаще всего виноват кабель или
    порт коммутатора, а не ПК, — это не «ремонт». У обычного ПК медленная сеть в вердикт не входит (о ПК она не говорит).
    Отклик агента (`rtt_ms`, S7-H-8) строже не считаем: он идёт через облачный сервер — это интернет клуба и обработка
    агентом, а не путь до сервера образов в LAN; порог по нему тревожил бы из-за интернета.
  - *Панель:* пометка «Бездисковый ПК» вместо строк дисков и SMART (обе вкладки), «Сеть» — сразу после проблем, в
    сводке недели — «Медленная сеть: N ч», подпись проблемы — «Медленная сеть» (а не «упала»), проблемы дисков в
    «Истории проблем» не показываются. Без новых CSS-классов (`cm-info-list`).
  - Тесты: `health/health_test.go` `TestEvaluateDiskless`, `verdict_test.go` (`diskless: …`), `hourly_test.go`
    `TestDiskFactsDiskless`, `stream/health_integration_test.go` `TestHealthDisklessIgnoresDisks`,
    `http/clubmap_health_weekly_integration_test.go` `TestClubMapComputerHealthDiskless`, `ClubMapPage.test.tsx`
    («hides disks of a diskless PC in both tabs»).

## Осознанное отличие от старого дизайна (CLAUDE.md «Фронтенд»)

- [x] **S7-H-10. Карточка ПК на карте и панель «Информация о ПК».** На карточке ПК в сети с новым агентом — две полоски
  2 px внизу (CPU — зелёная, ОЗУ — голубая; ширина — процент) и круглый значок ⚠ в левом верхнем углу с подсказкой-
  списком проблем (правый угол занят кнопкой правки в редакторе); в подсказке карточки — «CPU N % · ОЗУ M %». В панели —
  разделы «Состояние» (тот же `cm-info-list`, проблемные строки — `cm-info-warning`) и «История проблем» (кнопка
  «Показать ещё»). Новые классы — только используемые (`cm-pc-load`, `cm-pc-alert`, `cm-info-more`). Без данных (ПК офлайн,
  старый агент, демо-данные визуального сравнения) разметка карточки и панели та же, что в старом шаблоне — проверено
  тестами (`ClubMapPage.test.tsx`: «renders the same PC markup without agent data», «shows no state sections…») и
  прогоном `task visual -- --page club-map`.
- [x] **S7-H-17. Вкладки «Сейчас» / «По неделям» в разделе «Состояние».** Кнопки вкладок и кнопки недель — существующий
  класс `cm-info-more` (без новых CSS); недели — тот же `cm-info-list` (вердикт «наблюдать»/«ремонт» — `cm-info-warning`);
  графики — `<canvas>` Chart.js без новых классов (высоту задаёт соотношение сторон Chart.js). Вкладки — только если есть
  и живое состояние, и недели; без данных разметка панели прежняя (`ClubMapPage.test.tsx`).

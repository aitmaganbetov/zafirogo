# Вопросы Этапа 1: пакеты `cash` и `stock` (чистые расчёты)

Пакеты: `server/internal/cash`, `server/internal/stock`. Старый код: `app/Services/CashRegisterService.php`,
`app/Services/ShiftReport.php`, `app/Services/StaffShifts.php`, `app/Http/Controllers/CashRegisterController.php`,
`app/Http/Controllers/Api/Staff/CashController.php`, `app/Actions/AdjustStockAction.php`, `CreateProductAction.php`,
`UpdateProductAction.php`. Код, который зависит от ответа, помечен `CQ-N` в комментарии.

- [ ] **CQ-1. Сумма, которая проходит `gt:0`, но округляется до 0.00 (`"0.001"`): отклонять?**
  - Контекст: `StoreBalanceTopUpRequest` / `StoreCashTransactionRequest` — `numeric|gt:0`; Laravel 13 сравнивает точно
    (brick/math), `"0.001" > 0` — правило проходит; MySQL записывает `0.00`. Старый код создавал пополнение/приход на 0.00.
    Ledger (`ledger/post.go`) не принимает нулевых проводок.
  - Сейчас: `ParseTopUpAmount` / `ParseTransactionAmount` возвращают ошибку правила `gt` поля `amount` (отступление).
  - Рекомендация: оставить отказ.

- [ ] **CQ-2. Сумма больше `decimal(14,2)` в приходе/расходе и начальном остатке смены.**
  - Контекст: `StoreCashTransactionRequest` и `OpenCashShiftRequest` без верхней границы; в старом коде — ошибка MySQL 1264 (500).
  - Сейчас: ошибка правила `max` (`MaxShiftAmount` = 999 999 999 999.99 ₸), как советует BR-054.
  - Рекомендация: оставить.

- [ ] **CQ-3. «В кассе недостаточно средств»: сравнивать во float, как PHP, или точно?**
  - Контекст: `CashRegisterService::transact()` и `refund()` сравнивают `(float) $amount > (float) opening + income − expense`.
    Пример: остаток 0.30 + приход 0.60 = `0.8999999999999999` во float — расход 0.90 отклоняется, хотя точный остаток 0.90
    (проверено `php -r`). Ещё: расход `"200.004"` при остатке 200.00 отклоняется (сравнивается строка до округления),
    хотя в БД легло бы 200.00.
  - Сейчас: повторено буквально (`Totals.BalanceFloat()`, `TestExpenseFloatComparison`).
  - Варианты: (а) оставить float (полная совместимость); (б) точное сравнение тиынов (`amount > Balance()`).
  - Рекомендация: (б) — разница только на «копеечных» границах и в пользу кассира; но это отступление — решение владельца.

- [ ] **CQ-4. Бонус за пополнение считается не от записанной суммы, а от `(int) round($amount * 100)`.**
  - Контекст: `TopUpBonus::for((float) $amount)` берёт `(int) round($amount*100)` (PHP-округление), а баланс получает
    `(string) $float` (precision 14), округлённую MySQL. Они расходятся только на вводе с > 14 значащими цифрами:
    `"0.0149999999999999"` → баланс +0.02, база бонуса 1 тиын.
  - Сейчас: `ParseTopUpAmount` отдаёт обе суммы (`Amount`, `BonusBase`), `PlanTopUp` передаёт в `BonusFunc` именно `BonusBase`.
  - Для подключения: `billing.TopUp` вызывает `p.Bonus(p.Amount)` — при связке передавать уже посчитанный бонус
    (или функцию, которая игнорирует аргумент), иначе база будет `Amount`. Владельцу решать нечего, это задача следующего шага;
    вопрос — нужно ли вообще повторять такую точность (рекомендация: да, это дёшево).

- [ ] **CQ-5. Описания операций кассы переводятся в момент записи.**
  - Контекст: `description` пополнения (`__('Пополнение :balance: :user (:payment)')`) и возврата (`__('Возврат по чеку №:number')`)
    пишутся в БД уже переведёнными — на языке сотрудника. CLAUDE.md: данные из БД через `t()` не пропускать.
  - Сейчас: `TopUpDescription`, `RefundDescription` дают русский текст.
  - Варианты: (а) хранить русский текст (как в старом по умолчанию); (б) хранить ключ + параметры и переводить при показе.
  - Рекомендация: (б) для новых записей (описание = данные + вид операции), русский текст — для перенесённых.

- [ ] **CQ-6. Порядок сотрудников с равным приходом в X/Z-отчёте.**
  - Контекст: `ShiftReport::for()` — `GROUP BY user_id` без `ORDER BY`, затем устойчивый `sortByDesc('income')`. Порядок
    групп в MySQL не определён.
  - Сейчас: при равном приходе — по `user_id` возрастанию (NULL первым). Рекомендация: так и закрепить (`ORDER BY income DESC, user_id`).

- [ ] **CQ-7. Сортировка «Продано товаров» по float-сумме.**
  - Контекст: `usort` по `(float)` сумме строк: `0.10 × 3 = 0.30000000000000004` больше `0.30 × 1`, поэтому товар «Б» встаёт раньше
    «А» при равных точных суммах (`TestReportItemsSortedByFloatAmount`). Сейчас повторено буквально. После коммита `fab81f2`
    сумма товара в Blade не показывается (вместо неё остаток), но остаётся в API приложения сотрудника и в порядке строк.
  - Рекомендация: можно перейти на точные суммы (сортировка по тиынам, затем по имени) — различие только при равных суммах.

- [ ] **CQ-8. Приход с описанием «Продажа POS» из формы «Приход/расход».**
  - Контекст: вид «Продажа товаров» определяется по `description = 'Продажа POS'`; `transact()` описание не фильтрует —
    такой ручной приход попадёт в «Продажа товаров» (но не в товары и не в возвраты). Сейчас повторено.
  - Рекомендация: в новой схеме вид прихода — отдельное поле (OQ-BR-04), и продажу определять по нему, а не по тексту.

- [ ] **CQ-9. Возврат старого чека без `product_id`: товар ищется по имени (`->where('name', …)->first()`).**
  - Контекст: при нескольких товарах с одним именем `first()` без `ORDER BY` — не определено. Сейчас `SaleStockReturns`
    отдаёт имя, выбор товара — у вызывающего; в тестовой модели — наименьший `id`. Рекомендация: при переносе данных
    проставить `product_id` в старые чеки, где имя однозначно.

## Расхождения документов с кодом (для владельцев документов)

- `docs/business-rules.md` BR-073: «`substr(sku, 0, 200)`» — в коде `mb_substr` (по символам), `ProductDeleteController.php` ~стр. 22.
- `docs/golden-scenarios.md`, «Единицы»: «float-код кассы в Go заменяется целочисленной арифметикой с тем же результатом» —
  противоречит CLAUDE.md («формулы переносить буквально»). Сделано буквально (float + PHP/MySQL-округление); property-тесты
  показывают, что на суммах `decimal(14,2)` результат совпадает с целочисленным (`TestSaleFloatTotalMatchesExact`,
  `TestReportFloatPathsMatchExact`) — кроме сравнений из CQ-3.
- `server/internal/money/rounded.go`, комментарий к `ParseTengeRounded`: «PHP-float, привязанный PDO-параметром, уходит строкой
  кратчайшего представления (serialize_precision = -1)» — противоречит `PHPFloatString` / `FromTengeFloatDecimal` (precision 14).
  `php -r 'var_dump((string)0.0149999999999999)'` → `"0.015"`, т.е. precision 14; касса использует `FromTengeFloatDecimal`.
- MQ-1 (версия PHP): `composer.lock` старого проекта — `laravel/framework v13.35.0`, и `tools/php-oracle/run.sh` пишет, что
  lock требует PHP ≥ 8.4. Значит, прод почти наверняка на 8.4+, а `money.PHPRound` повторяет 8.3 — проверить с агентом `money`.
- BR-052: «Скидок в POS нет (поле `discount_amount` в отчёте — наследие, всегда 0)» — подтверждено; в отчёте поле сохранено (`Report.Discount`).

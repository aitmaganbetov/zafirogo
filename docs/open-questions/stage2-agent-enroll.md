# Этап 2, A2 — регистрация ПК и mTLS: вопросы

Реализация — `docs/agent-protocol.md` §12. Код: `server/internal/pki`, `server/internal/agent/enroll`,

## 1. Бездисковые ПК (Q-037) — решено

- [x] **Как бездисковый ПК получает сертификат после каждой перезагрузки?**
  - Решение (30.10.2026, docs/DECISIONS.md Q-037): вариант (а) — «ключ образа» клуба. Многоразовый ключ (хранится
    хэш, отзываемый, с ограничением подсети); ПК с известным MAC получает сертификат автоматически, новый MAC
    попадает в «ожидающие» и требует подтверждения сотрудником; сертификат таких ПК — 24 ч.
  - Сделано (Q-037): миграция `0013_agent_image_keys.sql` (ключи образа, ожидающие ПК, `agent_certificates.diskless`),
    `server/internal/agent/enroll/image_key.go`, поле `EnrollRequest.image_key` и `ERROR_CODE_PENDING_APPROVAL`
    в proto, протокол — `docs/agent-protocol.md` §12.8. Ключи создают и отзывают owner/admin (как ключ установки
    клуба в старом), подтверждают ПК — роли кодов регистрации. REST панели и экран — при переносе экрана ПК.
    Вариант (б) (TPM) не делается. Пункт «Сделано: только базовый путь» ниже — история до решения.
  - Контекст: сейчас служба бездискового ПК после загрузки сама получает токен по многоразовому ключу установки
    клуба + UUID + MAC, неизвестные ПК добавляются в «Не назначена» (`app/Http/Controllers/Api/AgentEnrollController.php`,
    `WindowsAgent/ZafiroAgent/Service/VaultServer.cs` `EnrollAsync`). В новом протоколе ключ и сертификат живут на ПК;
    на бездисковом ПК (CCBoot, iCafe8 и т.п.) локальные изменения пропадают при перезагрузке, а одноразовый код
    пришлось бы вводить каждый раз.
  - Сделано: только базовый путь — одноразовый код. Флаг `DeviceInfo.diskless` сервер пока **игнорирует**
    (сертификат обычный, 30 дней). Ничего из вариантов ниже не реализовано.
  - Варианты:
    - **(а) «Код образа» клуба** — многоразовый секрет (≥ 128 бит, не 8 символов), выдаёт только владелец, хранится
      хешем, отзывается кнопкой. Ограничения: (1) регистрация известных MAC проходит сразу, **новый MAC** — только
      после подтверждения в панели (или в окне N минут после нажатия «Добавить ПК по образу»); (2) опционально —
      белый список подсетей/внешних IP клуба; (3) сертификат короткий (24 ч) и с пометкой `diskless`;
      (4) лимиты как `agent-enroll`. Плюсы: работает с любым бездисковым решением. Минусы: секрет лежит в образе —
      утечка образа = возможность выдать себя за ПК клуба с известным MAC (MAC подделывается).
    - **(б) Ключ в TPM 2.0** — при первичной регистрации по одноразовому коду ключ создаётся в TPM ПК (переживает
      перезагрузку, т.к. TPM на материнской плате), сервер запоминает открытый ключ (SPKI) карточки. После загрузки
      агент шлёт CSR тем же ключом TPM → сервер выдаёт сертификат без кода, если SPKI совпадает с карточкой.
      Плюсы: секрета в образе нет, ключ неизвлекаем. Минусы: TPM 2.0 есть не у всех ПК клубов (нужна статистика),
      CNG-имя ключа хранится в профиле/реестре — его тоже надо держать вне образа (можно искать ключ по сертификату
      в TPM); сложнее поддержка.
    - **(в) Персистентное хранилище бездисковой системы** — у части решений есть per-client «личный диск» или
      writeback, переживающий перезагрузку: ключ (программный CNG, экспорт запрещён) и сертификат кладутся туда.
      Плюсы: ничего нового на сервере. Минусы: зависит от конкретного продукта и его настройки в клубе.
  - Рекомендация: (б) там, где есть TPM, плюс (а) с обязательным подтверждением новых MAC как запасной путь.
    Нужен список бездисковых решений и доля ПК с TPM 2.0 в клубах.
  - Решение (30.10.2026): по DECISIONS Q-037 — «ключ образа» клуба (вариант (а)): хэш, отзыв, ограничение подсети, подтверждение новых MAC сотрудником, сертификат 24 ч.

## 2. Формат идентичности в сертификате

- [x] **CN `computer:<id>` или `pc-<id>`?**
  - Контекст: ТЗ Этапа 2 задаёт `SAN/CN = computer:<id>`; `enrollment.proto` (комментарий к `certificate_pem`) и
    `docs/agent-protocol.md` §3 — `CN=pc-<computer_id>`, `O=club-<club_id>`.
  - Сделано: `CN=computer:<id>`, `O=club:<club_id>`, SAN URI `zafiro://club/<club_id>/computer/<id>` (как в §3).
    Идентичность сервер берёт из SAN URI, CN только сверяет. Агенту формат CN не важен.
  - Рекомендация: оставить как сделано и поправить комментарий в `enrollment.proto` и §3 (не мои файлы).
  - Решение (30.10.2026): сделано: формат `CN=computer:<id>` оставлен, proto и документация приведены к коду (stage-2-report).

## 3. Права

- [x] **Кто выдаёт код, отключает и перерегистрирует ПК?**
  - Контекст: в Laravel регистрация ПК — не право матрицы `ClubPermissions`, а роль: `ClubComputerPolicy::register()`
    → `ClubComputerSessions::STAFF_ROLES = owner, admin, manager, operator` (кассир — нет). «Отключить ПК» в старом
    проекте нет (токен устройства сотрудник не отзывал). Удаление карточки — право `club_map.delete`.
  - Сделано: выдача кода, «Перерегистрировать», «Отключить ПК», отмена и список кодов — роли STAFF_ROLES и не режим
    просмотра суперадмином (`enroll.CanRegister`).
  - Вариант: привязать к матрице (`club_map.create` — подключить, `club_map.delete` — отключить), чтобы владелец мог
    настраивать в «Права». Рекомендация: оставить роль (как в старом) до решения.
  - Решение (30.10.2026): по DECISIONS «Коды регистрации» — по роли, как в старом (owner, admin, manager, operator).

## 5. Истёкший сертификат — ошибка TLS, а не gRPC

- [x] **Нужен ли агенту ответ `CERTIFICATE_EXPIRED` при подключении с уже истёкшим сертификатом?**
  - Контекст: по ТЗ `ClientAuth = VerifyClientCertIfGiven` — Go отклоняет истёкший/чужой сертификат на рукопожатии,
    агент видит обрыв TLS (`UNAVAILABLE`). `CERTIFICATE_EXPIRED` приходит только когда сертификат истёк за время
    жизни соединения.
  - Вариант: `RequestClientCert` и полная проверка в перехватчике — тогда любой отказ приходит кодом gRPC.
  - Рекомендация: оставить; агент знает свой `not_after` и при истечении сам идёт в `Enroll`.
  - Решение (30.10.2026): принята рекомендация: оставить; агент сам идёт в `Enroll` по `not_after`.

## 6. Перерегистрация карточки с новым железом

- [x] **Менять ли MAC карточки при перерегистрации на другой ПК?**
  - Контекст: код «Перерегистрировать» привязан к карточке; как в `ClubComputerRegistrar::adoptMac()`, MAC пишется
    только в пустое поле. Если ПК заменили (другой MAC), карточка сохранит старый MAC, и следующий Enroll «новым ПК»
    по MAC создаст отдельную карточку.
  - Варианты: (а) как сейчас; (б) код перерегистрации перезаписывает MAC и device_id карточки (если MAC не занят
    другой карточкой клуба). Рекомендация: (б) — это и есть сценарий «заменили ПК на месте».
  - Решение (30.10.2026): принята рекомендация: (б) код перерегистрации перезаписывает MAC и device_id, если MAC не занят другой карточкой.

# Этап 4, H4 — безопасность и эксплуатация: решения по ходу работы

Решено самостоятельно по принципам `docs/DECISIONS.md` (владелец поручил); пересмотреть можно без переделки схемы.

## H4-1. Один ключ шифрования данных вместо `superadmin.secret_key`

- **Контекст.** Этап 3 (G6) шифровал токены Telegram ключом `superadmin.secret_key` (формат `v1:`, без id ключа,
  ротация невозможна). Q-050 требует шифровать и секреты вебхуков клубов.
- **Решение.** Общая связка `security.data_keys` (`kid:секрет`, первый шифрует, остальные расшифровывают) для всех
  секретов в базе; формат `v2:<kid>:…`. `superadmin.secret_key` остаётся только для расшифровки старых `v1`
  (воркер `reencrypt-secrets` перешифровывает их), в dev больше не генерируется. В prod `security.data_keys`
  обязателен (ошибка запуска без него) — секреты вебхуков без ключа выдать нельзя.
- **Вариант, который отвергнут:** отдельный ключ на каждый вид секрета — больше конфигурации без выигрыша: контекст
  (associated data) и так не даёт переставлять шифротексты между местами хранения.

## H4-2. Адрес установщика агента и выпуски CI

- **Контекст.** Кабинет суперадмина берёт установщик по шаблону старого проекта
  `https://github.com/aitmaganbetov/Zafiro/releases/download/agent-v{version}/ZafiroAgentSetup-{version}.exe`
  (`AgentUpdate::INSTALLER_URL`, `superadmin/release.go`) и манифест — `<установщик>.update.json` рядом. Агент C# ещё
  собирается в старом репозитории.
- **Решение.** `.github/workflows/agent-release.yml` (этот репозиторий) подписывает установщик, скачанный по https,
  и публикует установщик + манифест в выпуск `agent-v<версия>` **этого** репозитория. Пока шаблон в кабинете указывает
  на старый репозиторий, манифест нужно приложить к выпуску там же (вручную, `gh release upload`), либо перенести
  шаблон на этот репозиторий, когда агент переедет сюда (одна строка `installerURL`).
- **Рекомендация владельцу.** При переносе агента сделать шаблон адреса настройкой (`agent.update.installer_url`) и
  собирать установщик в этом workflow (шаг «Установщик» уже вынесен).

## H4-3. Какие строки сервера считаются ключами перевода

- **Контекст.** Проверка «каждый ключ переведён» (`server/internal/i18n/coverage_test.go`) должна знать ключи
  сервера, а у сервера нет единой функции-обёртки: тексты ошибок переводятся по самому русскому тексту
  (`httpx.ResponseError`, `d.T`), ошибки агента — на стороне агента.
- **Решение.** Ключи сервера — все русские строковые литералы Go (разбор `go/ast`, без комментариев) вне `cmd/`,
  `internal/config`, `internal/app` (тексты для оператора) и сгенерированного кода, кроме фрагментов склеиваемых
  описаний (пробел/знак на краю, глаголы `fmt`) и явного списка маркеров данных (`notKeys` с причиной, например
  «Продажа POS», «Заказ из агента» — CLAUDE.md «Данные из БД и маркеры для сравнений через `t()` не пропускать»).
  Ключи фронта — литералы `t('…')`. Новые переводы — `db/seed/translations-new.{ru,kk,en}.json`, импорт —
  `import-translations -seed` (по умолчанию `../db/seed`); строки старого файла важнее.
- **Следствие.** Новая русская строка без перевода валит job `translations` в CI — перевод добавляется в те же три
  файла (тест `TestSeedTranslations` проверяет подстановки и число форм: ru — 3, kk — 1, en — 2).

## H4-4. Error pages: «Forbidden», «Not Found», «Server Error»

- Старый проект показывал стандартные страницы Laravel с английскими заголовками на всех языках (в
  `database/translations` их нет). В новых переводах ru оставлен как есть (ключ), kk переведён («Қолжетімділік жоқ»,
  «Табылмады», «Сервер қатесі»), en — как в Laravel. Это расширение, а не изменение поведения для ru.

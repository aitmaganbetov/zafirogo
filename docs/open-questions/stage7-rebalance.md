# Этап 7: перебалансировка потоков агентов (S6-O4-12)

Решения приняты по принципам `docs/DECISIONS.md` (приоритет — безопасность и незаметность для гостя, затем скорость).
Описание механизма — `docs/agent-protocol.md` §13.6, код — `server/internal/agent/stream/rebalance.go`.

- [x] **R-1. Механизм переподключения — существующий `Command.drain`, агент не меняется.** Агент
  (`agent/src/Zafiro.Agent.Core/Runtime/AgentRuntime.cs`, `case Command.KindOneofCase.Drain`) закрывает стрим, затем
  `RunStreamAsync` освобождает канал (`channel.Dispose()`), и через `Backoff.Drain` (случайно в `[0, within)`)
  открывается новый канал — новое TCP-соединение, которое L4-балансировщик отдаёт наименее загруженному инстансу.
  Альтернатива — GOAWAY/закрытие соединения сервером (`codes.Unavailable`): агент ушёл бы в обычный backoff с
  счётчиком попыток и без явного окна; новое сообщение протокола не нужно.
- [x] **R-2. ПК с гостем, сессией, сервисным режимом или командой в пути не трогаются никогда** (а не «в последнюю
  очередь»). Пока агент переподключается, у него нет канала: вызовы гостя (`GuestApi.Invoker()`) получают
  `Unavailable "agent is not connected"`, денежный вызов в полёте может оборваться при `channel.Dispose()` — гость заметил бы.
  Цена: в часы пик, когда почти все ПК перегруженного инстанса заняты, выравнивание идёт медленнее — по мере того как
  ПК освобождаются. Выживший инстанс по замеру держит все 5 000 ПК без ошибок (`docs/load-test.md` §4.2), так что
  медленное выравнивание безопасно. Экран входа (`locked`) переподключается: окно ≤ `rebalance_reconnect_within`
  (3 с) — попытка входа в эти секунды получит `Unavailable` и повторится гостем; риск принят как малый.
- [x] **R-3. Порог с гистерезисом.** Начать: `local > 1,2 × среднего` и превышение ≥ 50 потоков; закончить: превышение
  ≤ 25. Без гистерезиса либо выравнивание остановилось бы на 1,2 × среднего (3 000/2 000), либо инстанс реагировал бы на
  шум подключений. Инстанс никогда не опускается ниже своей доли и недогруженный никого не отпускает — маятника нет
  (`TestRebalanceConvergesWithoutPendulum`, интеграционный тест проверяет 5 интервалов покоя после выравнивания).
- [x] **R-4. Скорость: 100 ПК за 15 с с инстанса (jitter интервала ±20 %), окно переподключения 3 с.** ≈ 7
  подключений/с с инстанса — на два порядка меньше выдержанного при падении инстанса (≈ 715/с). Окно меньше
  `offline_grace` (проверяется конфигом) — переподключение не пишет в Postgres и не мигает на карте клуба.
- [x] **R-5. Учёт живых инстансов — hash в Valkey с собственным сроком в значении**, а не ключ на инстанс с TTL
  (тогда понадобился бы SCAN) и не срок полей hash (`HSETEX`, Valkey 9 — меньше переносимо на управляемые сервисы).
  Часы инстансов расходятся на секунды при сроке 45 с — допустимо. Новый инстанс публикует себя сразу при старте
  (с 0 потоков), уходящий — удаляет себя в `Drain`.
- [x] **R-6. Задача на каждом инстансе, не «один исполнитель».** CLAUDE.md требует не запускать фоновые задачи дважды
  — это про задачи над общими данными; здесь каждый инстанс решает только о своих потоках.
- [ ] **R-7 (наблюдение). Балансировщик не знает об инстансе, который ещё не в upstream.** Если инстанс опубликовал
  себя в Valkey, но балансировщик его не видит (k8s: под ещё не Ready в Service), отпущенные ПК вернутся на прежние
  инстансы (они пересчитают долю и через интервал отпустят ещё — до `rebalance_batch` лишних переподключений за
  интервал). Публикация идёт из фоновых задач, которые стартуют вместе с HTTP/gRPC, а `/readyz` готов за ≈ 0,6 с —
  на практике окно — один интервал. Если станет заметно — публиковать только после первого принятого потока.
- [ ] **R-8 (не проверено).** На staging с генератором (`server/cmd/loadgen`) не перемерено: сборка образа
  (`task staging:image`, ≈ 3–4 ГБ образов и кэша) при ≈ 6,6 ГБ свободного диска, общих с двумя параллельными задачами,
  была бы риском для них. Проверено интеграционным тестом с реальными Postgres/Valkey/NATS: 40 ПК на A, поднимается B →
  20/20 за 4 интервала, 60+ долговременных команд во время перебалансировки доставлены и выполнены. Для замера:
  `loadgen run -restart kill`, затем `docker start app2` и наблюдать `zafiro_agent_streams_active` /
  `zafiro_agent_stream_rebalance_requested_total`.

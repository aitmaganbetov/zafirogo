# Этап 3, группа 6 — суперадминка: вопросы и принятые решения

Владелец поручил решать самостоятельно (DECISIONS.md, принципы). Каждый пункт — решение и обоснование.

- [x] **SA-1. Домен кабинета (Q-069) в SPA.** В старом кабинет на `SUPERADMIN_DOMAIN` отвечает с корня (`Route::domain()`),
  без домена — с префиксом `/superadmin` (`routes/web.php` ~52–106, `app/Support/SuperadminHost.php`).
  - Решение: конфиг `superadmin.domain` (`ZAFIRO_SUPERADMIN_DOMAIN`). Сервер: REST `/api/superadmin/*` — только на этом хосте
    (иначе 404); на хосте кабинета REST панели клуба — только суперадмину в режиме просмотра клуба (иначе 403, как
    `RestrictSuperadminHost`; страницы SPA перенаправляет гард `requireClub`); вход на хосте кабинета — только суперадмины
    («Здесь входят только суперадмины Zafiro.», журнал `auth.login_failed`/`not_superadmin`, при успехе — `superadmin.login`,
    сессия без клуба). `index.html` хоста кабинета отдаётся с `<html data-superadmin-host>`; роутер SPA на этом хосте
    переписывает адреса (`/clubs` ↔ внутренний `/superadmin/clubs`, `web/src/features/superadmin/host.ts`).
  - Не перенесено: старый на хосте клуба при настроенном домене разлогинивал суперадмина без клуба и уводил в кабинет
    (`AuthController::login()` ~79–84); новый пускает его и показывает 403/кабинет на этом хосте. Во `vite dev` атрибута
    хоста нет — домен проверяется на собранном бинарнике (в dev без домена кабинет — `/superadmin`, как в старом).
- [x] **SA-2. Исходный каталог переводов.** `TranslationCatalog::sourceKeys()` читал `database/translations/ru.php`; в
  бинарнике нового сервера этого файла нет.
  - Решение: исходный каталог — строки языка `ru` в `translations` (их загружает `cmd/import-translations` из того же файла).
    Строки хранятся в формате Laravel (`:name`) — редактор показывает его (Q-065), в i18next (`{{name}}`) их переводит
    каталог при выдаче пакета; поэтому «хранить формат i18next» из задачи не потребовалось: формат на выходе тот же.
  - Отличие: порядок строк в редакторе — по `translations.id` (импорт сортирует группы и ключи), в старом — порядок файла
    `ru.php`. Визуальное сравнение страницы переводов — порог 7 %. Сохранить порядок файла можно, если импорт будет
    вставлять строки в порядке файла (Shipped сейчас — map); не сделано, чтобы не трогать импорт F1.
- [x] **SA-3. Релиз агента с подписью Ed25519.** Старый с автообновлением брал `<установщик>.sha256` с GitHub
  (`AgentReleaseController::installerChecksum()`), агент сам опрашивал предложение обновления (`AgentUpdate::offerFor()`).
  - Решение (DECISIONS «Обновления агента»): автообновление объявляется только с манифестом CI
    `<установщик>.update.json` (`version`, `sha256`, `size_bytes`, `channel`, `key_id`, `signature_ed25519` base64),
    подпись проверяется открытыми ключами `agent.update.public_keys` (`commands.VerifyUpdate`); нет манифеста — прежняя
    ошибка поля `auto_update`, подпись не сошлась — «Подпись установщика :url не прошла проверку.» (новый текст, нужен
    перевод kk/en). После объявления ПК со старым агентом (клубы с активной подпиской и включённой настройкой
    `agent_auto_update`) получают долговременную команду `UpdateAvailable` (24 ч, при отсутствии возможности
    `self_update` — не отправляется). Нужен шаг CI, публикующий манифест (Этап 4, агент).
  - Не перенесено: лимит предложений бездисковым ПК (`MAX_OFFERS`, `OFFER_INTERVAL_MINUTES`) и выдача предложения в
    Welcome — ПК, включённый позже 24 ч, обновление не получит до следующего объявления (Этап 4, агент).
  - Запасной релиз из `config/club.php` (`AGENT_LATEST_VERSION` и т. п.) не перенесён: релиз — только из кабинета.
- [x] **SA-4. «В сети» на экранах кабинета.** Старый считал `last_seen_at >= now − 90 с`; в новом связь с агентом — в Valkey.
  - Решение: `presence.Store.OnlineByClub` — члены набора `online` с неистёкшим сроком (ПК, чей стрим закрылся, считается на
    связи до конца окна переподключения). Сортировка клубов «В сети» — в SQL по массивам из Valkey.
- [x] **SA-5. Telegram — только настройки (Этап 4).** Токены шифруются ключом `superadmin.secret_key` (AES-256-GCM,
  `internal/secretbox`; аналог `Crypt::encryptString`), в ответ и журнал не попадают. Проверка токена в Telegram
  (`getMe`, `checkVerificationStatus`), поиск чата и проверочное сообщение — Этап 4: сейчас токен сохраняется без проверки,
  «Отправить проверочное сообщение» отвечает старой ошибкой «Не удалось отправить сообщение: проверьте бота и чат.»,
  без указанного чата оповещения считаются подключёнными с пустым чатом. В prod без `superadmin.secret_key` сохранить
  токен нельзя (503).
  - Сделано (Этап 4, H2): проверка токена Gateway, `getMe`/`getUpdates`/проверочное сообщение бота, реальная кнопка
    «Отправить проверочное сообщение» и оповещения мониторинга — `internal/telegram`, см. `stage4-telegram.md`.
- [x] **SA-6. Мониторинг (PD-10).** `CollectServerMetrics`, `SnapshotClubLoad`, `PruneMonitoringData`, `ExpireSubscriptions` —
  воркеры с прежними расписаниями (минута, 5 минут, сутки, 5 минут) под advisory lock (Q-086). Счётчики запросов
  (`RequestRecorder`) — в памяти каждого инстанса, раз в минуту складываются в `request_metrics`/`club_request_metrics`
  (UPSERT со сложением); каналы: REST `/api/v1` — `api`, остальной HTTP — `panel`, gRPC агента — `agent` (каждое сообщение
  стрима — как heartbeat старого), сервисы гостя — `guest`. Очереди Laravel нет — «Ждут выполнения/Упавшие задания» = 0.
  Журнал ошибок (кольцевой буфер slog), проверка SSL (`monitoring:certificates`) и алерты Telegram — Этап 4 (Q-060, PD-5):
  блок ошибок пуст, SSL — «Ещё не проверялся» для доменов `superadmin.ssl_hosts`. Истёкшие триалы остаются `trialing` (Q-036).
- [x] **SA-7. Тёмная тема кабинета.** `layouts/superadmin.blade.php` не подключает скрипт темы и переключателя нет — кабинет
  в старом всегда светлый (снимки визуального сравнения). Перенесено как есть: класс `.dark` снимается на время кабинета.
- [x] **SA-8. Экран «Сервер» и окружение стенда.** Живые показатели (load, память, диск, uptime, размер и таблицы базы,
  журнал ошибок старого `laravel.log`) зависят от машины и СУБД стенда: эти блоки скрыты в обоих снимках (`hide` в
  `tools/visual/pages.json`, высота карточек плавает от переноса чисел), порог — общий 0,5 % (факт 0,03–0,08 %).
  Задачи мониторинга нового (`monitoring-collect`, `monitoring-flush`, `monitoring-clubs`) в стенде выключены
  (`dev.disable_workers`, только dev/test), как планировщик старого: оба показывают «Планировщик ещё не запускался»,
  пустые графики и «За этот период запросов клубов ещё нет», а не трафик самого прогона снимков (раньше — 24–32 %).
  Диск «использовано» — как `disk_free_space()` PHP: `f_bavail` (свободно без резерва root), а не `f_bfree`.
- [x] **SA-9. Пагинация кабинета.** Списки кабинета — страницы с номерами (`page`), как `paginate()` старых экранов (вид
  ссылок Laravel), а не keyset: суперадмину нужны номер страницы и итог, объёмы (клубы, аккаунты) невелики; журнал —
  по 50 по индексу id.
- [x] **SA-10. Аудит.** Все изменения кабинета — в `platform_logs` (PD-15, как в старом) и в `audit_log` (`actor_kind =
  superadmin`; категории: подписка — `settings`/`tariff`, тарифы платформы — `tariff`, права суперадмина — `permission`,
  блокировка и Telegram — `security`, языки, переводы, новости, релиз агента — `settings`; `club_id` NULL — событие
  платформы). Вход суперадмина и просмотр клуба теперь пишутся в `platform_logs` (раньше — только системный лог).

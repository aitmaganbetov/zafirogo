# Этап 5 — перенос данных: решения и открытые вопросы

Решения приняты по принципам `docs/DECISIONS.md` (владелец поручил). Описание инструмента —
`tools/migrate-from-mysql/README.md`; код — `server/cmd/migrate-from-mysql`, `server/internal/migrate`.

## M1. Ядро переноса

### Решено

- [x] **S5-M1-1. `apply` — одна транзакция Postgres на клуб, без шагов с возобновлением.**
  Клуб заморожен в Laravel, объём одного клуба (тысячи клиентов, журнал за годы) Postgres проводит одной транзакцией;
  зато нет частичных состояний: ошибка, блокер в данных или расхождение сверки — откат, повтор начинается с чистого
  листа. Шаги с возобновлением требовали бы таблицы состояния переноса и идемпотентной дозаписи каждой таблицы —
  а ledger только дополняется (0002), так что «доделать» половину денег безопасно нельзя. Партиции журналов
  создаются до транзакции (`db.EnsurePartitions`, DDL идемпотентен; лишние пустые партиции безвредны).
  Сверка (`verify`) выполняется **внутри** транзакции до коммита (README старого плана: «при расхождении — откат»).
  Чтение MySQL — один снимок `REPEATABLE READ … CONSISTENT SNAPSHOT`, общий для чтения, записи и сверки.
- [x] **S5-M1-2. Повторный `apply` перенесённого клуба — отказ без изменений** (код выхода 5), а не идемпотентное
  обновление. После коммита клуб живёт в zafirogo (новые операции, ledger только дополняется), «обновить из MySQL»
  значило бы затереть его новые данные. Проверка — до транзакции и ещё раз под advisory-блокировкой переносов.
  Интеграционный тест сравнивает отпечаток данных до и после повторного запуска.
- [x] **S5-M1-3. Последовательности id (уточнение Q-029).** id сохраняются; последовательность каждой таблицы старой
  схемы (ядро и таблицы M2) ставится **не ниже `max(id во всей MySQL) + 10⁹`** (флаг `--id-reserve`), а не выше
  максимального id переносимого клуба: Laravel продолжает выдавать id остальным клубам, и строка, созданная в zafirogo
  с id «max клуба + 1», столкнулась бы с id клуба, переносимого позже (риск §3.10 `docs/schema-changes.md`).
  Запас 10⁹ — из рекомендации Q-029; значение только растёт (повторные переносы его не уменьшают).
  `mobile_api_tokens` (с 10¹²) не трогаем. Тест: новая запись журнала после переноса получает id > max MySQL + запас.
- [x] **S5-M1-4. Общие аккаунты (`users`).** Переносятся участники клуба и все аккаунты, на которые ссылаются строки
  клуба (автор новости, сотрудник смены, клиент брони…), — набор строится из ссылок (`UserRefs` в `spec.go`).
  Аккаунт с тем же id уже в zafirogo (перенесён с другим клубом) — не дублируется и **не перезаписывается**: после
  первого переноса источник правды — zafirogo (смена пароля/имени там не должна откатиться); отличия — в отчёте
  (`user_kept`). Тот же id с другим телефоном или телефон, занятый другим id (аккаунт, созданный в zafirogo), —
  блокер: нужно ручное слияние. Ссылка на несуществующий аккаунт — блокер.
- [x] **S5-M1-5. `member_balances.id` не сохраняется.** Роль `zafiro_platform` может вставлять в `member_balances` только
  `club_id, user_id, created_at, updated_at` (0004, баланс меняет только ledger); id строки баланса нигде не
  используется (ключ — `club_id, user_id`). Остатки — `billing.MigrateOpeningBalance`.
- [x] **S5-M1-6. Время.** `config/app.php` старого проекта — `'timezone' => 'UTC'` (~74, не из env), в
  `config/database.php` у соединения нет `timezone` — Laravel пишет строки UTC, сессия MySQL в поясе сервера.
  Инструмент читает так же (пояс сессии не меняет: `TIMESTAMP` вернёт ту же строку, что записал Laravel) и трактует
  строки в `--source-tz` (по умолчанию UTC). В отчёте — `@@global.time_zone`, `@@session.time_zone`,
  `@@system_time_zone`. Риск: если пояс сервера MySQL менялся между записью и переносом, `TIMESTAMP`-колонки
  сдвинутся — проверить на копии прода (см. открытые вопросы).
- [x] **S5-M1-7. Значения вне CHECK (Q-026) — блокер**, без автоматической замены: CHECK-списки читаются из
  `pg_constraint` (не дублируются в коде), неизвестное значение исправляется в источнике по одному (рекомендация Q-026).
- [x] **S5-M1-8. `created_at = NULL` (Q-030).** В партиционированных журналах (`activity_logs`, `api_request_logs`)
  ключ партиции обязателен — `COALESCE(created_at, updated_at, момент переноса)`, как миграция 0011; в остальных
  таблицах NULL переносится как есть, всё — в отчёт. `NOT NULL DEFAULT now()` — отдельной миграцией после переноса
  всех клубов (иначе следующий клуб с NULL не перенесётся).
- [x] **S5-M1-9. Настройки (Q-022, Q-023, BQ-3) в M1 — только отчёт**, запись как есть (v1): новый сервер читает
  старые значения так же, как `SettingsController::minutes()` (`internal/http/sections/settings/values.go`).
  Нормализация («30 сек» → число, черновые ключи) и уровни v2 — одним проходом в M2 (Q-003). Клуб `legacy` без
  `settings`: `--legacy-settings storage/app/settings.json` подставляет файл, без файла — дефолты (предупреждение).
- [x] **S5-M1-10. Не переносятся ядром:** `agent_qr_logins` (одноразовые QR, живут минуты; агенты переустанавливаются),
  `transfer_codes`, `password_recovery_codes` (Q-051), `server_metrics`, `request_metrics` (Q-083),
  `api_keys`/`api_idempotency_keys`/`webhook_endpoints`/`webhook_deliveries` (M2: секреты APP_KEY, Q-050),
  `api_request_logs` старше срока хранения. `club_request_metrics`, `club_load_snapshots` — переносятся (Q-083
  «по желанию», это данные клуба). `platform_logs` — только события с `club_id` клуба; платформенные таблицы и
  события без клуба — отдельный платформенный шаг.
- [x] **S5-M1-11. Касса в ledger.** Входящий остаток `cash_drawer` (`migration_opening_balance`, ключ
  `opening_cash_drawer`, встречный счёт `opening_balance`): остаток открытой смены (opening + приходы − расходы),
  а без открытой смены — `closing_balance` последней закрытой. Без этого первое закрытие смены в zafirogo записало бы
  снимок кассы без перенесённого остатка (CSQ-7); выравнивание при открытии следующей смены (CSQ-1) исправило бы это,
  но одной большой «разницей».
- [x] **S5-M1-12. Минуты пакетов** — входящий остаток в ledger минут (`opening_minutes:<id>`), чтобы сумма движений
  пакета сходилась с `minutes_left`; если владелец пакета не участник клуба (FK ledger минут), пакет переносится,
  а остаток в ledger не пишется (предупреждение).
- [x] **S5-M1-13. Ключ установки клуба** (`clubs.installation_key*`) не переносится — по Q-050 выпускается заново.
  Хэши `club_computers.agent_token_hash`, `club_invitations.token_hash`, PIN `agent_exit_pin_hash` — как есть
  (Q-051; судьба старых токенов агентов — M2).
- [x] **S5-M1-14. Slug клуба, совпадающий без учёта регистра со slug клуба zafirogo (Q-025), — блокер**: в MySQL
  (`utf8mb4_unicode_ci`) это был бы один клуб. Внутри одного клуба дублей без учёта регистра быть не может — их
  не пропустили бы уникальные индексы MySQL с той же сортировкой.
- [x] **S5-M1-15. Роль Postgres.** Логин — владелец схемы с членством в `zafiro_platform` (PD-9): данные пишутся под
  `SET LOCAL ROLE zafiro_platform` (RLS-политики платформы, права на `member_balances` как у сервера), `setval` и
  партиции — исходной ролью. `app.club_id` клуба ставится тоже (ledger проверяет тенант транзакции). Строки
  подключения — из окружения, не из аргументов.
- [x] **S5-M1-16. Источник тестов — настоящая схема.** `tools/migrate-from-mysql/dump-schema.sh`: копия старого
  проекта, `php artisan migrate:fresh` в `mysql:8.4.13` (php 8.4 + `pdo_mysql`, собирается из исходников образа без
  сети), демо-данные — старый сидер `tools/visual/old/seed.php` (он писал в sqlite, с MySQL работает без правок;
  кассовые операции — сервисом старого кода). Дамп `--no-data` и данные — в `testdata`, тесты PHP не запускают.
  `translations` в дамп не входят (платформенные, ~7 тыс. строк).
- [x] **S5-M1-17. Новая зависимость** `github.com/go-sql-driver/mysql v1.10.1` (02.09.2026, старше 14 дней — PD-4) и её
  `filippo.io/edwards25519 v1.2.0`. `govulncheck` в этой среде недоступен (vuln.go.dev закрыт прокси, Q-079).

## M2. Производные данные, секреты, файлы, платформа

Код: `server/internal/migrate/ext_*.go`, `settings_norm.go`, `laravelcrypt.go`, `platform.go`; описание —
`tools/migrate-from-mysql/README.md` («M2», «Платформенный шаг», «Порядок перевода клуба»).

### Решено

- [x] **S5-M2-1. Заморозка клуба в старом Laravel — «Приостановить подписку» в его суперадминке** (без изменений кода
  Laravel). `Superadmin\ClubController::suspend()` ставит `status = suspended`, `canceled_at = now()` и не трогает срок;
  `RequireActiveSubscription` отвечает 402 панели, агентам (экран блокировки), `/api/v1` и мобильным приложениям —
  данные клуба перестают меняться (фоновые `club-computers:expire-sessions` и т. п. по-прежнему работают, поэтому окно —
  без игроков; снимок MySQL всё равно согласован). Перенос возвращает подписке статус до заморозки флагом
  `--thaw-subscription active|trialing` (`canceled_at` → NULL: у действующей подписки его нет, `extend()` обнуляет);
  без флага приостановленная подписка переносится как есть с предупреждением `freeze` (уточнено S5-M3-2: статус
  подписка получает при `go-live`, до него перенесённый клуб закрыт). Альтернативы хуже: режима
  «только чтение» в старом коде нет; блокировка через nginx невозможна — балансировщик не знает клуба запроса панели.
- [x] **S5-M2-2. JSON v2 (Q-003) — через читатели сервера.** Чек: `cashsvc.DecodeReceipt` (экспортирован) → запись тем же
  форматом, что `encodeReceipt()` (не экспортирован — повторён в `ext_json.go`, совпадение проверяет чтение обратно:
  значение v2, прочитанное сервером, `reflect.DeepEqual` значению v1 — иначе блокер). Заказ: `shop.DecodeItems` →
  `shop.EncodeItems`. Чек/заказ, который сервер не читает и сейчас (сумма не разбирается), остаётся v1 с
  предупреждением: сервер вёл бы себя с ним так же, как без переноса. Сверка повторяет чтение для каждой строки.
- [x] **S5-M2-3. Нормализация настроек (Q-023) — значение, которое реально действовало.** Читатели минутных полей в
  старом коде расходились: рантайм брал `is_numeric ? число : умолчание` (`ComputerReservations::gapMinutes()` 30,
  `GuestFeatures::idleLogoutMinutes()` 5, `afterSessionAction()` 0.5, `StaffShifts::limit()` без лимита), экран —
  `SettingsController::minutes()` («15 мин» → 15). Строка-число → число (все согласны); нечисловая строка → умолчание
  рантайма (поведение клуба не меняется, принцип 2), а если экран показывал другое — предупреждение
  «экран показывал X, действовало Y». Поля, которые никто не читает (Q-024: `session_idle_timeout`,
  `session_auto_terminate_when_pc_unavailable`), — значение экрана. Флаги — по своему читателю:
  `filter_var(… ?? умолчание, FILTER_VALIDATE_BOOLEAN)` (`GuestFeatures`, `AgentUpdate`) или `(bool) data_get(…, false)`
  (`TopUpBonus`, `LoyaltyProgram`, `PaymentRules`). Черновые ключи (`tax_rate`, `loyalty_rules`) и неизвестные
  секции — как есть (DECISIONS: «неиспользуемые настройки переносятся как есть»), они уже в отчёте ядра.
- [x] **S5-M2-4. Уровни (BQ-3)** → v2 `bonus.EncodeLevels(bonus.Normalize(v1))`; проверка — `bonus.ParseSettings` до и после
  (уровни обоих видов `DeepEqual`), иначе поле остаётся v1 с предупреждением. Порядок уровней-объекта и равные пороги
  уже зафиксированы MySQL (JSON-колонка сортирует ключи при записи — Laravel читал тот же порядок), v2-список его
  сохраняет — проблема BQ-3 с `jsonb` после конвертации снимается.
- [x] **S5-M2-5. CQ-9:** `product_id` проставляется строке старого чека без `product_id`/`service_id`, если среди НЕ
  удалённых товаров клуба ровно один с таким именем; сравнение — запросом в MySQL (сортировка `utf8mb4_unicode_ci`, как
  `Product::where('name', …)` в `CashRegisterService::returnToStock()`). Побочный эффект, принятый решением CQ-9:
  в X/Z у такой строки появляется остаток склада (`ShiftReport::for()` берёт его по `product_id`).
- [x] **S5-M2-6. CSQ-2:** приход, у которого журнал отмечает и пополнение, и гостевую сессию (старый X/Z считал бы его
  дважды), переносится как `top_up` с предупреждением. `payment_method` (Q-013) заполняется по `details.payment_method`
  — подпись на языке оператора (`__('наличные')`…), сопоставление по ключам и переводам `translations` старой базы;
  неоднозначная или неизвестная подпись — NULL (сведения). Решение 0005 «старые строки — NULL» уточнено: журнал
  однозначно знает способ, а X/Z его не использует (Q-013), так что заполнение ничего не меняет в суммах.
- [x] **S5-M2-7. SV-3:** части идущих сессий и записи `tariff.purchased|time.purchased|time.package_started` с тем же
  `details.session_id` сопоставляются по порядку id (одна покупка — одна часть и одна запись в одной транзакции `sell()`)
  с проверкой вида; при несовпадении — NULL (сервер читает такие части по `kind`, S1-SES-02). Зона части-тарифа —
  текущая зона ПК покупки (`details.computer_id`): для пересадки она не используется (`session.AllowedZones` берёт зоны
  тарифа), только для отчётов.
- [x] **S5-M2-8. Токены и ключи.** `api_keys` — как есть (хэш `hash('sha256', …)` тот же, H1-1); аккаунты из
  `api_keys.created_by/revoked_by`, `webhook_endpoints.created_by` входят в набор переносимых аккаунтов (иначе FK; ключ,
  выпущенный бывшим сотрудником, сервер отклонит как и старый — `api_key_owner_lost_access`). `api_idempotency_keys` — с
  `club_id` ключа. Мобильные токены — `personal_access_tokens` пользователей (`App\Models\User`) с ability `club:<id>`,
  не истёкшие на момент переноса, владелец перенесён; id и хэш те же, последовательность `mobile_api_tokens` не трогаем
  (§2.3 `docs/mobile-compat.md`); занятый id — блокер. Токены входа по QR и регистрации старых агентов — тоже токены
  пользователей с ability клуба: переносятся (вреда нет, по ним работают только `/api/guest/*` старого формата).
  `club_computers.agent_token_hash` — как есть: новый сервер его не читает, агенты переустанавливаются с gRPC.
- [x] **S5-M2-9. Секреты APP_KEY (Q-050).** `Illuminate\Encryption\Encrypter` (laravel/framework v13.35.0, `aes-256-cbc`)
  повторён в `laravelcrypt.go`: base64(JSON `iv`, `value`, `mac`, `tag`), MAC `hash_hmac('sha256', iv.value, key)`
  проверяется каждым ключом (`APP_KEY`, затем `APP_PREVIOUS_KEYS`) за постоянное время, PKCS#7; тег у CBC — ошибка, как
  в `ensureTagIsValid()`. Каст `'encrypted'` и `Crypt::encryptString` не сериализуют; `Crypt::encrypt()` с `serialize()`
  тоже читается (`s:N:"…";`), хотя в старом коде им ничего не шифровалось. Что шифровалось: `webhook_endpoints.secret`
  (каст), токены `platform_settings` `telegram_gateway`/`telegram_alerts` (`Crypt::encryptString`),
  `clubs.installation_key` (каст; не переносится — S5-M1-13). Перешифровка — `secretbox` текущим ключом
  `ZAFIRO_SECURITY_DATA_KEYS` (вебхук — с контекстом `webhook.SecretContext(club)`, токены Telegram — без контекста, как
  читает `telegram.Store`). Тест — на значениях, зашифрованных настоящим PHP 8.4.27 (`laravel-crypt-fixture.sh`).
  Ключи — только из окружения; в отчётах и ошибках — только id строк.
- [x] **S5-M2-10. Файлы (Q-085):** диск `local` старого Laravel — `storage/app/private` (`config/filesystems.php`
  Laravel 11+, не `storage/app/public` и не `storage/app`); флаг `--laravel-storage`. Байты — в `club_images`/`news_images`
  (Этап 3, S-1/N-1), S3/MinIO — позже (Q-085 в `docs/backlog.md`). Проверки как у формы сервера: PNG/JPEG
  (`image.DecodeConfig`), размер ≤ 1/3/2 МБ; размеры в пикселях не проверяются (файл уже прошёл правило `dimensions`
  старой формы). Путь из базы — недоверенный: только внутри корня (`os.DirFS`, без `..`). Нет файла — предупреждение,
  путь остаётся (старый сервер в этом случае тоже отдавал 404).
- [x] **S5-M2-11. Платформенный шаг повторяем.** Языки, переводы, настройки: недостающие строки добавляются всегда;
  существующие перезаписываются значениями MySQL только при первом переносе (маркер — запись аудита
  `migration.platform_imported`): до него в Postgres только файлы `import-translations`, а MySQL хранит правки

### Решено

- [x] **S5-M3-1. Откат до открытия — `purge --club <id|slug> --confirm <slug>`** (вместо `forget` из S5-M2-О2).
  Журналы `ledger_*` и `audit_log` по-прежнему только дополняются; удаление — осознанная платформенная операция:
  функция `zafiro_purge_imported_club(club, slug, users[])` (0027) — `SECURITY DEFINER`, `search_path` закреплён,
  `EXECUTE` отозван у `PUBLIC` и никому не выдан (вызывает только владелец схемы — логин инструмента, PD-9; `zafiro_app` и
  `zafiro_platform` получают 42501 — тест). Условия: slug совпал (защита от опечатки в id), клуб в состоянии `imported`
  (S5-M3-2), в ledger клуба только `migration_opening_balance` и `package_expired` (сгорание пакетов фоновой задачей
  `burn_packages` работает и для закрытого клуба — без участия людей и денег кассы), в аудите — только `migration.*`;
  иначе отказ (код 6). Триггер «только добавление» (`zafiro_forbid_change`) пропускает DELETE строки, только если в
  транзакции стоит `zafiro.purge_club_id` = `club_id` строки **и** клуб в состоянии `imported`: настройку может поставить
  кто угодно, но DELETE на журналах есть только у владельца (REVOKE 0004), а клуб `live` так не удалить (тест).
  Удаляются строки клуба во всех таблицах с `club_id` (список — из каталога, порядок — по внешним ключам: ссылки NO
  ACTION/RESTRICT вроде `activity_logs → club_memberships`, `products → product_categories`; партиции — через родителя;
  RLS владельцу не мешает — функция ставит `app.club_id`), затем сам клуб; событие `migration.club_purged` (с числом
  удалённых строк по таблицам) — в `platform_logs` (в `audit_log` строку без клуба владелец не вставит: `FORCE RLS`).
  **Аккаунты.** Удаляются аккаунты, на которые ссылался только этот клуб: иначе исправленный в MySQL телефон аккаунта
  дал бы при повторном переносе блокер `user` (S5-M1-4). Отбор — в инструменте, под ролью `zafiro_platform` (владелец под
  `FORCE RLS` видит только клуб `app.club_id`, а «ссылок нет» нужно проверить по всем клубам): кандидаты — значения всех
  внешних ключей на `users` в строках клуба; они блокируются `FOR UPDATE` (новое членство в другом клубе ждёт транзакцию
  и не пройдёт проверку FK); остаются те, на кого ссылается любая строка вне клуба (по всем внешним ключам на `users`,
  включая `ON DELETE CASCADE/SET NULL`), и суперадмины. Если хоть одну таблицу со ссылками роль платформы видит не целиком
  (нет политики `USING (true)`), аккаунты не удаляются (предупреждение) — каскад FK иначе мог бы задеть другой клуб.
  Последовательности id и партиции не трогаются. Альтернатива «не удалять аккаунты» отвергнута (тупик при исправлении
  источника), «отключать триггеры ALTER TABLE» — тоже (блокировка ACCESS EXCLUSIVE ledger всех клубов до конца транзакции).
- [x] **S5-M3-2. Состояние клуба `clubs.migration_state`: `imported` → `live`; до `go-live` клуб закрыт подпиской.**
  `apply` создаёт клуб в состоянии `imported`, `go-live --club` переводит в `live` (окончательно: триггер запрещает
  `live → imported`; клубы, созданные в zafirogo, — сразу `live`). Как закрыт клуб до открытия: его подписка — `suspended`
  (статус после открытия — в записи аудита `migration.club_imported`, поле `go_live_subscriptions`: статус до заморозки из
  `--thaw-subscription` с `canceled_at = NULL`, а не замороженная — свой прежний статус). Это тот же механизм, которым
  клуб заморожен в Laravel (S5-M2-1): все входы клуба в zafirogo уже проверяют подписку (панель — `requireSubscription`,
  агенты — регистрация и поток, `/api/v1`, мобильные приложения) и отвечают 402 — **сервер вне инструмента не меняется**
  (отдельная проверка `migration_state` на каждом входе дублировала бы подписку в четырёх местах, в том числе в коде
  агента). Суперадмин видит клуб в кабинете; просмотр панели клуба до открытия — 402, как у замороженного клуба в Laravel
  (проверка до открытия — отчёты `verify`). `go-live` открывает подписку (только строки, всё ещё `suspended`; изменённую
  после переноса не трогает — предупреждение), пишет аудит `migration.club_live` и событие журнала платформы. Сверка
  `verify` не считает события инструмента (`platform_logs.event LIKE 'migration.%'`), иначе после `go-live` она
  расходилась бы на одну строку. S5-M2-1 уточнено: `--thaw-subscription` действует при `go-live`, а не сразу при `apply`.
- [x] **S5-M3-3. Q-005 — пересчёт балансов по истории старой базы: отчёт, не блокер.** Журнала денег в старом коде не

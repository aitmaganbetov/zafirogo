# Аудит производительности сервера и БД — решения и то, что оставлено владельцу

Исправления по находкам PB-01 … PB-27 аудита (фаза 2, исполнитель «скорость сервера и БД»). Замеры — на стенде с
крупным клубом (200 клубов, клуб №1: 50 035 членов, 500 ПК, 1 млн строк журнала, 306 тыс. кассовых операций,
база 2,3 ГБ, Postgres 18.6, машина 4 vCPU, общая с другими задачами — миллисекунды шумят, число страниц устойчиво).

Код: `server/internal/i18n` (каталог-снимок), `server/internal/db/plan.go`, `tx.go` (планы, таймауты),
`server/internal/http/compress.go`, `server/internal/webui/webui.go` (сжатие, кэш), `db/migrations/0032_perf_indexes.sql`,
`db/queries/*` (запросы), разделы `clubmap`, `customers`, `staff`, `reservations`, `superadmin`, воркеры
`monitoring`, `agent/presence` (пакетная запись).

Решения приняты по принципам `docs/DECISIONS.md`; отменить может только владелец.

## Принятые решения (подтвердить)

- [x] **AP-1 (PB-01). Каталог переводов — снимок в памяти, в базу на пути запроса не ходит.** `i18n.Catalog` держит
  неизменяемый снимок (`atomic.Pointer`): включённые языки, строки, готовые пакеты i18next, языки клубов. Обновляет его
  фоновая горутина каталога раз в 3 с на платформенном пуле (`httpserver.NewRouter` даёт каталогу `PlatformPool`).
  `Lookup` / `Translate` / `ClubLocale` — только чтение снимка: ни соединения, ни мьютекса на время ввода-вывода.
  Раньше перевод изнутри транзакции клуба раз в 5 с брал второе соединение того же пула под общим мьютексом — при
  занятом пуле все соединения висели «idle in transaction» до таймаута запроса (30 с, отказ панели).
  - Правка перевода в суперадминке: в пакетах i18next (`GET /api/i18n/{locale}`) — сразу (версия сверяется на каждый
    запрос, как раньше), в текстах сервера — не позже ~3 с (было ≤ 5 с).
  - Язык клуба: смена в «Настройки → Языки» видна на этом инстансе сразу (`SetClubLocale`), на остальных — ≤ 3 с
    (было ≤ 30 с). Выключенный язык — «нет перевода» из памяти (раньше — поход в базу на каждый вызов).
  - «Холодный» каталог (снимка ещё нет): запрос ждёт первую загрузку не дольше 3 с, затем отвечает русским текстом;
    после неудачной загрузки (база недоступна) — пауза 1 с без ожидания. Каталог, к которому не обращались 2 мин,
    останавливает сверку и забывает снимок.
- [x] **AP-2 (FE-04). В пакет i18next не кладутся записи «ключ = значение».** Клиент (`fallbackLng: false`) без
  перевода показывает сам ключ и подставляет в него `{{name}}` так же. Пакет `ru`: 264 292 → 33 672 байт
  (в gzip — 3 083). Формы множественного числа (`ключ_one` …) остаются. Серверный перевод берёт строки не из пакета.
- [x] **AP-3 (PB-11). Сжатие — в самом сервере, gzip из стандартной библиотеки (без новых зависимостей).**
  - API: JSON и текст от 1 КБ — gzip уровня 5 клиентам с `Accept-Encoding: gzip`; `Vary: Accept-Encoding`; сильный
    ETag обработчика становится слабым (`W/`). Не сжимаются: маленькое, уже сжатое, 204/304, HEAD, WebSocket,
    потоки (`text/event-stream`, ответ с `Flush` до первого килобайта) и `/api/auth/*` (в ответах токены — сжатие
    секрета вместе с управляемым извне текстом небезопасно, BREACH).
  - Вшитый фронт: текстовые файлы сжимаются один раз при первом запросе (уровень 9) и хранятся в памяти процесса
    (+~0,9 МБ); ETag — хеш содержимого (одинаков у инстансов, PB-23), `Last-Modified` убран; `/assets/*` —
    `immutable`, `index.html` и `sw.js` — `no-cache`. Brotli нет в стандартной библиотеке — при желании его даёт
    nginx/CDN перед сервером (решение владельца; выигрыш к gzip ≈ 15–20 % на JS).
- [x] **AP-4 (PB-02). Запросы с необязательными фильтрами планируются под значения.** Список запросов —
  `db.customPlanQueries` (33 запроса: журнал, клиенты, товары, заказы, API v1, мобильный API, суперадминка). Они
  выполняются в режиме `pgx.QueryExecModeCacheDescribe` — безымянным оператором, который Postgres планирует при
  каждом выполнении; обращение к серверу по-прежнему одно. Выбрано вместо `plan_cache_mode` (лишнее обращение или
  настройка на всю транзакцию) и вместо разделения запросов (десятки новых запросов). Тест
  `TestCustomPlanQueriesCoverOptionalFilters` не даст добавить запрос с `($x = '' OR …)` мимо списка.
  Цена — планирование на каждый вызов (0,3–2 мс; журнал с партициями — до 5–10 мс).
- [x] **AP-5 (PB-17). Таймауты Postgres — в транзакции клуба, а не на ролях.** Логины сервера создаёт развёртывание
  (имена не известны миграции), а `ALTER ROLE … SET` на групповой роли на её членов не действует. Поэтому
  `db.InTenantTx` ставит `statement_timeout = 2 мин` и `idle_in_transaction_session_timeout = 1 мин` той же командой,
  что `app.club_id` (только до конца транзакции). Транзакции без клуба (`InPlatformTx`: воркеры по всем клубам,
  суперадминка, перенос данных, миграции) не ограничены; для долгой законной операции в транзакции клуба —
  `db.Options{NoTimeouts: true}`.
- [x] **AP-6 (PB-05). `pg_trgm` + GIN по `users(name)`, `users(phone)`.** Расширение «доверенное» (PostgreSQL ≥ 13):
  его ставит владелец базы без суперпользователя. В управляемом Postgres с белым списком расширений `pg_trgm`
  включают в настройках кластера до миграции. Индексы — 6,0 и 3,9 МБ на 155 тыс. пользователей.
- [x] **AP-7 (PB-13). Удалены только доказанные дубли индексов** (запрос к `pg_index`: те же ведущие колонки, классы
  операторов и порядок, индекс не обслуживает ограничение): одноколоночные `(club_id)` на `cash_shifts`,
  `cash_transactions`, `club_computers`, `club_zone_tariff`, `club_zones`, `product_categories`, `products`,
  `stock_movements`, `tariffs` и `cash_transactions_club_shift_fk`. Плюс два индекса `club_computers` (`status`,
  `last_seen_at`), которые не использует ни один запрос, но делали каждое обновление состояния ПК не-HOT (PB-12).

## Оставлено владельцу

- [ ] **AP-O1 (PB-03). Журнал действий: список пользователей в фильтре и потолок счётчика.** Каждая страница журнала
  отдаёт всех членов клуба, у которых есть запись в журнале (у крупного клуба — 50 010 человек, 3,7 МБ; запрос 0,4–1,1 с
  — это 50 тыс. чтений `users` и сортировка, ускорить без смены состава нельзя). Так же делал старый экран
  (`User::whereIn('id', ActivityLog::select('user_id'))`). Варианты: (а) в списке — только сотрудники, клиент ищется
  подгрузкой по вводу, как в бронях (меняет экран); (б) отдавать список один раз, а не с каждой страницей (правка API
  и фронта). Сейчас ответ сжимается (389 КБ по сети). Счётчик «Записей: N» оставлен точным: потолок («10 000+»)
  меняет текст экрана. Без фильтров он стоит 110–500 мс на 1 млн строк; с поиском по описанию — секунды (полный
  просмотр журнала клуба: `/api/activity-logs?search=…` p50 8,2 с). Рекомендация: период по умолчанию (например,
  30 дней) или поиск только внутри выбранного периода.
- [ ] **AP-O2 (PB-05). Пустой поиск на кассе** («первые 25 клиентов по имени») сортирует всех клиентов клуба
  (93 мс на 50 тыс.). Убрать сортировку можно копией имени в `club_memberships` (схема) или показом «последних
  клиентов» (меняет экран).
- [ ] **AP-O3 (PB-15, решение PD-8). Партиции метрик и остальных журналов** — не сделано: это не одна безопасная
  миграция. Нужны: новые партиционированные таблицы и перенос строк (`club_request_metrics`, `club_load_snapshots`,
  `request_metrics`, `platform_logs`, `webhook_deliveries`), смена первичных и уникальных ключей (ключ партиции обязан
  входить в них — `ON CONFLICT (club_id, minute)` счётчиков нужно пересобрать), белые списки функций
  `zafiro_create_monthly_partitions` / `zafiro_drop_monthly_partitions`, `db.PartitionedTables` / `RetentionTables`,
  замена `DELETE … WHERE minute < $1` на удаление партиций в воркерах и экраны суперадминки, читающие эти таблицы.
  Оценка — 2–3 дня с тестами; делать до первого переноса клуба (таблицы пусты — без риска для данных). Сроки
  хранения по таблицам — решение владельца. До тех пор: `club_request_metrics` растёт на «клубы × минуты» (при 500
  клубах и 30 днях — 21,6 млн строк, ~3,9 ГБ), очистка — одним `DELETE`.
- [ ] **AP-O4 (PB-13). Индексы-кандидаты на удаление, не дубли.** Одноколоночные по малозначным полям без `club_id`:
  `cash_transactions_type_index`, `stock_movements_type_index`, `cash_shifts_status_index`, `club_zones_status_index`,
  `club_zones_sort_order_index`, `tariffs_is_active_index`, `tariffs_duration_minutes_index`, `products_category_index`,
  `club_subscriptions_status_index`, `activity_logs_event_index`, `activity_logs_created_at_event_index` (44 МБ),
  `activity_logs_subject_type_subject_id_index` (29 МБ); и ни разу не использованные в прогоне панели
  (`session_purchases_*`, `ledger_transactions_club_id_session_id` …). Удалять — после сбора `pg_stat_user_indexes`
  на staging под нагрузкой агентов, гостей и воркеров.
- [ ] **AP-O5 (PB-18). X-отчёт**: чеки смены читаются в Go и агрегируются там (62 мс на смену в 3 000 операций).
  Перенос агрегации в SQL затрагивает денежный расчёт (чеки v1/v2) — нужен отдельный шаг с золотыми сценариями.
- [ ] **AP-O6. `/dev/shm` контейнера Postgres.** С планами под значения Postgres чаще выбирает параллельные планы;
  в Docker по умолчанию `/dev/shm` — 64 МБ, и параллельный запрос падает с «could not resize shared memory segment …
  No space left on device» (получено на стенде: поиск по журналу, 4 запроса одновременно). В compose-файлах Postgres
  (dev, staging, prod) нужен `shm_size: 1g` (или `--shm-size`); файлы `deploy/` и `docker-compose.dev.yml` — зона

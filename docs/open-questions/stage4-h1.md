# Этап 4, блок H1 — интеграционный API /api/v1: решения и открытые вопросы

Решения приняты по принципам `docs/DECISIONS.md` (владелец поручил). Код: `api/v1.yaml`,
`server/internal/http/sections/v1`, `server/internal/apikey`, `db/queries/apiv1.sql`, `db/migrations/0022_api_v1.sql`.

## Решено

- [x] **H1-1. Старые ключи без перевыпуска.** `ApiKeyManager::create()` хранил `prefix = zfk_<8>` и
  `key_hash = hash('sha256', $plain)` (hex) — без APP_KEY и соли. Новый сервер проверяет ключ тем же алгоритмом
  (`apikey.Hash`, тест со значением, снятым PHP 8.4), поиск — по тому же уникальному префиксу. Перенесённые строки
  `api_keys` работают как есть; перевыпуск не нужен. Ключи, созданные в настройках нового сервера
  (раздел integrations), — того же формата.
- [x] **H1-2. Поиск ключа до выбора клуба (L-3).** Узкая политика `api_key_lookup` на `api_keys` (строка видна роли
  `zafiro_app` только при `app.api_key_prefix` = её префикс, как `enroll_code_lookup` в 0009), затем в той же
  транзакции `app.club_id` клуба ключа — членство создателя и подписка. Без SECURITY DEFINER и без пула
  `zafiro_platform` в обработчике запроса.
- [x] **H1-3. Кэш метаданных ключа (300 с) не переносится.** Старый кэш сбрасывался наблюдателями при каждом
  изменении (отзыв, права создателя, подписка); новый сервер читает ключ, членство и подписку одним коротким
  запросом на каждый вызов — отзыв и потеря прав действуют сразу, без логики сброса. Объём v1 мал по сравнению с
  трафиком агентов; при необходимости — кэш в Valkey с версией клуба.
- [x] **H1-4. Лимиты — ключи конфигурации** `integrations.*` (env `ZAFIRO_INTEGRATIONS_*`): `key_rate_limit` 120,
  `key_rate_limit_max` 1000, `club_rate_limit` 600, `failed_auth_per_minute` 20, `max_request_kb` 256,
  `max_bulk_items` 50, `idempotency_retention` 24h. Счётчики окон — Valkey (общие для инстансов; без Valkey — в
  памяти). Раздел «Интеграции» тоже берёт 120/1000 из конфигурации.
- [x] **H1-5. Журнал запросов `api_request_logs` — месячные партиции (PD-8)** в 0022 с переносом строк, как
  `activity_logs` в 0011; новые партиции создаёт `db.EnsurePartitions`.
- [x] **H1-6. Срок хранения ключей идемпотентности (24 ч).** Старый `integrations:prune` удалял строки раз в час;
  здесь просроченная строка удаляется при следующем запросе с тем же ключом (поведение то же: через 24 ч ключ
  свободен). Таблица `api_idempotency_keys` с `club_id` (Q-028, 0012).
- [x] **H1-7. Вебхук `computer.reservation_changed` от экрана «Брони».** Новый `reservations` слал его с
  данными `{computer_id, reservation_id, action}`; в старом коде этот вебхук отправляли только флаг брони ПК
  (карта клуба, API v1) с `{computer_ids, reserved}`, а `ReservationController` вебхуков не слал. Исправлено:
  брони пишут `reservation.changed` и `computer.state` (карта перечитывает ПК), внешние подписчики получают
  только прежние события. Остальные события и подпись (`v1=` HMAC, `X-Zafiro-*`, `event_id`) совпадают;
  суммы — строки + `*_tiyn` (RQ-3).
- [x] **H1-8. Статус и `last_seen_at` ПК** в ответах v1 — из присутствия агента (Valkey), как на карте клуба:
  heartbeat больше не пишется в Postgres. Свежесть «90 с» старого кода заменена признаком «агент в сети».
- [x] **H1-9. Курсоры** — тот же формат, что `Cursor::encode()` Laravel (`{"<таблица>.id": N,
  "_pointsToNextItems": true}` в base64url). Неразборчивый курсор или курсор «назад» — первая страница (API
  выдаёт только `next_cursor`; в старом курсор без `_pointsToNextItems` давал 500).
- [x] **H1-10. Справка /docs/api** показывает `api/v1.yaml` (копия в пакете public обновляется `api/gen.sh`, тест
  сверяет). Отличия от старой спецификации — только `operationId`, `x-go-type` у `price` и имена компонентов
  ответов `ProductResponse`/`ProductListResponse` (совпадали с именем схемы `Product` — генератор не различает).

## Отличия, оставленные осознанно (не влияют на интеграторов)

- [ ] **H1-11. Валидация — одна ошибка на поле.** Валидатор Laravel в редких сочетаниях правил отдавал несколько
  сообщений одного поля; здесь — первое нарушенное правило (все поля сразу). Коды и поля `error.fields` те же.
- [ ] **H1-12. Байты JSON.** `json_encode` Laravel экранировал `/` и не-ASCII (`А`); ответы нового сервера —
  UTF-8 без экранирования. Для JSON-клиентов разницы нет; хэш идемпотентности считается по телу запроса, не ответа.
- [ ] **H1-13. `stock_movements.product_id` удалённого товара** — как в старом: проходит `exists` (без условия
  `deleted_at`), затем 404 `not_found` (findOrFail с SoftDeletes).

## Открытые вопросы

- [x] **H1-Q1. Очистка `api_request_logs` старше 90 дней** (`request_log_retention_days`) и доставок вебхуков старше
  30 дней. С партициями это `DROP` старых партиций; задачи удаления партиций в проекте пока нет (общая для журналов
  PD-8). Рекомендация: одна фоновая задача «срок хранения партиций» с таблицей сроков по журналам — в блоке
  эксплуатации.
  - Сделано (хвосты Этапа 4): фоновая задача `logs:retention` (`server/internal/worker/log_retention.go`, под
    `leader.RunOnce`, раз в час как `integrations:prune`) удаляет (DETACH + DROP) месячные партиции, весь месяц
    которых старше срока: `api_request_logs` — `integrations.request_log_retention` = 90 дней. Функция
    `zafiro_drop_monthly_partitions` (0026_log_retention.sql) — с белым списком (только `api_request_logs`):
    ledger_*, `audit_log` не удаляются никогда, `activity_logs` старый код хранил вечно. Отличие: строки живут
    не меньше 90 дней, до месяца дольше (старый код удалял построчно). `webhook_deliveries` (30 дней) не
    партиционирована — её очистка к этой задаче не относится.
- [x] **H1-Q2. Интеграционные тесты `stage3_g4`/`stage3_g5` (пакет `internal/http`) падают с 1 ноября 2026**
  (`no partition of relation "activity_logs" found for row`): у них зафиксированы часы 2026-10-15, а миграции
  создают партиции с текущего месяца. Не связано с H1; исправление — в `dbtest` создать партиции прошлых месяцев
  (но `ledger.TestPartitions` проверяет «текущий + 3» после миграций — его тоже нужно поправить) или сдвинуть
  часы тестов. Решает владелец этих тестов/оркестратор.
  - Сделано: `dbtest.Start` создаёт партиции всех `db.PartitionedTables` на `dbtest.PartitionMonthsBack` (24)
    месяца назад тем же `db.EnsurePartitions`; `ledger.TestPartitions` проверяет инвариант (нужные месяцы есть,
    повтор ничего не создаёт, новый месяц создаётся). Визуальный стенд (`cmd/visual-seed`) — от месяца
    `dev.fixed_now`. В проде без изменений; перенос старых данных создаёт партиции сам
    (`tools/migrate-from-mysql/README.md`).

# Этап 7 — второй фактор входа суперадмина (TOTP)

Поручение владельца: TOTP для суперадминов (снимает SQ-2 в `docs/open-questions/stage6-security.md` и SEC-010 в
`docs/security-review.md`). В старом Laravel этого нет — новая функция, поэтому экраны сделаны в стиле существующих
(карточка входа `auth-*`, таблица пользователей кабинета), без новых CSS-классов. Решения ниже приняты по принципам
`docs/DECISIONS.md` (4 — безопасность по умолчанию); каждое можно пересмотреть.

## Что сделано

- [x] **Алгоритм** — `server/internal/auth/totp`: RFC 6238 поверх HOTP RFC 4226 на stdlib (HMAC-SHA1, 6 цифр, шаг
  30 с, окно ±1 шаг), сравнение за постоянное время. Тесты — векторы RFC 6238 (приложение B) и RFC 4226
  (приложение D), окно, повтор шага. Новой зависимости нет.
- [x] **Вход** — `server/internal/auth/mfa` + `auth.Service`: после верного пароля суперадмина — «полувход» (202,
  `challenge`), сессии и cookie нет. Полувход — случайный токен 256 бит, в Valkey только sha256 и пользователь (клуб,
  «запомнить меня», имя и телефон для журнала), срок 5 мин, одноразовый, не больше 5 попыток кода.
  Эндпоинты `POST /api/auth/second-factor/setup|verify` (`api/auth.yaml`).
- [x] **Принудительная настройка**: TOTP не настроен → `setup` выдаёт ключ (base32) и `otpauth://`; первый верный
  код включает TOTP и выдаёт 10 кодов восстановления, только потом сессия.
- [x] **Хранение**: ключ — только шифротекст `secretbox` (`security.data_keys`, `v2:<kid>:…`, контекст
  `superadmin_totp.secret:user=<id>` — шифротекст нельзя перенести другому); CHECK `^v[0-9]+:` в схеме. Не в логах,
  не в журнале, не в аудите, не в Valkey. Перешифровка при ротации ключей — воркер `reencrypt-secrets`.
- [x] **Повтор кода**: `superadmin_totp.last_step` — принимается только шаг больше последнего (в той же транзакции
  с `FOR UPDATE`).
- [x] **Коды восстановления**: 10 штук `xxxx-xxxx-xxxx-xxxx` (base32 Крокфорда, 80 бит), показываются один раз,
  хранятся sha256 с привязкой к пользователю; использование — одноразово, в `platform_logs`
  (`superadmin.totp_recovery_used`, сколько осталось).
- [x] **Лимит**: правило `superadmin-totp` — 5/мин и 30/ч на аккаунт, 300/мин на IP; неудачи —
  `superadmin.totp_failed` в `platform_logs`.
- [x] **Сброс**: (а) в кабинете («Пользователи» → «Сбросить 2FA», с подтверждением) —
  `DELETE /api/superadmin/accounts/{id}/second-factor`, журнал `superadmin.totp_reset` и `audit_log`, сеансы
  отозваны; свой — нельзя, режим просмотра клуба — 403 `read_only` (и `readOnlyAllowed`, и обработчик);
  (б) аварийно — `zafiro superadmin-totp-reset -phone …` (`docs/deploy.md` §5 «Аварийный сброс второго фактора суперадмина»).
- [x] **Сессии**: флаг `mfa` в сессии Valkey; сессия суперадмина без него не действует (`auth.Service.Authenticate`
  отзывает её). Так закрываются сессии, открытые до выкладки, и сессия сотрудника, которому выдали права
  суперадмина, — нужен новый вход с кодом.
- [x] **Права в базе**: `0029_superadmin_totp.sql` — таблицы только у `zafiro_platform`; `zafiro_app` не видит
  (`TestAppRoleLeastPrivilege`).
- [x] **Фронт**: шаг второго фактора в карточке входа (`SecondFactor.tsx`), метка «2FA не настроена» и кнопка сброса
  в «Пользователях»; переводы ru/kk/en (`db/seed/translations-new.*.json`).
- [x] **Тесты**: Go unit (векторы, окно, повтор, коды, лимит), интеграционные (`internal/auth/mfa`, `internal/auth`,
  `internal/http/second_factor_integration_test.go`, `cmd/zafiro`, `internal/worker`, `internal/db`), Vitest
  (`SecondFactor.test.tsx`), Playwright (`e2e/superadmin.spec.ts`: вход с настройкой, сброс).

## Решения

### T7-1. Окно и повтор

Окно ±1 шаг (90 с) — как у большинства серверов TOTP; уже, чем это, — частые отказы при неточных часах телефона.
Повтор: только шаг больше последнего принятого. Следствие: два входа одного суперадмина в пределах одного шага —
второй ждёт следующий код (≤ 30 с). Принимаем.

### T7-2. Лимит попыток — «как у входа» плюс часовой

Вход (`web-login`) — 5/мин на «IP + телефон» и 300/мин на IP. Для второго фактора пользователь известен из полувхода,
поэтому ключ — аккаунт, а не «IP + аккаунт»: иначе перебор шёл бы с разных IP. Только 5/мин дают 7 200 попыток в
сутки (≈ 2 % вероятности угадать 1 из 3 кодов окна за сутки) — поэтому ещё **30 в час** на аккаунт (≈ 0,2 % в
сутки) и 5 попыток на полувход (дальше — снова пароль, а он под `web-login`). Обратная сторона (SQ-1): тот, кто знает
пароль суперадмина, может держать его второй фактор под лимитом — но это уже инцидент (пароль утёк), и он виден в
журнале (`superadmin.totp_failed`). Лимит считает сервис (`mfa.Manager`), а не HTTP-middleware: пользователь
известен только из полувхода в теле запроса.

### T7-3. Хеш кодов восстановления — sha256, не Argon2id

У кода 80 бит случайности: перебор по sha256 из утёкшей базы невозможен, а Argon2id ×10 кодов на каждую попытку
нагружал бы вход и ограничитель хэширования паролей. Хеш привязан к пользователю (`zafiro.recovery.v1:<id>:<код>`).

### T7-4. QR-кода нет

В `web/package.json` библиотеки QR нет (вход гостя `/pc-login` QR не рисует — его рисует агент), новую зависимость
не добавляем: ключ показывается текстом (поле только для чтения, можно скопировать) и ссылкой `otpauth://` (на
телефоне открывает приложение-аутентификатор). Если владелец захочет QR — отдельная задача с закреплённой версией
библиотеки.

### T7-5. Сессии до выкладки — недействительны

Флаг `mfa` в сессии; сессия суперадмина без него отзывается при первом запросе. После выкладки все суперадмины
входят заново и проходят настройку. Альтернатива («доверять старым сессиям до истечения») оставляла бы до 30 дней
доступ без второго фактора.

### T7-6. Сброс: кто и что

- В кабинете — любой другой суперадмин (не себе: себе — через другого суперадмина или командой; иначе укравший
  сессию снимал бы второй фактор). Сбрасывает ключ и коды восстановления, отзывает сеансы. Режим просмотра клуба —
  запрет (это «только смотреть», хотя маршрут кабинета `readOnlyGuard` обычно пропускает).
- Аварийно — `zafiro superadmin-totp-reset -phone +7…` с конфигурацией сервера (Postgres `zafiro_platform`, Valkey):
  когда суперадмин один и потерял телефон и коды, или потерян ключ данных `security.data_keys`. Пишет
  `platform_logs` (от имени платформы, `details.via`) и `audit_log` (`actor_kind = system`).
- Ключ не расшифровывается (ключ данных потерян) — отдельный ответ «обратитесь к другому суперадмину для сброса»,
  а не «неверный код», и ошибка в журнале сервера.

### T7-7. Какие входы суперадмина требуют кода

Любой вход пользователя с `is_superadmin`: на хосте кабинета и в панели клуба (суперадмин, который ещё и сотрудник
клуба, тоже вводит код — его сессия даёт права суперадмина). Сотрудники клубов и клиенты — без изменений. Без
подключённого второго фактора (`auth.Options.SecondFactor`) вход суперадмина закрыт (`ErrSecondFactorUnavailable`),
а не пропускается.

### T7-8. Визуальный стенд (dev)

Снимки страниц суперадмина входят заново на каждый снимок (десятки входов подряд). У демо-суперадмина TOTP включён
заранее известным ключом (`tools/visual/fixtures/demo.json` `login.totp_secret`, его шифрует `visual-seed` ключом
`VISUAL_DATA_KEY`), Playwright вычисляет код (`web/e2e/visual/support.ts` `totpNow`). Повтор кода в пределах шага
стенд разрешает ключом `dev.totp_allow_replay` (только dev/test, в prod — ошибка валидации; код и окно проверяются
всегда), лимит `superadmin-totp` на стенде выключен, как `web-login`. Журнал платформы при этом получает ровно те же
строки, что старый (`superadmin.login`), — настройка TOTP на стенде не проходит.

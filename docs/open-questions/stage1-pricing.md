# Вопросы Этапа 1: пакет `billing/pricing`

Пакет: `server/internal/billing/pricing` — чистые расчёты цен и оплаты времени (WeeklyPeriods, PaymentRules,
цена тарифа/часа/минут, раскладка по балансам `sell()`, покупка тарифа/минут/пакета, «весь баланс», автобиллинг,
гостевая сессия). Оракул: `oracle_test.go` (тег `phporacle`) через `tools/php-oracle/eval.php`.

- [x] **PQ-1. «Игра на весь баланс» не всегда продаёт максимум минут — переносим как есть?**
  - Контекст: `WindowsAgent/Frontend/main.js` `affordableMinutes()` берёт `floor(balance*60/hour)` и уменьшает,
    пока цена > баланса. Из-за «+30» в `minutesPriceInCents()` при дешёвом часе ещё одна минута иногда стоит столько же
    (1 тиын/ч, баланс 5 тиынов: 300 мин, а 301 мин тоже за 5 тиынов). На реальных ценах (сотни тенге в час) эффект — 0 минут.
  - Варианты: (а) буквально как агент (сделано, допущение Q-008); (б) искать максимум минут с ценой ≤ баланса.
  - Рекомендация: (а) — те же числа, что у клиентов сейчас.
  - Решение (30.10.2026): принята рекомендация: (а) буквально как агент.

- [x] **PQ-2. `discounted()` зависит от версии PHP для процентов с 3+ знаками — пакет следует `money` (PHP 8.4).**
  - `(int) round($percent * 100)`: PHP 8.3 и 8.4 расходятся на процентах вида `x.xx5` (40.245 %, 0.145 %, 1.005 %).
    Первый прогон дифф-теста (тогда `money.PHPRound` был 8.3) против оракула на PHP 8.4.27 дал ровно такие расхождения
    (`percent 40.245, price 355802309888`: 8.3 → 212591880158, 8.4 → 212627460389). Пакет `money` переключён на 8.4
    (composer.lock старого проекта требует PHP ≥ 8.4 — см. stage1-money MQ-1); `pricing` считает через `money.BasisPoints`
    и теперь совпадает с 8.4 (в тесте — и эти проценты).
  - Скидки в БД — `decimal(5,2)` (личная) и уровни лояльности с 2 знаками: там 8.3 и 8.4 совпадают, на реальные цены не влияет.
  - Рекомендация: подтвердить `php -v` на проде (MQ-1); если 8.3 — достаточно переключить `money.BasisPoints`.
  - Решение (30.10.2026): решено фактом: PHP 8.4 (MQ-1), `pricing` считает через `money.BasisPoints` по 8.4.

- [x] **PQ-3. Где валидировать запрос: `minutes` 1…720, `balance ∈ {main, bonus}`.**
  - В старом коде это правила запроса (`GuestMinutesController::purchase()`, `PurchaseAgentTariffRequest`), ответ 422 с полем.
    В пакете такие входы — `ErrInvalidInput` (ошибка вызывающего), а не `*pricing.Error`. HTTP/gRPC-слой должен отклонять
    их раньше (OpenAPI/proto `minimum/maximum/enum`), иначе клиент получит 500.
  - Рекомендация: так и оставить; отметить в `api/openapi.yaml` и `proto/agent/v1`.
  - Решение (30.10.2026): принята рекомендация: отклонять раньше (`minimum/maximum/enum` в OpenAPI и proto).

- [x] **PQ-4. Цены больше `decimal(12,2)` / формы.**
  - Формулы перенесены для цен 0…`MaxPrice` = 999 999 999 999 тиынов (StoreTariffRequest max 9 999 999 999.99) и балансов
    |b| ≤ `money.MaxAmount`. Вне — `ErrInvalidInput` (PHP переполнил бы int в float). В Postgres `tariffs.price`,
    `club_zones.price_per_hour` — `bigint` без CHECK.
  - Рекомендация: добавить CHECK `price BETWEEN 0 AND 999999999999` в схему (агент схемы) или валидацию формы.
  - Решение (30.10.2026): принята рекомендация: CHECK `price BETWEEN 0 AND 999999999999` в схеме и валидация формы. Сделано: CHECK в 0014, тест `TestPriceChecks`; валидация формы — с экраном тарифов (Этап 3, backlog).

- [x] **PQ-5. Ошибки старого кода, которые читаются странно, переносятся буквально — подтвердить.**
  - Цена 1 тиын, 50 % бонусами: `bonusLimitCents(1) = intdiv(50, 100) = 0` → «В клубе бонусами нельзя оплачивать время.»
    (`sell()`), хотя бонусы в клубе разрешены.
  - Отрицательный основной баланс: `sell()` отклоняет даже покупку за 0 (запуск пакета) — «Недостаточно средств…».
  - Гостевая сессия на ПК: занятость проверяется после цены, поэтому на занятом ПК в зоне без цены ошибка — про цену.
  - Рекомендация: оставить (перенос, а не редизайн).
  - Решение (30.10.2026): принята рекомендация: оставить (перенос, а не редизайн).

- [x] **PQ-6. Проверка брони при гостевой продаже — внутри цикла по ПК.**
  - `GuestSessions::sell()` проверяет бронь каждого ПК сразу после его занятости, до следующего ПК. Чтобы порядок ошибок
    совпал, `QuoteGuestSession` принимает колбэк `CheckBooking`; вызывающий (billing) передаёт туда проверку брони из БД.
    Для покупки клиентом бронь проверяется после `Quote*` (в `sell()` она после проверки денег).
  - Вопроса к владельцу нет — фиксирую договорённость для агента, который подключит пакет к БД.
  - Решение (30.10.2026): принято как сделано (колбэк `CheckBooking`).

- [x] **PQ-7. `user_roles` тарифа недостижим из интерфейса (BR-016), но правило перенесено (GAP-015).**
  - Рекомендация: оставить в расчёте; решение о форме — к владельцу при переносе экрана тарифов.
  - Решение (30.10.2026): по принципам (PD-11) — правило остаётся в расчёте; поле в форме тарифа не добавляем.

- [x] **PQ-8. Найдено оракулом: старый `sell()` читает отрицательный баланс от −0.99 до −0.01 ₸ как положительный.**
  - `AgentTariffPurchaseService::amountToCents("-0.01")` = `(int)"-0" * 100 + (int)"01"` = **+1** тиын (знак теряется у
    целой части «-0»). Дифф-тест (`Purchase.run`, 1500 случайных покупок) дал 52 расхождения — все с балансом `-0.01`:
    PHP пропускает покупку за 0.00/0.01 ₸ и даже «пишет» баланс 0.01, Go честно отказывает «Недостаточно средств…».
    При балансе ≤ −1.00 ₸ (`"-1.50"` → −150 + 50 = −100) PHP тоже ошибается в сумме, но знак верный.
  - В новой схеме баланс — точный `bigint`, этот баг не переносится (как Q-004 для `formatCents`). Генератор дифф-теста
    теперь даёт только неотрицательные балансы.
  - Вопрос к владельцу: бывают ли в проде отрицательные балансы (касса/владелец могут списать больше?) — если да,
    при переносе данных `tools/migrate-from-mysql` их нужно найти отдельно (поведение покупок для таких клиентов изменится).
  - Рекомендация: не повторять баг; проверить данные запросом `WHERE balance < 0 OR bonus_balance < 0`.
  - Решение (30.10.2026): по DECISIONS Q-004 — баг не повторяем; отрицательные балансы при переносе — входящим остатком с пометкой в отчёте.

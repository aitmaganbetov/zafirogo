# Вопросы Этапа 1: пакет `money`

Пакет: `server/internal/money`. Оракул: `tools/php-oracle/gen-round-fixture.php` (README там же, раздел «round()»).

- [x] **MQ-1. Какая версия PHP в проде старого Laravel? — 8.4+ (по факту `composer.lock`); формальное подтверждение — за владельцем.**
  - Факт: `../Zafiro/composer.lock` требует PHP ≥ 8.4.1 у **рабочих** (не dev) пакетов — `symfony/http-kernel`,
    `symfony/console`, `symfony/http-foundation`, `symfony/routing` и др. v8.1.x (`"php": ">=8.4.1"`); dev — PHPUnit 13.2.6,
    `brianium/paratest` (`~8.4.0 || ~8.5.0`). На PHP 8.3 `composer install` без `--ignore-platform-reqs` не пройдёт, а
    оракулы (`tools/php-oracle/run.sh`) гоняют Laravel на `php:8.4.27-cli`. `composer.json` (`"php": "^8.3"`) ниже, чем lock.
  - Решение в коде: `money.PHPRound` = `round()` **PHP 8.4** (перенос `_php_math_round()` с тега php-8.4.27; сверен побитно с
    PHP 8.4.27 на 310 449 значениях, 0 расхождений). Реализация 8.3 сохранена как `money.PHPRound83` (только справка/тесты,
    фикстура `testdata/php83_round.json`). Всё остальное в пакете (`FromTengeFloat`, `BasisPoints`, `FormatFloat2`,
    `StoredCents`, `ParseTengeViaFloat`…) считает через `PHPRound`, то есть по 8.4.
  - PHP 8.5: `ext/standard/math.c` в ветке PHP-8.5 совпадает с php-8.4.27 байт в байт; на `php:8.5-cli` (8.5.12) полный набор
    `round()` и вся фикстура (`(int)`, `number_format`, строки, центы) — те же байты, что на 8.4.27. Отличие 8.5 только в
    предупреждениях: `(int)` от float вне int64 и NAN → строка печатают Warning (значения прежние). Дефолт — 8.4.
  - Что меняется по сравнению с 8.3 (проверено на `php:8.4.27-cli` и локальном 8.3.6):
    - `(int) round($x * 100)` (`TopUpBonus::for()`, `Friends::storedCents()`, `discounted()`, `PercentLevels`): в 8.4 это ровно
      `math.Round(x*100)`. `1.005 → 100` (8.3: 101), `0.145 → 14` (8.3: 15), `0.285 → 28` (8.3: 29); `discounted(1000000, 0.145)` =
      998600 (8.3: 998500), `discounted(1000000, 1.005)` = 990000 (8.3: 989900). Расходится у 1 147 из 25 000 сумм `x.xx5`
      и 452 из 10 000 крупных.
    - `round($x, 2)` / `number_format($x, 2)` у сумм `x.xx5`: 8.3 и 8.4 совпадают (0 из 100 000), но **не** равны наивному
      `math.Round(x*100)/100` (4 588 из 100 000: `1.005 → 1.01`, наивно 1.00).
    - Всего 8.3 и 8.4 расходятся в 13 475 из 310 449 значений (в основном соседи половин и большие/малые масштабы).
  - Нюанс переноса: `php_intpow10(n)` при n > 22 зовёт glibc `pow(10, n)`, который не округлён корректно: для n = 23 и 210
    он на 1 ulp больше, чем `1e23`/`1e210` (сверено с PHP для всех n 23…308). В `phpIntPow10` это учтено (влияет только
    на `|places| ≥ 23`, не на деньги).
  - Осталось: владельцу подтвердить `php -v` на сервере (`/home/admzafiro/Zafiro`). Если вдруг 8.3 — заменить `PHPRound` на
    `PHPRound83` в `FromTengeFloat`/`BasisPoints` (одна строка в каждой) и пересчитать фикстуры профильных пакетов.
  - Решение (30.10.2026): сделано: эталон — PHP 8.4 (`composer.lock`), `money.PHPRound` = 8.4.

- [x] **MQ-2. В `docs/business-rules.md` BR-001 был неверный пример про наивный Go — исправлено.**
  - Было: `math.Round(x*100)` даёт `1234 / 10000 / 100 / 267` для `12.345, 100.005*100, 1.005*100, 2.675`. Во float64
    `12.345*100`, `100.005*100`, `2.675*100` — ровно `.5`, поэтому наивный ответ совпадает с PHP. А `1.005*100 = 100.49999999999999`
    в PHP 8.4 тоже даёт 100, как и наивный вариант (101 — только в 8.3).
  - Теперь BR-001 описывает алгоритм 8.4 и примеры: `round($x)` ≡ `math.Round`; `round($x, 2)` ≠ `math.Round(x*100)/100`
    (`1.005 → 1.01`, `0.285 → 0.29`). Пример в CLAUDE.md («Деньги») обновлён так же.
  - Ловушка в Go: константное выражение `100.005 * 100` вычисляется **точно** (без float64), поэтому в тестах множители надо
    передавать переменными (в `money_test.go` — `mul()` с `//go:noinline`).
  - В §0 `business-rules.md` (стр. 15, «round(x) … с «предокруглением» … см. BR-001») осталась формулировка 8.3 — поправить
    владельцу документа (агент правил).
  - Решение (30.10.2026): сделано (BR-001 и CLAUDE.md исправлены); остаток — формулировка §0 `business-rules.md`.

- [x] **MQ-3. Касса: что именно MySQL получал от PHP-float.**
  - Проверено на `mysql:8.4.13` (strict mode): строка в `decimal(12,2)` округляется половиной от нуля по десятичной записи
    (`'1.005' → 1.01`, `'-1.005' → -1.01`, `'12.999' → 13.00`, `' 7.125 ' → 7.13`, `'1.5e2' → 150.00`); `'1,5'`, `'abc'`, `''`,
    `'0x1A'`, `'1.5x'`, `'1e400'` — ошибка 1366; выход за `decimal(12,2)` (`'9999999999.995'`, `'123456789012.34'`) — ошибка 1264.
    `d + 1.005` и `d + '1.005'` дают одинаковые 1.01 (и `2.675 → 2.68`). Таблица — `TestParseTengeRoundedMySQL`.
  - PHP-float уходит в SQL строкой `(string)$float` с `precision = 14` (Eloquent `increment()` вставляет число в SQL,
    PDO-параметры — `PARAM_STR`). Для этого есть `money.FromTengeFloatDecimal` = `ParseTengeRounded(PHPFloatString(f))`.
    Не проверено на живом Laravel (vendor в `../Zafiro` не установлен): точный путь `increment()`/каста `decimal:2` в версии
    Laravel старого проекта — пусть подтвердит агент кассы оракулом `tools/php-oracle` (Pest в копии Zafiro).
  - Рекомендация: в кассе для ввода пользователя — `ParseTengeRounded(строка запроса)`; для сумм, которые PHP считал во float
    (`$total += (float)$price * $qty`) — повторять float-формулу и `FromTengeFloatDecimal`.
  - Следствие PHP 8.4 (MQ-1): пополнение `"1.005"` зачисляется как 1.01 (MySQL округляет строку `"1.005"`), а бонус
    считается от `(int) round(1.005 * 100) = 100` тиынов (в 8.3 было 101). Расхождение «зачислено 101, база бонуса 100» —
    поведение старого кода на 8.4, `cash.ParseTopUpAmount` возвращает оба значения (`Amount`, `BonusBase`).
  - Решение (30.10.2026): по DECISIONS Q-002 — ввод пользователя: строго ≤ 2 знаков (иначе 422), разбор в тиыны; суммы, которые PHP считал во float, — float-формула + `FromTengeFloatDecimal` (рекомендация).

- [x] **MQ-4. Граница `MaxAmount = 1e15` тиынов (10 трлн ₸).**
  - Больше любого `decimal(14,2)` старой схемы (≈ 1e14 тиынов), меньше 2^53 (суммы точно представимы во float64).
    `ParseTenge*` возвращают `ErrOutOfRange` выше неё, `Add`/`Sub`/`MulDivRound` проверяют переполнение int64.
    Пределы конкретных колонок (`decimal(12,2)` = 999 999 999 999 тиынов) пакет не проверяет — это валидация места вызова.
  - Рекомендация: оставить; если владелец хочет повторить ошибку MySQL 1264 буквально — проверка на уровне формы/сервиса.
  - Решение (30.10.2026): принята рекомендация: оставить `MaxAmount = 1e15`; пределы колонок — валидация места вызова.

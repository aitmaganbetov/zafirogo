# Этап 3 — визуальное сравнение (F2): вопросы и принятые решения

Инструмент — `tools/visual/README.md`. Владелец поручил решать самостоятельно по принципам `docs/DECISIONS.md`;
ниже — решение и причина по каждому пункту.

## V-1. Фиксированное «сейчас» в новом сервере не действует на `now()` в SQL

- Контекст: `dev.fixed_now` (`ZAFIRO_DEV_FIXED_NOW`, `server/internal/config`) подменяет часы приложения: billing
  (`billingsvc.ClockFunc`), касса (`cashsvc.Service.Now`), обработчики админки (`httpserver.Options.Now`). Запросы
  с `now()` в `db/queries/*.sql` (28 мест: сессии, покупки, балансы, касса, ledger, outbox) берут время Postgres.
  Подменить время Postgres без libfaketime нельзя.
- Решение: правило для агентов экранов — время, от которого зависит **показанное** («сегодня», остаток сессии, «онлайн
  за 90 с»), передаётся в запрос параметром из `opts.Now`, а не `now()` в SQL (так же, как старый код брал `now()`
  Carbon в PHP). Записи времени событий (`created_at` ledger/outbox) остаются на `now()`. Записано в README.

## V-2. Статус ПК «в сети» в новом — Valkey, а демо-данные — только Postgres

- Контекст: старый считает «в сети» по `last_seen_at` за 90 с (`ClubComputer::currentStatus()`) и `status = 'online'`
  (`ClubComputerSessions::changes()`); новый хранит присутствие в Valkey (`internal/agent/presence`), в Postgres — только
  смены состояния (`status`, `last_seen_at`, `agent_state`). Сверка присутствия (`agent.sweeper.reconcile_every`)
  сбросила бы `status = 'online'` без живого потока.
- Решение: `visual-seed` пишет `status`/`last_seen_at`/`agent_state` (как старый), визуальный сервер запускается со
  сверкой раз в сутки (`ZAFIRO_AGENT_SWEEPER_RECONCILE_EVERY=24h`). Если экран карты/списка ПК будет брать «в сети»
  из Valkey, агент этого экрана добавляет в `visual-seed` запись присутствия (`presence.Store.Acquire` + `Refresh`
  с длинным TTL) — без симулятора агента.

## V-3. Внешние ресурсы старых страниц (CDN) в снимках

- Контекст: старые страницы грузят Font Awesome 6.4.0 с cdnjs, Chart.js 4.5.1 с jsdelivr, Inter с Google Fonts;
  в этой среде cdnjs и jsdelivr закрыты прокси (403), в CI сеть есть, но снимок не должен от неё зависеть.
- Решение: Playwright перехватывает запросы: cdnjs/jsdelivr → те же файлы из npm-пакетов тех же версий
  (`tools/visual/package.json`, версии точные), Google Fonts → кэш (`curl` один раз), прочее внешнее — блок с
  записью в отчёт. Новый по Q-064 берёт шрифты и иконки из npm; если версия Inter в npm отличается от Google Fonts
  v20 и это даёт расхождение текста выше порога — это осознанное отличие: маска или порог с объяснением в `note`.

## V-4. Порог совпадения

- Контекст: pixelmatch 8.0.0, сравнение полностраничных снимков; повторный прогон тех же страниц без изменений —
  0–17 отличающихся пикселей на снимок 1440×1318 (0,001 %).
- Решение: по умолчанию `pixelThreshold` 0.1 (цвет, OKLab), сглаживание не считается, `maxDiffPercent` 0.5 %
  площади. Повышать порог страницы — только с причиной в `note`. Живые элементы — маски, а не порог.

## V-5. Время записей, которые новый сервер ставит сам

- Контекст: журнал действий нового (`activity.Record`) пишет `time.Now()`, ledger и audit_log — `now()` транзакции.
- Решение: `visual-seed` после каждой кассовой операции выставляет `activity_logs.created_at` = `at` операции
  (как старый под `Carbon::setTestNow`). ledger и audit_log — только добавление (триггеры), их время — время загрузки;
  в интерфейсе клуба они не показываются (история клиента — из `activity_logs`/`session_purchases`).

## V-6. Заказы с ПК и сессии в демо-данных — без движения денег

- Контекст: настоящий заказ с ПК списывает баланс (`AgentShop::purchase()` / `shop.Service`), сессия ПК — покупка тарифа.
- Решение: в демо-данных заказы (`shop_orders`) и идущие сессии (`club_computers.current_session_*`) — готовые записи
  без списаний в обоих приложениях (балансы клиентов от них не меняются ни там, ни там). Для экранов, где важна связь
  заказа/сессии с деньгами, агент экрана добавляет операцию в `operations` и выполняет её сервисом в обоих загрузчиках.
  `session_purchases` не заполняются (в новой схеме — дополнительные `zone_id`, `source`).

## V-7. Заморозка времени и сессия старого Laravel

- Контекст: Laravel считает срок cookie сессии от `now()`; при `Carbon::setTestNow(2026-10-15)` срок оказывается
  в прошлом для браузера, cookie удаляется, вход «молча» возвращает на `/login` (419).
- Решение: в `.env` копии `SESSION_EXPIRE_ON_CLOSE=true` (cookie до закрытия браузера). Проверка свежести файла сессии
  (`filemtime` против замороженного `now`) этим не задета. Правки — только в копии (`~/.cache/zafirogo-visual/old`).

## V-8. Вход в новый, пока экран входа не перенесён

- Решение: `login()` ищет форму `#phone` на `/login` (разметка старого `auth/login.blade.php`); нет формы — `POST
  /api/auth/login` в контексте браузера (refresh-cookie). Способ входа виден в отчёте. Лимит `web-login` на
  визуальном сервере выключен (`ZAFIRO_RATELIMIT_DISABLE=web-login`): каждый снимок входит заново.

## V-9. Dependabot для `tools/visual/package.json`

- Контекст: новые закреплённые npm-зависимости (`pixelmatch` 8.0.0, `pngjs` 7.0.0, `@fortawesome/fontawesome-free` 6.4.0,
  `chart.js` 4.5.1). `.github/dependabot.yml` — не файл F2.
- Решение: добавить в Dependabot экосистему npm с `directory: /tools/visual`, **игнорируя** обновления
  `@fortawesome/fontawesome-free` и `chart.js` (их версии равны версиям CDN старого проекта и меняются только вместе
  с ним). Сделать при следующей правке `dependabot.yml` (оркестратор).

## V-10. Окружение нового сервера для сравнения

- Решение: отдельный проект compose `zafirogo-visual` (`tools/visual/compose.yml`) в tmpfs на своих портах: прогон не
  трогает базу разработки и каждый раз начинается с чистой схемы. Пароли — случайные, создаются `new.sh` в
  `~/.cache/zafirogo-visual/new/secrets.env` (в репозитории их нет).

## V-11. Записи и метрики, которые пишет сам прогон снимков

- Контекст: каждый снимок входит заново. Вход сотрудника пишет `auth.login` в журнал клуба, вход суперадмина —
  `superadmin.login` в журнал платформы; HTTP-запросы прогона попадали в метрики экрана «Сервер», а снимки загрузки
  клубов — в «Загрузку по часам» карточки клуба. У старого в стенде нет планировщика (метрики не собираются), а время
  записей — замороженное `Carbon::setTestNow`.
- Решение: (1) журнал клуба при входе/выходе и неудачном входе берёт время из часов приложения (`dev.fixed_now`), как
  журнал платформы; (2) задачи мониторинга нового в стенде выключены — `dev.disable_workers` (только dev/test, в prod —
  ошибка валидации; неизвестное имя — ошибка запуска); (3) в `demo.json` — 10 записей журнала платформы
  (`platform_logs`), чтобы «Последние действия суперадминов» (последние 10) всегда были полными; (4) страницы
  суперадмина снимаются по порядку в одном воркере — иначе параллельный вход между снимками старого и нового менял
  число строк журнала платформы в паре.

## V-12. Падения Chromium и очень длинные страницы

- Контекст: полностраничный снимок выше ~14 500 px при ширине 1440 (wiki — 26 000 px) — «Unable to capture
  screenshot» и падение браузера; браузер воркера оставался мёртвым, и следующие страницы падали с «Target page,
  context or browser has been closed». Плюс «Target crashed» при почти полном диске: Playwright по умолчанию держит
  общую память рендерера во временных файлах (`--disable-dev-shm-usage`).
- Решение: снимок выше 12 000 px — верх страницы этой высоты (в отчёте «Обрезано»); упавший браузер воркера
  заменяется новым, снимок после падения вкладки/браузера повторяется один раз (в отчёте «Повтор»); Chromium стенда —
  с `/dev/shm` (без `--disable-dev-shm-usage`).
